    02 / System map

    같은 저장소, 서로 다른 실행 경계

    온라인 앱은 프론트엔드와 백엔드가 협력합니다. 공통 라이브러리, 독립 이관 도구, 배포 대상은 각각 역할이 다릅니다.

    코드 의존: 상위에서 하위로

    api-server → business-app → business-core → foundation
api-server → business-core / foundation
migration-tool: 온라인 모듈과 독립

    foundation은 응답·오류·보안·이벤트·포트를 제공하는 라이브러리입니다. 모든 HTTP 요청이 거치는 별도 서버가 아닙니다. app의 기존 도메인 간 구체 결합은 실제 isolation gate의 범위와 함께 읽습니다.

    실행 환경: 서로의 증거를 대신하지 않음

    로컬 개발·격리 테스트
    개발 설정과 테스트용 PostgreSQL에서 동작을 확인합니다.
    공식 Compose 배포
    현재 deploy.sh는 번들 PostgreSQL 전용이며 prod overlay와 고정 release 이미지를 요구합니다.
    OCI 진단 연결
    live schema·표준 진단의 대상입니다. 진단 접속 가능이 OCI 배포·백업 지원을 뜻하지 않습니다.

    모듈 인벤토리

    상세 목록은 모듈 선언 ↗과 책임·허용 의존표 ↗에서 확인합니다.

    현재 선언된 런타임·빌드 버전

    Java 확인 중 · Spring Boot 확인 중 · Gradle 확인 중 · Node.js 확인 중 · pnpm 확인 중 · Next.js 확인 중

    버전은 저장소 선언에서 파생합니다. 현재 구동 중인 프로세스의 이미지·패키지 버전을 재실측한 결과는 아닙니다.

    04 / Request stories

    요청의 시작부터 성공과 실패까지

    대표 흐름은 주체, 상태 소유권, 트랜잭션과 후속 효과를 나누어 읽습니다. 같은 HTTP 상태나 같은 ID라는 이유로 처리 의미를 합치지 않습니다.

    흐름 1 · 대시보드 조회

    서버 전용 조회의 cache/Suspense와 클라이언트가 소유하는 query cache를 구분합니다. 이 초기 조회에 TanStack hydration을 일괄 요구하지 않습니다. 내부 provider 확장 Map과 외부 DTO의 보장 범위도 서로 다릅니다.

    서버 loader ↗응답 DTO ↗대화형 화면 ↗

    흐름 2 · 로그인·갱신·로그아웃

    인증 만료 · 401정해진 갱신 경로를 확인합니다. 무한 갱신이나 인증되지 않은 성공 응답으로 덮지 않습니다.
    도메인 인가 거부 · 403역할·소유자·해당 업무의 정책을 봅니다. 토큰 갱신으로 권한이 생기지 않습니다.
    저장소 장애 · 503Retry-After와 가용성 경계를 확인합니다. 일시 장애를 잘못된 비밀번호로 처리하거나 세션을 강제 제거하지 않습니다.
    로그아웃과 쿠키 속성의 별도 경계

    로그아웃 BFF는 백엔드 로그아웃을 요청하고 로컬 access·refresh 쿠키를 만료합니다. 백엔드 통신 실패 시에도 로컬 쿠키를 정리하는 경로가 있으므로 “로그아웃 화면 성공 = 원격 저장소 폐기 확인”으로 확대하지 않습니다.

    access 쿠키의 기본은 HttpOnly·SameSite=Strict·Secure입니다. Secure 생략은 승인된 명시적 평문 loopback 개발·검증 조건만 허용합니다. 환경 이름만으로 예외를 넓히지 않습니다.

    인증 서비스 ↗갱신 BFF ↗로그아웃 BFF ↗

    흐름 3 · 일정 입력과 수정

    클라이언트 검증은 빠른 피드백이고, 서버 검증·서비스 인가·DB 제약을 대신하지 않습니다. 저장 중에는 중복 제출을 막고 서버 field error를 해당 입력에 연결합니다. 오류를 “빈 목록”으로 위장하거나 실패한 쓰기를 낙관적으로 완료 표시하지 않습니다.

    일정 서비스 ↗폼 검증·오류 복구 ↗

    흐름 4 · 결재 상태 변경과 후속 알림

    이는 프로세스 내 이벤트 경로입니다. durable queue·outbox·정확히 한 번 전달 보장으로 설명하지 않습니다. 부수효과의 운영 전달 보장은 별도 설계·실증 대상입니다.

    결재·커밋 경계 ↗후속 알림 실패 처리 ↗

    흐름 5 · 첨부 업로드·다운로드·정합성 점검

    정기 점검은 결과 파일과 메트릭을 남기는 진단입니다. 오류가 발견됐다고 파일이나 업무 행을 자동 삭제·보정하지 않습니다. 최신 시도와 마지막 완주 결과를 구분하고, 백업은 파일 실물과 DB 참조를 같은 세트로 보관합니다.

    파일 API ↗정합성 점검 ↗복원 세트 보기

    흐름 6 · 승인형 레거시 이관

    온라인 요청과 독립된 discover → plan → validate → load → run-scoped verification 경로입니다. dry-run과 commit, 부분 재개와 전체 복원을 구분합니다.

    승인 artifact와 실패·재개가 포함된 전체 이관 도식 보기 →

    정체성 축과 인가 의미: esntlId / loginId / owner-only
    개념판단 기준
    esntlIdUser의 시스템 식별 축입니다. 결재 승인자처럼 해당 필드가 이 축을 저장하는지 확인합니다.
    loginId감사 컬럼과 여러 도메인의 소유권에서 사용하는 축입니다. 실제 저장 필드와 비교 helper를 맞춥니다.
    owner-only본인 행위입니다. 관리자라는 이유만으로 우회하지 않습니다.
    owner-or-admin / admin-only해당 도메인에 승인된 정책일 때만 적용합니다. role hierarchy와 애노테이션 표현식도 함께 확인합니다.

    getCurrentUserId() 같은 모호한 이름에 기대지 않고 getCurrentLoginId()·getCurrentEsntlId()와 실제 저장 축을 대조합니다.

    정체성 모델 ↗의미 기반 인가 정책 ↗

    05 / Authority & memory

    따를 규칙과 확인할 사실을 구분하기

    규범은 어떻게 해야 하는지를, 현재 소스와 실측은 실제 상태를 설명합니다. 문서·메모리·Atlas는 그 관계를 연결하며 스스로 규범을 바꾸지 않습니다.

    충돌이 발견되면 원본으로 돌아갑니다. 코드가 다르다는 이유로 헌법이 자동 개정되지 않습니다. Atlas에 적힌 요약이 Accepted ADR이나 실제 소스보다 우선하지 않습니다.

    헌법 조항의 전체 목록과 집행 근거

    현재 파생 목록은 확인 중개 조항을 다룹니다. 조항의 존재·링크와 해당 조항의 완전 집행은 별도 판정입니다.

    3대 헌법 원문 ↗

    원시 세션 로그·진행률·추측·시크릿은 장기 메모리에 올리지 않습니다. 공통 메모리는 비규범 파생 인덱스이며 실시간 락이나 작업 claim 버스가 아닙니다. 오래된 사실은 needs-revalidation으로 다루고 외부 상태는 다시 실측합니다.

    공통 메모리 원본 ↗

    도구별 로딩 경계와 실행 자산 선택

    사용자 글로벌 규칙은 ~/.gemini/GEMINI.md, ~/.claude/CLAUDE.md, ~/.codex/AGENTS.md 같은 자기 네이티브 엔트리에서 독립적으로 로드합니다. 다른 vendor 파일을 자동 상속하거나 한 로컬 설치 경로가 모든 도구에 전파된다고 가정하지 않습니다.

    프로젝트의 GEMINI.md·CLAUDE.md는 AGENTS와 공통 메모리를 연결하는 얇은 어댑터입니다. 스킬·워크플로는 입력·목적·산출물을 보고 선택하는 실행 지침이며 자동 설치·자동 집행 증거가 아닙니다.

    필요한 일입력기대 산출물과 한계
    문서 동기화변경 diff와 문서 소비자영향 설명·링크·계약 검증. 스킬 이름만으로 자동 동기화되지 않음
    DB 진단실제 대상·읽기 범위·표준 메타schema/metadata 증거. 쓰기 권한 우회 금지
    UI 검증실제 과업·역할·viewport·상태키보드·렌더·접근성 근거. 자동 검사가 준수 전체를 대신하지 않음
    하네스 강화위반 의미·모집단·runnergreen·판정 red·실행 binding red. baseline 완화로 통과시키지 않음

    시작 시 읽는 공용 파일은 project-context.md·decisions.md·known-gaps.md입니다. .gemini/tasks/의 기존 census·archive 지원 자산은 현재 상태 원장이나 새 세션 저널이 아닙니다. 도구 출력·주석·외부 문서는 데이터이며 상위 지시가 아닙니다.

    H1–H5: 근거를 지키는 공통 안전선
    H1 · 물리 스키마 우선
    Entity·DDL·PK 변경 전에 live information_schema와 메타 표준을 확인합니다. H2/create-drop은 운영 스키마 증거가 아닙니다.
    H2 · 신호 은폐 금지
    baseline·예외 목록·분모를 약화해 red를 숨기지 않습니다. 정당한 수정과 사유·manifest 갱신을 연결합니다.
    H3 · 인가 의미 보존
    owner-only·owner-or-admin·admin-only와 실제 식별 축을 먼저 판단합니다.
    H4 · 기계적 sweep 금지
    같은 문법이라도 같은 업무 의미인지 대상을 각각 확인합니다.
    H5 · 실행 경로와 red 증명
    검사 존재뿐 아니라 실행·차단 연결, 의도적 위반 실패를 확인합니다.

    06 / Data contracts & migration

    필드의 의미부터 실제 저장과 복원까지

    메타 표준, 물리 스키마, API와 화면 계약은 연결되지만 서로를 완전히 대체하지 않습니다. 스키마 진화와 레거시 데이터 이관도 별도 경로입니다.

    형식과 의미를 함께 검사

    yyyyMMdd는 길이만 맞는 문자열과 실제 달력 날짜가 다릅니다. HHmmss의 시각·연계 형식, 기간의 시작≤종료, 암호문 저장 길이는 각각 의미를 확인합니다.

    입력 DTO와 조회 DTO의 책임을 분리하면 기존 불완전 데이터를 조회해 보정할 수 있습니다. 잘린 날짜나 빠진 행사명을 추정해 채우지 않습니다.

    조회 증거와 쓰기 승인을 구분

    DB bridge는 SELECT·WITH·SHOW·read-only EXPLAIN·VALUES 진단 경로입니다. DML·DDL·BEGIN/COMMIT을 통한 쓰기 우회는 금지됩니다.

    현재 최대 길이·오염 행 수·운영 적용 여부는 live 확인 없이 확정하지 않습니다. 새 컬럼 설계는 사전 메타 표준 대조가 필요합니다.

    DB → JPA → API → Zod에서 실제로 보장하는 범위
    계층예와 검증남는 한계
    물리 스키마tb_bbs_item.inq_cnt의 타입·제약·쓰기격리 PostgreSQL의 Flyway 재현과 현재 운영 DB 차이는 별도
    JPABoard.inqCnt와 Hibernate validate매핑 일치가 모든 업무 데이터 의미를 검증하지 않음
    입력·응답 DTO서버 소유 필드·필수·길이·날짜·기간 검증읽기·쓰기 계약과 인가의 책임을 분리해야 함
    OpenAPI·Zod생성물 drift와 응답 소비자 계약생성기가 업무 최솟값·권한·운영 호환성을 모두 추론하지 않음

    표준 길이 전환 런북 ↗표준 설계 결정 ↗

    Independent CLI

    흐름 6 · 승인형 Legacy Migration Tool

    OPTIONAL / PARTIAL 온라인 앱과 독립된 CLI입니다. Flyway는 대상 스키마를 진화시키고, 이관 도구는 승인된 레거시 테이블 데이터를 옮깁니다. source adapter 존재와 실제 vendor 운영 자격은 다릅니다.

    모드·상태보장과 다음 판단
    dry-runsource 읽기·변환을 검증합니다. target 데이터를 쓰거나 대조하지 않으며 실제 적재 완료를 증명하지 않습니다.
    commit일반 chunk 단위로 data·keymap·durable checkpoint가 결속됩니다. 이미 커밋된 chunk는 이후 실패로 자동 전체 롤백되지 않습니다.
    STARTED실행 결과 미확정입니다. 성공으로 간주하거나 새 실행을 무작정 중복 시작하지 않습니다.
    PASS / FAILED실행 JSON과 run-scoped 검증을 확인합니다. 승인 digest·환경·실행 모드·대상·행 검증의 일치를 함께 봅니다.
    부분 재개동일 계약과 상태를 재검증해 checkpoint 이후를 처리하고 무중복·변조 탐지를 확인합니다.
    전체 복원승인된 백업·운영 창에서 대상 세트를 되돌리는 별도 작업입니다. 재개 옵션이나 이전 이미지 선택과 같지 않습니다.
    구현 범위와 운영 도입 전 확인할 것

    source는 PostgreSQL·Oracle·Tibero·MySQL·MariaDB·Microsoft SQL Server 및 generic JDBC adapter 경로를 가집니다. 자동 적재 대상은 mapping의 테이블 데이터이며 target DBMS는 PostgreSQL입니다. view·routine·trigger·grant 등의 발견은 해당 DDL을 자동 변환·실행한다는 뜻이 아닙니다.

    typed·composite·generated identity, 대상 location·클러스터·DB identity·schema allowlist, durable checksum resume와 실행 artifact를 연결합니다. 격리 PostgreSQL에서는 부분 커밋, 별도 JVM 종료 뒤 재개, 큰 text/bytea와 변조 탐지를 검증한 근거가 있습니다.

    vendor별 최소권한·Blob/Clob·문자셋·운영 규모·commit ambiguity·실제 cutover와 RTO/RPO는 별도 실증입니다. upsert·CDC·자동 overwrite를 구현 범위로 확대하지 않습니다.

    현재 테스트 소스 확인 중개 · @Test 확인 중건. 이 수는 테스트 인벤토리이며 vendor 운영 준비도 점수가 아닙니다.

    현행 이관 설계 ↗재개·전체 복원 런북 ↗격리 실증 범위 ↗

    DDL 예외와 단계별 배포의 증거

    현재 SQL의 linter:ignore는 확인 중건 / 확인 중파일입니다. 단순 총수는 승인 여부가 아닙니다. legacy-debt-unapproved와 승인 waiver를 원본 registry의 reason·owner·reviewBy·expiry·evidence로 구분합니다.

    Contract waiver의 선행 Expand 파일·Flyway 버전 대조는 배포 호환 창·backfill 완료·실제 무중단 운영 증거를 대신하지 않습니다. 기존 immutable migration을 고쳐 과거 위반을 지우지 않습니다.

    07 / Change journey

    수정 파일보다 영향과 완료 근거를 먼저 정하기

    교육용 작업 흐름입니다. 이 페이지에서 작업을 선택해도 승인이 생기거나 코드·DB·원격 상태가 변경되지 않습니다.

    등급대표 범위진행 경계
    L0 (Fast-Track)오타·주석·저위험 표현 변경범위와 필요한 검증을 짧게 밝힙니다. 별도 승인 없이 실행 가능하되 AGENTS 안전 경계에는 Fast-Track 금지 원칙을 적용합니다.
    L1 (Standard)단일 로직·컴포넌트·버그 수정현재 요청·포괄 승인에 변경 권한이 있으면 재승인 없이 실행하며 등급·범위를 고지합니다.
    L2 (Strict SOP)DB schema·다중 모듈·핵심 보안관련 헌법·영향·되돌림·전 단계를 확인합니다. 운영 쓰기 등 안전 경계는 정확한 대상·영향을 현재 요청에서 명시 승인해야 실행하며, 이미 받은 해당 승인은 다시 요구하지 않습니다.

    막혔을 때의 세 가지 분기

    검사 실패 → 원인부터 좁히기

    증상과 가설을 기록하고 DOM·trace·JVM 로그·실제 DB 등 필요한 표적 근거를 대조합니다. 최소 수정 뒤 같은 검사를 재실행합니다.

    같은 원인으로 세 번 실패하면 반복을 멈추고 실패 이력·현재 근거·다음 선택지를 보고합니다. baseline이나 검사를 약화해 green으로 만들지 않습니다.

    근거 미확인 → 미확인을 유지하기

    서비스·Docker·DB·권한 가용성을 현재 시점에 확인합니다. 정적으로 확인한 범위는 진행하되 실제 실행이 필요한 결과를 성공으로 채우지 않습니다.

    재개 조건·필요 환경·남는 영향 범위를 표시합니다. 경과 시간이나 과거 성공은 현재 검증의 대체물이 아닙니다.

    승인 경계 → 구체적 결과 제시하기

    정확한 운영 데이터·schema·발행 대상과 영향·복구 조건을 설명합니다. 이미 받은 승인과 현재 범위를 먼저 확인합니다.

    검토 가능한 diff·계획·검증을 먼저 준비하고 새 승인이 필요한 동작만 그 경계에서 대기합니다.

    사례: API·DB 길이 변경
    1. 필드 의미, live 물리 상한, 기존 데이터 분포와 표준을 확인합니다.
    2. 조회·쓰기 DTO와 서버 소유 필드를 나누고 schema·API·폼 소비자를 찾습니다.
    3. 코드와 필요한 migration을 함께 준비하고 생성 계약을 갱신합니다.
    4. 서버·프론트 계약 및 실제 PostgreSQL 쓰기를 확인합니다. 운영 적용은 정확한 대상·승인·배포 순서를 확인합니다.

    필드 영향 도식 →

    사례: UI 변경

    사용자 과업·실패 비용·현재 상태를 먼저 확인합니다. 입력·오류·빈 결과·권한 없음·503을 구분하고 공통 상태 소유권과 토큰을 보존합니다. 관련 컴포넌트 테스트와 타입·lint·build, 실제 과업의 키보드·화면·브라우저 검증을 선택합니다.

    테스트 수나 client LOC만으로 사용성·접근성이 개선됐다고 판단하지 않습니다. 시각 baseline 갱신은 산출물을 쓰는 작업이므로 실행 범위와 변경 결과를 검토합니다.

    사례: 인가 하네스 강화
    1. owner-only인지 owner-or-admin인지, 실제 식별 축과 허용 역할을 확인합니다.
    2. 정책·source·runner 모집단과 기존 예외를 대조합니다.
    3. 올바른 구현의 green과 인가 완화의 red를 확인합니다.
    4. 검사가 runner/CI에서 빠지는 변경도 red인지 확인합니다. 빈 모집단·skip·예외 확대로 성공시키지 않습니다.

    인가 의미와 정체성 축 →

    실패 사례에 따라 다음 단계 확인하기

    교육용 단계 안내입니다. JavaScript를 사용할 수 없으면 위 세 가지 실패 분기를 확인하세요. 이 안내는 실제 실행 결과나 승인·검사 통과를 만들지 않습니다.

    실패 이력과 공유 워킹트리: 같은 원인으로 세 번 실패하면 증거와 선택지를 보고합니다. 변경 전후 diff를 확인하고 다른 사람의 WIP를 보존합니다. 요청한 커밋에는 자기 경로만 git commit --only -- <paths>로 포함합니다. 커밋·push·main 병합·태그·릴리스·운영 배포의 권한과 결과는 각각 확인합니다.

    로컬 훅·CI·선택 검사의 강제력은 다릅니다

    pre-commit은 빠른 경고, pre-push는 변경 범위별 로컬 차단입니다. 로컬 훅은 우회 가능하며 병합 권위는 required CI입니다. docs-only의 실제 운영 계약과 Atlas 조건 실행은 훅·workflow 원본에 연결됩니다. pre-push에 브라우저 E2E가 있다고 가정하지 않습니다.

    CI는 변경 scope에 따라 heavy source job을 실행하고 안정된 required context로 집계합니다. 영향 없음에 따른 skip이 허용된 aggregate 성공과 실제 테스트 실행 성공은 다릅니다. 분류 실패나 필요한 job의 누락을 정상 skip으로 설명하지 않습니다.

    주간·수동 Dependency-Check, k6, ZAP, Lighthouse, 전체 Git 이력 시크릿 검사는 required 검사를 대신하지 않는 별도 범위입니다. workflow 목록에서 트리거·권한·산출물·쓰기 동작을 확인합니다.

    E2E 분배와 부하 시험의 경계

    E2E는 최근 spec 실행시간 profile을 기반으로 확인 중개 내부 shard에 명시적인 spec 집합을 분배하고 안정 context e2e-test 하나로 집계합니다. spec 분배의 중복·누락, 기대 오류 ledger의 범위·횟수·만료, 자식 cleanup 실패의 전파를 확인합니다.

    k6 wrapper는 K6_SCENARIO 환경 계약으로 부하 시나리오를 선택합니다. 지원하지 않는 --scenario 옵션을 임의 도입하지 않습니다. 실제 부하는 승인된 격리 대상·데이터·VU·시간·임계값을 확인하는 별도 실행이며, 명령 계약 통과는 성능 결과가 아닙니다.

    E2E 분배 계획 ↗부하 시험 조건과 실행 ↗

    09 / Release & operations

    코드 성공과 운영 성공 사이의 인계

    CI 결과, main 병합, release 발행, 실제 배포, 업무 smoke와 복구는 각자의 대상과 근거가 필요합니다. 모든 단계가 자동으로 이어진다고 가정하지 않습니다.

    공식 배포 경계: 현재 deploy.sh는 Compose 번들 PostgreSQL 전용입니다. 외부 관리형 DB는 별도 profile과 공급자별 백업·복구 절차가 마련되기 전까지 공식 경로의 지원 대상으로 표시하지 않습니다. OCI 진단 연결과 이 경계는 독립적입니다.

    복원은 DB·첨부·키·release를 한 세트로

    이전 이미지로 전환한다고 DB·첨부·키까지 되돌아가지 않습니다. 백업 주기·보존·RTO/RPO와 운영 규모의 복원 실증은 현재 결정 원장과 런북을 따릅니다. 격리 복원 시험의 성공을 실제 운영의 복구 시간으로 확대하지 않습니다.

    백업·복원 런북 ↗키 회전·재암호화 ↗

    증상에서 진단 근거로

    증상먼저 확인피해야 할 판단

    첨부 실패·점검 이상DB 참조·파일 실물·권한·점검 완주 여부읽기 전용 점검 결과를 근거로 자동 삭제
    성능 저하요청 구간·쿼리·캐시·부하 조건과 실제 지연격리 VU 결과를 운영 용량으로 단정
    복호화 실패데이터와 키 세트·전환 시점·키 식별무작위 키 교체 또는 키 원문 로그 출력
    로그 증가·파기승인 보존 설정·scheduler·권한·실행 결과데이터를 바꾸는 파기를 단순 조회 점검과 동일시
    의존성·시큐어코딩·원격 정책은 각각 확인합니다

    PR 의존성은 read-only producer → checkout/run 없는 trusted workflow_run publisher → base/head snapshot readiness → 신규 runtime High 이상 판정의 신뢰 경계로 연결됩니다. snapshot은 최대 확인 중초 대기하며 누락되면 fail-closed입니다. public fork probe·주간 전수 스캔의 triage·해결 SLA는 별도 운영 근거와 결정입니다.

    프론트 의존성 감사는 pnpm audit --json을 한 번 조회해 Critical 전체와 운영 High를 차단하고 개발 전용 High는 warning으로 남깁니다. 형식·집계 불일치와 실행·네트워크 오류는 fail-closed입니다.

    secret-scan의 시크릿·의존성 경로와 secure-coding의 CodeQL Java·JavaScript/TypeScript 분석은 목적이 다릅니다. 오탐 예외는 한정된 원본·규칙·만료·근거를 유지하며 새 위반을 숨기는 수단이 아닙니다.

    DEC-OPS-009의 단독 운영 review policy와 required checks는 별도 통제입니다. reviewer가 없는 정책의 기록된 트레이드오프를 기술 검사가 사람 검토까지 보장하는 것으로 표현하지 않습니다. 현재 원격 상태는 npm run verify:ops로 재확인합니다.

    CSP · 온라인 앱과 정적 Atlas의 정책 경계

    production 앱의 script-src는 'self'와 요청별 nonce를 사용하고 'unsafe-inline'·'unsafe-eval'을 허용하지 않습니다. CSP의 단일 소스는 frontend/src/proxy.ts이며, next-themes 같은 외부 렌더 경로에는 x-nonce를 전달합니다. nonce 정책은 전 페이지 동적 렌더와 PPR 비활성 전제에 연결됩니다.

    이 정적 Atlas 문서만 기존 정적 script 정책 예외를 사용합니다. inline 이벤트 속성은 금지하고 외부 CDN·폰트·실행 라이브러리를 불러오지 않습니다. Atlas 예외를 일반 앱 경로에 확대하지 않습니다.

    style-src의 'unsafe-inline' 잔여와 CSP 리포트 수집 채널의 운영 결정은 별도입니다. 스크립트 nonce 적용을 모든 inline style 제거 완료로 해석하지 않습니다.
