# 로컬 TOTP MFA 운영과 복구

[ADR-0025](../02-architecture/decisions/ADR-0025-enterprise-completeness-and-durable-operations.md)의 D11 A를 구현한 인증 흐름과 운영 적용 조건이다. 개발 migration·격리 검증은 실제 운영 DB 적용, 실계정 권한 배정, 운영 키 발급 또는 MFA 강제 전환을 포함하지 않는다. TOTP는 피싱 저항성 인증이 아니다.

## 적용 범위와 설정

일반 사용자는 내 계정에서 선택 등록한다. 보호계정은 현재 DB의 유효 권한에 `USER_PASSWORD`, `AUTHRT_GRANT`, `AUTHRT_ASSIGN` 중 하나가 포함된 계정이다. `ROLE_ADMIN` 같은 표시용 그룹 이름으로 분류하지 않는다.

| Spring 설정 | 환경 변수 | 의미와 기본값 |
| --- | --- | --- |
| `nuri.security.mfa.active-key-id` | `MFA_ACTIVE_KEY_ID` | 신규 암호화에 사용할 키 식별자. 기본 미설정 |
| `nuri.security.mfa.keys-json` | `MFA_KEYS_JSON` | 키 식별자와 표준 Base64로 표현한 32바이트 AES 키의 JSON 객체. 기본 미설정 |
| `nuri.security.mfa.require-protected` | `MFA_REQUIRE_PROTECTED` | 보호계정의 등록 의무. 기본 `false` |

두 키 설정이 모두 비어 있고 강제 적용이 꺼져 있으면 등록은 사용할 수 없다. 미등록 일반 계정의 기존 비밀번호 로그인은 유지된다. 키 없이 강제 적용을 켜거나, 키 설정 일부만 제공하거나, 키 형식·활성 키 식별자가 잘못되면 애플리케이션이 기동을 거부한다. 키링은 최대 16개 키를 수용한다.

이미 등록된 계정은 강제 적용 설정과 관계없이 MFA가 필요하다. 보호계정 강제 적용을 끄는 행위가 등록된 MFA를 해제하지 않는다. 현재 자격을 복호화할 키가 없으면 인증을 실패 처리하며 비밀번호만으로 우회하지 않는다. 정상 앱에서 키가 준비되지 않은 MFA 작업은 `MFA503`으로 중단된다.

키 값은 승인된 비밀 저장소나 배포 비밀 주입 경로로 제공한다. 저장소·명령 이력·지원 로그·채팅에 키, OTP, 복구코드 또는 토큰을 넣지 않는다. 이 문서는 복사 가능한 암호 예제값을 제공하지 않는다.

격리 브라우저 실행기와 CI E2E 샤드는 실행마다 새 키링을 만들고 해당 임시 API에만 주입한다. CI는 키와 JSON 전체를 마스킹한 뒤 환경 전달 파일에 기록한다. 이 테스트 설정은 기존 환경의 키를 상속하지 않으며 보호계정 강제 적용은 꺼 둔다. 운영 키 설정이나 운영자의 실제 권한을 테스트 fixture로 사용하지 않는다.

## 등록·로그인·재인증

| 단계 | 사용자 행동 | 서버가 발급하거나 폐기하는 것 |
| --- | --- | --- |
| 선택 등록 시작 | 내 계정에서 현재 비밀번호 확인 | 등록용 비밀과 제한 도전. 자격 버전이 바뀌어 기존 일반 세션은 사용할 수 없게 됨 |
| 필수 등록 진입 | 보호계정이 비밀번호 로그인 | `ENROLLMENT_REQUIRED` 제한 도전만 발급. 정상 access/refresh 토큰 없음 |
| 등록 확인 | 인증앱에 등록한 뒤 6자리 코드 입력 | 성공 counter 저장, 자격 활성화, 새 access/refresh, 일회용 복구코드 10개 |
| 등록된 계정 로그인 | 비밀번호 확인 후 6자리 코드 입력 | 비밀번호 단계에서는 `MFA_REQUIRED` 제한 도전만 발급. 2차 인증 완료 뒤 정상 세션 발급 |
| 민감 작업 재인증 | 현재 비밀번호와 새 TOTP 코드 입력 | 용도가 제한된 5분짜리 일회용 재인증 증명 |
| 복구코드 재발급 | 재인증 증명 제출 | 자격 버전·복구코드 교체, 이전 세션 폐기 후 새 정상 세션 발급 |
| 선택 MFA 해제 | 재인증 증명 제출 | 자격 비활성화, 기존 세션·도전·복구코드 폐기. 다음 비밀번호 로그인 필요 |

강제 적용 대상인 보호계정은 선택 해제를 할 수 없다. 일반 사용자의 등록 시작 후 확인을 취소하면 재로그인이 필요하다. 재로그인 시 계속 선택 등록할 수 있으며, 분실 복구 후의 필수 재등록 의무는 취소하거나 비밀번호 로그인을 반복해 없앨 수 없다.

TOTP는 6자리 ASCII 문자열이며 선행 0과 `000000`도 유효한 형식이다. 기본 간격은 30초, 허용 시간 차이는 앞뒤 한 구간이다. 이미 성공한 counter는 새 도전을 발급받아도 다시 사용할 수 없다. 직전에 사용한 코드는 다음 구간의 새 코드로 바뀐 뒤 입력한다. 서버·인증앱의 시각이 맞지 않으면 먼저 시간 동기화를 확인한다.

제한 도전은 5분 동안만 유효하며 등록·로그인·재인증 용도를 바꿔 사용할 수 없다. 검증 실패는 계정의 MFA 자격에 누적된다. 5회 실패하면 15분 동안 MFA 검증을 잠그며 새 비밀번호 로그인으로 실패 횟수를 초기화하지 않는다. 기존 비밀번호 잠금과 MFA 잠금은 별개다. IP 요청 제한도 MFA 경로에 적용된다.

BFF는 제한 도전과 재인증 증명을 HttpOnly 쿠키에 보관한다. 브라우저 JSON·URL·영구 저장소로 증명을 전달하지 않는다. 등록용 비밀과 복구코드는 사용자에게 전달하는 시점에만 표시하며 외부 QR 서비스로 보내지 않는다. 복구코드는 안전한 별도 보관 장소에 저장해야 한다.

## 분실 복구

복구코드를 사용할 수 있으면 비밀번호 로그인 후 코드 하나를 제출한다. 그 코드는 한 번만 사용할 수 있으며, 서버는 모든 이전 복구코드·세션·도전을 폐기하고 필수 재등록으로 전환한다. 새 인증앱 등록을 확인하기 전에는 정상 업무 토큰을 발급하지 않는다. 복구코드를 다시 사용하거나 이전 등록용 도전을 재사용하면 거부한다.

복구코드도 잃었다면 별도 복구 담당자가 처리한다. 담당자는 자신의 MFA가 등록되어 있어야 하고, 현재 비밀번호와 새 TOTP로 재인증해야 한다. `MFA_RECOVER` 권한과 해당 증명이 필요하며 대상이 보호계정이면 `AUTHRT_GRANT`와 `AUTHRT_ASSIGN`도 모두 필요하다. 비밀번호 초기화 권한만으로 MFA를 복구할 수 없고 자기 계정을 직접 관리자 복구할 수 없다. 대상의 비밀번호 잠금 해제·계정 재활성화는 각 작업의 기존 권한으로 별도 처리한다.

담당자는 기관이 정한 본인확인을 완료한 뒤 승인 참조를 제출한다. 참조는 영문자 또는 숫자로 시작하는 1~200자이며 영문자·숫자·점·밑줄·하이픈만 허용한다. 시스템은 형식을 검증하고 대상과 함께 성공 감사에 기록한다. **참조 문자열만으로 외부 본인확인이 완료되었다고 검증하지 않는다.** 신분 확인 자료·연락처·비밀값을 이 필드에 넣지 않는다.

`MFA_RECOVER`는 기본 그룹과 실계정에 자동 배정하지 않는다. 이 정책은 G+A 보유자를 신뢰하는 D02 A와 결합하며, 권한관리자를 견제하는 이중 승인 체계라고 해석하지 않는다. 실제 담당자·대체 담당자·승인 증빙 보관처·비상 접근 절차를 운영 적용 전에 정해야 한다. 별도 무제한 우회 계정은 제공하지 않는다.

복구 권한을 자기 부여하는 우회를 막기 위해 `MFA_RECOVER`의 추가·회수와 해당 그룹의 배정·회수·삭제에는 `AUTHRT_GRANT`와 `AUTHRT_ASSIGN`이 모두 필요하다. 개인·부서 일괄 배정, 가입 기본 그룹, 사용자 삭제도 동일하게 검사한다. 보호계정 분류는 기존 3개 권한을 유지하므로 `MFA_RECOVER`만 가진 계정을 새로 보호계정으로 분류하지는 않는다. 이 구분은 승인된 복구 경계의 집행이며, G+A 보유자 자체를 분리 승인하는 기능은 아니다.

## 저장·세션·감사

TOTP 비밀은 AES-256-GCM으로 암호화하며 계정·자격 버전·키 식별자에 결속한다. 도전과 복구코드 원문은 DB에 저장하지 않고 목적에 맞춘 SHA-256 digest만 저장한다. 복구코드는 계정과 자격 버전에도 결속한다. 사용자 행과 자격 행의 잠금으로 동시 코드 소모를 직렬화한다.

정상 JWT는 MFA 자격 버전과 실제 검증 시각을 담는다. 현재 DB의 필수 상태와 버전을 요청·refresh 시 확인하므로 보호권한 취득 후 이전 비밀번호 전용 세션이 상향 인증되지 않는다. Refresh는 원래 MFA 검증 시각을 보존한다. 비밀번호 변경·관리자 초기화는 제한 도전과 refresh를 폐기하고 활성 MFA 자체는 유지한다.

WebSocket은 HTTP 인증에서 검증한 MFA 증거를 STOMP 연결에 보존하며, 이후 송수신에서 현재 MFA 상태·권한 버전·비밀번호 변경 시각을 다시 확인한다. 핸드셰이크와 STOMP CONNECT 사이의 비밀번호 변경도 거부한다. 개인 알림은 `NOTI_READ`, 대시보드 통계는 `DASHBOARD_READ`가 필요하며 구독 ID와 실제 수신 목적지를 결속한다. 구독 취소 후의 지연 메시지나 현재 권한을 잃은 연결에는 데이터를 전달하지 않는다. 권한이 없는 활성 계정의 연결 자체는 가능하지만 보호된 구독은 허용하지 않는다. 세션 상태 변경은 다음 송수신 검사에서 연결을 종료하며 유휴 연결을 즉시 일괄 종료하는 별도 push 장치는 없다.

MFA 등록 완료·복구코드 재발급·해제·복구의 성공 감사는 업무 변경과 같은 트랜잭션으로 저장한다. 감사 저장이 실패하거나 후속 정상 토큰 생성이 실패하면 해당 업무 변경과 성공 감사가 함께 롤백된다. HTTP 시도와 종료 감사는 별도 단계이며 성공 기록은 클라이언트가 응답을 실제로 수신했다는 보장이 아니다. 코드·토큰·등록 비밀은 감사 내용에 기록하지 않는다.

만료되거나 소모된 도전은 검증에서 항상 거부한다. 현 구현은 자격 재등록·폐기·비밀번호 변경 때 도전을 삭제하며, 만료 시간만으로 주기 수거하지 않는다. 장기 보존량을 측정한 뒤 별도 수거 정책을 정할 후속 운영 항목이다. 이를 인증 유효기간 연장으로 해석하지 않는다.

## 키 회전·백업·운영 적용

1. DB·첨부·암호화 키를 함께 복구하는 [백업 절차](backup-and-restore-runbook.md)를 적용한다. MFA 키링도 해당 DB 백업과 결속해 보호한다.
2. 새 키를 추가하고 활성 키 식별자를 바꾸면 이후 등록·자격 버전 회전은 새 키로 암호화한다. 기존 행 전체를 자동 재암호화하지 않는다. 기존 envelope를 읽을 수 있도록 이전 키를 유지한다.
3. 이전 키 제거 전 실제 참조 현황과 백업 복구를 격리 환경에서 검증한다. 참조된 키를 먼저 삭제하면 해당 자격을 복호화할 수 없다. 키를 잃었을 때 평문을 추정하거나 비밀번호 전용으로 강등하지 않는다.
4. 운영 DB 적용은 승인 대상·백업·이전 버전 호환성·rollback/복구 방안을 먼저 확정한다. `V2_112__expand_local_totp_credentials.sql`은 신규 표준과 자격·도전·복구코드를 추가하는 후보이며 기존 `otp_secret` 평문 컬럼을 자동 정리하지 않는다. 기존 OTP 정책은 새 등록 흐름으로 이행한다.
5. 복구 담당자와 비상 절차를 준비하고 승인된 대상에서 등록·로그인·분실 복구·세션 폐기를 리허설한다. 기관의 등록 유예와 단계 적용 계획에 따라 보호계정 강제 적용을 켠다. 일괄 강제 전환은 이 개발 작업의 완료에 포함되지 않는다.

## 검증 근거의 범위

`TotpVerifierTest`·`MfaSecretCipherTest`·`MfaChallengePolicyTest`는 표준 벡터, 0으로 시작하는 코드, 변조·키 결속·회전, 도전 만료와 목적 제한을 다룬다. `MfaFlowIntegrationTest`는 실제 PostgreSQL에서 실패 횟수 커밋, 동시 OTP 소모, 복구·재등록, 보호권한 취득, 직접 HTTP 경로, 감사/토큰 발급 실패 롤백을 검사한다. `ProtectedAccountAdministrationIntegrationTest`는 관리자 초기화의 감사 실패 롤백을 포함한다. 파일의 존재가 실행 성공을 뜻하지 않으며 해당 커밋의 테스트 결과로 판정한다. 운영 인증앱·실제 배포·키 복구 리허설은 별도 증거가 필요하다.
