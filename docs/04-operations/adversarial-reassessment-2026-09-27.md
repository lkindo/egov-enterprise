# eGov Enterprise 평가의 적대적 재검토 — 2026-09-27

사용자가 제공한 Claude 평가를 `main 0ef8af32f`의 코드·설정과 대조한 **비규범 검토 문서**다. 실행 승인은 별개이며 이 문서가 기존 제품 결정이나 헌법을 대체하지 않는다. 후속 실행에는 [루프 프롬프트](../03-guides/evidence-first-improvement-loop-prompt.md)를 사용한다.

## 판단과 증거 범위

**“대략 70점 수준이며 운영·배포가 약하다”는 방향은 수용한다. 정확한 70점과 개선 후 75점이라는 예측은 수용하지 않는다.** 실제 보안·데이터 결함이 있는데 릴리스 발행의 점수 기여를 앞세운 우선순위도 바꿔야 한다. 현재 결과는 배포 승인이나 전체 제품의 안전성 인증이 아니다.

- 기준: 현재 HEAD와 원문 기준 SHA가 일치한다. 기존 `frontend/next-env.d.ts` 수정은 보존했다.
- 직접 확인: 코드·테스트 소스·CI 정의·관련 결정, GitHub 저장소 공개 여부·라이선스 인식·저장소 변수 이름/개수·릴리스 목록·Lighthouse 실행 로그.
- 수행하지 않음: 제품 빌드·런타임 공격 재현·전체 테스트·live DB 조회·운영 배포·원본 계정의 자격 폐기 여부 확인. 테스트 파일의 존재를 이번 실행 통과로 표현하지 않는다.
- 비밀 값이나 과거 사용자 행은 보고서에 복사하지 않는다. 과거 노출 자격의 현재 유효성은 미확인이다.
- 여러 검토자가 독립 범위를 조사했고 최종 통합자가 주요 반박과 보안·배포 경로를 현재 파일에서 다시 확인했다. 검토자 수는 재현성이나 통계적 신뢰도의 증명이 아니다.

## 채점 방법에 대한 반박

1. **산술은 맞지만 종합 방법은 불명확하다.** 분야 11개 평균은 68.636…, 도메인 33개 평균은 71.575…로 재계산된다. 두 집합은 인증·DB·테스트 등을 중복 평가하므로 다시 섞어 하나의 정밀 점수를 만들면 같은 위험을 중복 계산한다. 분야별 하위 축의 전체 가중치도 원문에 없다.
2. **동일 척도가 아닌 시계열 증감은 성과 수치가 아니다.** 엄격도를 바꿨다고 인정하면서 `+13`, `+16`을 개선량으로 제시하면 기준 변경과 구현 변경이 섞인다. 과거 SHA를 새 기준으로 다시 채점하기 전에는 개선 사례만 설명한다.
3. **미제공 기능과 결함을 구분한다.** SMS 어댑터·ISG 최종 사용자 화면·공개 약관·다중 인스턴스는 제품 범위와 기관 연동의 문제일 수 있다. 미구현 사실은 기록하되 제공하기로 하지 않은 기능을 일괄 개발하지 않는다.
4. **게이트와 검토 기록도 검증 범위를 가진다.** PIT 범위 밖이라고 단위·E2E 테스트까지 없는 것은 아니다. 반대로 green과 높은 커버리지가 권한 조합·데이터 수명·사용자 과업 완전성을 보장하지 않는다.
5. **릴리스 한 번에 CI/CD +12는 근거가 없다.** 배포 실패·롤백·업그레이드·자격 폐기·접근성 증거를 얻어야 관련 축이 오른다. 점수 상승을 작업 완료 조건으로 쓰지 않는다.

재평가의 6축은 기존 F(기능)·D(데이터)·S(보안)·T(테스트)·U(화면)·C(계약)를 유지하되, F의 분모는 승인된 제품 범위다. 5점은 중요한 사용자 경로나 불변식의 미완성, 7점은 핵심 구현과 일부 회귀 근거가 있으나 중요한 경계가 남음, 9점은 핵심 실패·권한·동시성·사용자 경로까지 실행 증거가 있는 상태로 본다. 이번에는 198개 축을 전수 실행하지 않았으므로 소수점 단위 새 점수를 만들지 않는다.

아래 구간은 통계적 신뢰구간이 아니라 **현재 증거로 방어 가능한 잠정 전문가 평가 범위**다. 33개 도메인의 약점 주장과 관련 강점을 표적 조사했지만 전체 기능·198개 축을 새로 실행한 점수는 아니다. 저장소 구현 품질은 대체로 70대, 외부 배포·기관 채택 준비도는 50대 후반~60대 초반으로 분리해서 보는 편이 타당하다. 공개 배포의 차단 사유는 평균점수로 상쇄하지 않는다.

## 주요 주장 판정과 수정된 권고

### A. 공개 배포·자격·라이선스

**수용:** GitHub API에서 public, license null, 저장소 변수 0개, 릴리스 v0.1.0 하나를 확인했다. 태그 이후 커밋 수는 1,020이다. 로컬의 문서 스킬 네 종류는 총 186개 추적 파일이며 모두 제3자 배포 제한 문구를 가진다. [재사용 생성기](../../scripts/generate-reusable-base-source.mjs)의 `trackedAndUntrackedFiles`/`copySourceTree`는 `.agent/skills`를 배제하지 않고 추적 안 된 비무시 파일도 복사한다.

**정정:** 루트 LICENSE 부재가 모든 상황의 사용을 일률적으로 불법으로 만드는 것은 아니다. 별도 권리 허락을 확인하지 않았고 GitHub 공개 저장소 열람·fork에는 플랫폼 약관상 권리가 있다. 다만 일반적인 기관 재배포 권리를 뒷받침할 공개 라이선스는 확인되지 않는다([GitHub 공식 설명](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/customizing-your-repository/licensing-a-repository)). 해당 스킬의 제한은 [Anthropic 배포 원본](https://github.com/anthropics/skills/blob/main/skills/docx/LICENSE.txt)에서도 확인된다. eGovFrame의 [Apache-2.0 채택](https://egovframe.go.kr/eng/sub.do?menuNo=10)이 저장소의 모든 자산에 같은 라이선스를 부여할 권한까지 주지는 않는다.

**권고:** 새 배포를 재개하기 전에 배포 대상 파일의 출처·권리를 정리하고 제한 스킬의 추적/산출물 제외안을 준비한다. 독점 자산을 남긴 채 LICENSE만 추가해서 해결됐다고 하지 않는다. 소스 아카이브도 clean SHA와 허용한 파일 모집단으로 만들어야 한다. 기존 계약 테스트를 확장해 금지 파일과 비무시 임시 파일이 산출물에 들어가는 변형을 잡는다.

과거 Supabase 자격·ARIA 키·DB 사용자 행의 존재/현재 유효성/폐기는 이번 감사에서 독립적으로 전부 확인하지 않았다. **원본 소유자가 노출한 자격을 채택 기관이 폐기할 수 없다는 책임 구분은 수용한다.** 비밀 값 대신 자산 종류·소유자·폐기 확인일·근거 위치만 남긴다. 유효한 자격이면 즉시 소유자가 회전/폐기해야 하며, 프로젝트 삭제·암호화 키 폐기는 데이터 복구·재암호화 영향이 있어 “작은 정리”로 묶지 않는다. Git 이력 삭제는 회전의 대체가 아니다.

### B. 릴리스와 운영 형상

[release.yml](../../.github/workflows/release.yml)은 backend `push:true` 뒤 frontend `push:true`를 실행한다. [프런트 Dockerfile](../../frontend/Dockerfile)은 두 API URL 인자가 비어 있으면 빌드를 거부한다. 현재 변수 부재는 확인됐지만, 전체 workflow를 실제 실행하지 않았으므로 반드시 backend push까지 성공한다고는 단정하지 않는다.

변수 검증을 verify 앞부분으로 옮기고 publish 없는 dry-run을 추가하는 제안은 수용한다. 그러나 **두 빌드 성공 뒤에도 두 번째 push는 실패할 수 있다.** 두 이미지를 불변 digest로 준비·검증한 뒤, 완전한 digest 쌍을 담은 릴리스 manifest를 최종 게시하고 배포가 그 manifest만 소비하게 하는 완료 경계가 필요하다. 정확한 구현은 현재 배포 소비자를 확인한 뒤 정한다. dry-run에서는 registry login/push, 태그 생성, Release 게시가 실제로 실행되지 않는지도 부정 검증한다.

운영 overlay smoke도 수용하되 ZAP을 prod 설정으로 바로 바꾸지 않는다. 현재 ZAP은 버리는 DB의 개발 시드 인증에 결속돼 있다. prod profile·edge·관리 포트·신뢰 proxy 검증을 격리된 형상에서 실행하고 기존 인증 스캔의 의미를 보존한다. [마이그레이션 릴리스 기록](migration-release-log.md)은 태그 발행이 아니라 **어느 환경에 실제 DB 변경이 배포됐는지** 기록한다. GitHub Release 생성만으로 행을 채우지 않는다. 신규 설치와 기존 v0.1.0 데이터의 업그레이드·복구 경로도 별개로 확인해야 한다.

### D. 도메인 데이터와 과업

- **쪽지:** [NoteService](../../business-app/src/main/java/nuri/business/service/note/NoteService.java)의 신규 수신자 존재·활성 확인과 미삭제 수신 행에 의존하는 파기를 함께 본다. 없는 ID·중복·비활성 수신자와 동시 상태 변경을 검증한다. 기존 고아 행을 추정 삭제하지 않는다.
- **부서 업무:** 서버가 담당자 ID를 그대로 저장하는 경로를 보완한다. UI 피커가 활성 사용자만 보여도 직접 API 요청을 막지는 못한다.
- **행사:** [EventInfoService](../../business-app/src/main/java/nuri/business/service/operation/EventInfoService.java)의 승인 여부/일자 요청 저장은 수용한다. 필드가 실제 승인 절차를 뜻하는지 확인하고, 서버 소유 필드라면 요청 바인딩을 차단한다. 별도 승인 workflow를 추측해서 만들지 않는다.
- **설문:** 일반 등록의 기간 UX와 선택형 응답 표시를 우선 수리한다. 현재 삭제는 답변 행 하나를 지우지만 “제출 전체 삭제”가 기존 명세라는 증거는 확인하지 못했다. 답변 삭제/제출 취소 중 사용자 계약을 먼저 정한다. 복제 기간 입력, 서버 기간 가드, 수정 API가 있으므로 기간 설정 화면과 마감 수단이 전혀 없다고 설명하지 않는다. 원문의 “공개”는 인터넷 익명이 아닌 인증 사용자 범위다. 제출 식별 단위가 필요한데 현재 모델로 표현할 수 없다면 스키마 결정 단계에서 멈춘다.
- **만족도:** [SatisfactionService](../../business-app/src/main/java/nuri/business/service/board/SatisfactionService.java)는 `frstRgtrId`를 감사 저장·중복 방지·소유 판정에 사용한다. 평가자가 저장되지 않는다는 진단은 틀렸다. 이름 표시 공백을 고치되 익명/실명 공개 정책은 별도로 확인한다.
- **결재:** [결재 설계 문서](../02-architecture/approval-workflow-ux.md)에 사용자 요청·규칙·검증 기록이 있다. DEC 번호 부재를 결정 부재로 해석하지 않는다. legacy endpoint의 소비자와 deprecation 전략을 확인하고 진행 문서 편집 가드를 제거하지 않는다.
- **트리·목록:** [명령센터](../../frontend/src/app/components/ui/global-command-center.tsx) 123과 [검색](../../frontend/src/app/search/SearchClient.tsx) 157은 2단계까지만 펼친다. 접근 가능한 트리를 임의 깊이로 순회하되 권한 없는 메뉴를 새로 가져오지 않는다. 메뉴 순환은 단건·일괄 변경의 최종 그래프와 동시 수정 의미를 함께 확인하고, 이미 훼손된 그래프의 읽기도 종료되게 한다. 일정/FAQ는 10건을 크게 늘리는 임시 처방 대신 페이지·더 보기·정렬과 빈/오류 상태를 선택한다. help의 Q&A도 같은 상한 소비를 표적 점검한다.
- **템플릿:** [커뮤니티 관리 화면](../../frontend/src/components/business/community/CommunityManageDialog.tsx) 101이 `templateAdminService.getTemplateList()`를 호출한다. “원장을 읽는 곳 없음”은 반박한다. 이것은 원장의 `tmpltPath`가 실제 화면 렌더링에 쓰인다는 증명은 아니다. DEC-OPS-105/106의 원장 ID와 레이아웃 ID 혼용 때문에 참조 강제를 보류한 맥락을 지키고, 점수를 올리려 FK나 렌더러를 임의로 추가하지 않는다.
- **파일·첨부:** [FileService](../../business-core/src/main/java/nuri/business/service/file/FileService.java) 48~52, 283~296에 요청당 20개·파일당 10MiB·요청당 50MiB 상한이 있다. 부족한 것은 사용자/기관의 누적 저장량 quota다. “DB 행이 없는 실물”, “업무 참조가 가리키는 마스터 부재”, “파일 DB 행은 있지만 업무에 미연결”은 서로 다르다. 기존 무결성 점검이 미연결 업로드의 자동 TTL 정리까지 해준다고 보지 않는다. 실제 누적을 읽기 집계하고 임시 보존기간·quota를 결정한 뒤 조치한다. 삭제 게시글 보존 정책과 혼합해 일괄 자동삭제하지 않는다.
- **알림:** 메모리 simple broker라 노드 간 즉시 push가 보장되지 않지만 [REST 보정](../../frontend/src/lib/hooks/use-notifications.ts)은 연결 중에도 가시 탭을 60초마다 정본과 맞춘다. 이미 저장된 알림의 push 미도달을 영구 DB 유실로 표현하지 않는다. 반대로 업무 커밋에서 비동기 listener가 알림 행을 만들기 전까지 영속 전달이 보장된 것도 아니다. 현재 한계·보정 지연을 문서화하고 날짜 표시만 공용 포맷으로 바꾼다. 공유 broker/outbox는 즉시 전달 SLA가 요구될 때 결정한다.
- **SMS·이관:** [운영 SMS sender](../../business-app/src/main/java/nuri/business/service/sms/UnavailableSmsSender.java)는 실패를 반환하며 UI도 미연동을 고지한다. 공급자별 연결 절차는 부족하지만 [공통 외부 연동 가이드](../02-architecture/domain-resilience.md)는 있다. [이관 실행기](../../migration-tool/src/main/java/nuri/migration/MigrationWorkflowRunner.java) 400~411은 UNVERIFIED COMMIT을 거부하고 EXPERIMENTAL도 adapter/source-freeze 확인을 요구한다. 이는 제공 범위의 한계와 안전통제 양쪽으로 평가해야 한다.
- **코드·투표:** [공통코드 서비스](../../business-core/src/main/java/nuri/business/service/code/CommonCodeService.java)는 이력을 남기고, [행정코드 서비스](../../business-core/src/main/java/nuri/business/service/code/AdministCodeService.java)는 쓰기 인가와 부모 존재/순환을 검사한다. 기관코드 수신 확인 후 원장을 자동 반영하지 않는 것은 DEC-OPS-069의 제한이다. [투표 서비스](../../business-app/src/main/java/nuri/business/service/survey/OnlinePollService.java)는 기간·항목 소속·중복·응답 보존을 검사한다. 반면 `SurveyManageClient`와 `OnlinePollAdminClient`는 같은 목록 API를 쓰면서 페이지 권한 축을 달리하므로, 주체별 페이지/API 허용표를 먼저 맞추고 화면 병합 여부는 별도 결정한다.

### E. 관측성·성능·DB·테스트

Lighthouse는 원격 로그로 `2026-08-23 0.75 → 08-30 0.56 → 09-06 0.46 → 09-13 0.53 → 09-20 0.47`을 확인했다([첫 실행](https://github.com/lkindo/egov-enterprise/actions/runs/32661128319), [마지막 실행](https://github.com/lkindo/egov-enterprise/actions/runs/35538241657)). 지속적인 낮은 성능은 수용하지만 매주 단조 하락한 것은 아니다. `warn` 자체는 의도된 관측 정책이며 오류가 아니다. 경고를 보고 누가 개선하는지가 빠진 문제다. AuthContext에서 generated operations/Zod로 연결되는 정적 import는 원인 **후보**다. 동일 환경 반복 측정과 실제 클라이언트 chunk·전송량·실행시간 분석 없이 이것만 원인으로 확정하거나 런타임 응답 검증을 제거하지 않는다.

로그인 실패를 접속으로 합산하는 쿼리, 매분 초기화되는 값의 “재기동 이후 누적” 라벨, SECURITY 탭의 시스템 로그 조회는 수리 가치가 있다. 반면 샘플 위젯은 샘플/미연동임을 표시하므로 허위 실측과 구분한다. OTLP의 localhost exporter 설정 가능성과 하루 1,440건의 **실제 운영 로그**는 다른 증거다. 실제 설정·로그를 확인한 뒤 미사용 exporter를 끄거나 실제 collector를 설정하고 경고를 숨기는 logger 하향으로 해결하지 않는다.

DB timeout은 저장소에 명시 설정이 없지만 DB role/database/session의 실제 값까지 0임을 뜻하지 않는다. live `SHOW`와 대표 쿼리·잠금 경합을 보고 온라인 요청과 migration/배치를 구분한다. [GlobalExceptionHandler](../../foundation/src/main/java/nuri/foundation/core/exception/GlobalExceptionHandler.java)는 이미 CHECK(23514)·NOT NULL(23502)을 400으로, UNIQUE/FK를 409로 매핑한다. 원문의 “값 오류가 409 중복”은 종류를 나눠야 한다. 나머지 입력 SQLState·잠금/timeout 변환은 점검 대상이다. 먼저 예외 의미·일시성·재시도 가능성을 정하고 timeout을 조정한다.

현재 versioned SQL은 112개, [ZDM 원장](../../config/governance/zdm-waivers.json)의 해시 고정 legacyDebt는 43개다. 차이 69개는 **해당 해시 집합 밖**이라는 뜻이지, 어떤 수정도 모든 CI를 반드시 통과한다거나 그 69개가 모두 live 적용됐다는 증거가 아니다. Flyway는 기존 DB에서 checksum을 대조하지만 매번 새 DB를 만들면 과거 파일 변조를 같은 방식으로 검출하지 못한다. 기존 게이트를 확장해 보호 기준 ref 대비 기존 versioned SQL 수정/삭제를 검사하고 repeatable migration·새 버전 추가와 구분한다. 별도 baseline을 마음대로 재생성해 변조를 승인하지 않는다.

[PIT 행렬](../../.github/workflows/ci.yml)은 실제로 IAM 인증 제공자·business-core RateLimitFilter·일부 인가/설문 경계를 포괄하지 않는다. 우선 보안 불변식의 작은 target부터 포함하고 잡 실행시간을 측정한다. 전 클래스를 한 번에 넣거나 통과율을 위해 exclusion을 늘리지 않는다. 페이지 title 역시 `<title>`의 실제 결과·redirect·동적 layout 상속을 보고 세야 하므로 “62개”는 고정 목표가 아니다. 제목·목적 식별 요구는 [W3C의 WCAG 2.4.2 설명](https://www.w3.org/WAI/WCAG22/Understanding/page-titled.html)을 따른다.

`decisions.md`는 378,462바이트로 크지만 “매일 10KB 증가”, 전체 지속 가능성 4/10은 이번에 시계열로 재확인하지 않았다. DEC 표 행 사이의 빈 줄은 현재 소스에서 9곳으로 세어져 원문의 6곳과 다르며, 최종 수정 때 실제 Markdown 렌더링도 확인해야 한다. 장기 결정의 안정 ID·기존 링크·필수 읽기 계약을 보존한 요약 인덱스/상세 기록 분리가 합리적이며 대량 이동은 별도 승인 경계를 따른다. 최신 상태·원시 실행 로그를 장기 메모리에 더 쌓는 방식은 피한다.

## 개선 배치와 완료 조건

`A`는 후속 실행 프롬프트를 사용자가 실제로 지시했을 때 진행할 수 있는 가역적 로컬 수정이다. `D`는 정책·권리·스키마·운영 결정 또는 별도 외부 작업 승인이 필요한 항목이다. 현재 감사 요청만으로 아래 구현을 시작하지 않는다. 우선순위는 공개 배포 차단(P1)과 사용자 영향/데이터 손상, 재현성, 수정 비용 순으로 정하며 점수 상승량은 사용하지 않는다.

| ID | 우선·순서 | 범위/권한 | 완료 조건 |
|---|---|---|---|
| R0 | 즉시 병행 | 원본 노출 자격 소유자 확인·권리 inventory·산출물 경계(A 조사/가드, D 폐기·대량 제거·라이선스) | 원본/채택기관 책임 분리, 금지 자산의 산출물 유입 red, 소유자 확인이 필요한 행은 blocked로 남김. 미확인 자격을 폐기 완료라고 하지 않음 |
| R1 | 첫 수정 배치 | 메일 검색 경계·refresh 절대 만료·인증 장애 분류(A) | 본문을 바꿔도 타인 검색 결과/건수 동일, 짧은 수명 설정이 최초·회전 JWT/DB/쿠키에서 유지, 인프라 오류와 비밀번호 오류가 안전하게 구분됨 |
| R2 | 다음 | 쪽지 수신자·담당자 검증(A, 기존 DML은 D) | 직접 API의 없는/비활성 ID 새 배정 거부, 정상 저장·원자성 유지. 기존 담당자를 유지한 본문 수정과 새 배정은 구분. 기존 데이터 보정은 별도 제안 |
| R3 | R0와 병행 준비, 발행은 나중 | 릴리스 preflight·publish 없는 dry-run·digest 쌍·운영 형상 smoke(A), 변수·태그·게시·배포(D) | frontend 실패/두 번째 push 실패/manifest 부재에 불완전 릴리스를 소비하지 않음. 신규 설치 및 기존 데이터 업그레이드/복구 범위 명시 |
| R4 | 정책 결정 후 | 주소록 최소 정보·고권한 계정 reset·BFF 경계·공지/투표 권한·행사 승인 의미·평가자 공개 방식(D 결정, 그 후 A) | 주체×대상×동작 권한표와 양/음성 사례. 행사 필드가 수기 관리값인지 승인 결과인지 판정 후 저장 제한. 기존 정상 사용자·비브라우저 소비자가 깨지지 않음 |

| R9 | 관련 수정과 묶음 | PIT 핵심 target·이미지 scan/SBOM·runtime 의존성 최소화·기존 문서 정리(A, 권리/대량 이동은 D) | 새 게이트 중복 없음, 의도 위반 red, 기존 실행 경로에 결속, 동일 SHA/digest 증거, 무거운 검증 시간 기록 |

R0의 권리·자격 책임과 R1/R2의 직접 결함을 덮어둔 채 v0.2.0부터 게시하지 않는다. 버전명 자체는 고정 요구가 아니다. 각 배치는 한 불변식/사용자 과업을 다룰 만큼만 잘라 진행한다. 독립된 조사와 파일 경계가 명확한 구현은 병렬 위임할 수 있지만, 같은 기계의 무거운 검증은 직렬 실행한다. 환경·제품 결정이 막힌 항목은 다음 행동과 결정권자를 남긴 뒤 다른 실행 가능한 항목을 계속한다.

기관별 누적 파일 quota/임시 업로드 수명, 알림 즉시 전달 SLA와 공유 broker, 공급자별 SMS 실발송, ISG 공개 화면, 템플릿 값 도메인, 행정/기관코드 이력은 요구·권리·운영 조건을 받은 뒤 별도 D 항목으로 설계한다. 현재 기능의 문구·기존 제약·제공 한계 문서화는 R5/R9에 포함할 수 있지만, 이 목록이 신규 기능의 자동 구현 승인은 아니다.

## 완료 판정

1. 해당 항목의 실패 재현과 최소 수정, 범위별 필수 검증, 직접 diff 감사가 모두 있어야 완료다.
2. 외부 승인·소유자 폐기·실사용자 접근성 검토는 로컬 테스트로 대체하지 않는다.
3. 점수가 올랐거나 원장의 행을 지웠다는 사실은 완료 증거가 아니다.
4. 원문에서 반박한 항목을 해결 과제로 다시 넣지 않는다. 이미 있는 기능이나 테스트를 새로 만드는 중복도 피한다.
5. 최종 보고는 `완료 / 승인 대기 / 외부 증거 대기 / 반박·범위 밖`으로 나누고 실행 명령·결과·SHA·남은 영향을 남긴다.
