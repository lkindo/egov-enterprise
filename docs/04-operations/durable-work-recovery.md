# 후속 작업 재처리

[ADR-0025](../02-architecture/decisions/ADR-0025-enterprise-completeness-and-durable-operations.md)의 D12·D14는 업무 변경과 후속 처리 의도를 같은 트랜잭션에 저장한다. 의도 저장 실패는 업무 실패이며, 커밋 이후 전달 실패는 남아 있는 의도로 재시도한다. 이 문서는 운영 DB 적용이나 실계정 권한 배정의 승인이 아니다.

## 상태와 재개

`tb_sys_job`의 `PENDING`·`RETRY` 작업은 예정 시각 뒤에 실행한다. 작업자는 `RUNNING` 상태와 120초 임대를 먼저 커밋하고, 실행 중에는 30초마다 같은 시도 식별자를 가진 `RUNNING` 작업의 임대를 갱신한다. 갱신은 시도 횟수를 늘리지 않는다. 프로세스가 중단되어 갱신이 끊기면 마지막 임대 만료 뒤 다른 작업자가 인수하며, 이전 작업자의 갱신·완료 통지는 시도 식별자가 달라 거부된다. 전달 중 프로세스가 종료되면 외부 효과가 반복될 수 있으므로 소비자는 의도의 고정 식별자와 도메인별 선점 상태로 중복 효과를 막아야 한다. 이 구조는 외부 전달의 exactly-once 보장이 아니다.

[전용 스케줄러와 실행기](../../business-core/src/main/java/nuri/business/service/system/job/DurableWorkSchedulingConfig.java)는 공용 fixed-delay 작업에서 영속 처리를 분리한다. 스케줄러는 poll·임대 갱신을 처리하고, 대기열 없는 4개 작업 스레드가 실제 작업을 수행한다. DB 선점은 작업 스레드 진입 후에만 하며 실행기 포화는 다음 poll로 미룬다. 각 작업 스레드는 한 번에 최대 20개 작업을 순서대로 처리한다. 외부 I/O를 기다리는 작업도 임대를 갱신하며, 작업 종료 시 갱신을 취소한다.

[실행기별 동시성 상한](../../foundation/src/main/java/nuri/foundation/core/job/DurableWorkHandler.java)은 같은 dispatcher 안에서 SMS 1개, 메일 2개다. 두 유형의 긴 발송이 겹쳐도 공통 4개 스레드 중 최소 1개는 파일 삭제·알림 등 다른 유형이 사용할 수 있다. 상한에 도달한 유형은 다음 DB 선점의 후보에서 제외하며, 후보 계산·선점 커밋·실행 수 증가를 함께 직렬화한다. 실행·완료 기록은 이 잠금 밖에서 수행하고 예외가 나도 실행 수를 반환한다. 이는 현재 코드의 로컬 실행 상한이며 외부 채널의 지연 시간이나 다른 유형의 최대 대기 시간을 실측한 결과는 아니다. 운영의 단일 dispatcher 빈을 전제로 하며, 다른 애플리케이션 인스턴스나 테스트용으로 직접 생성한 dispatcher끼리는 실행 수를 공유하지 않는다.

최대 8회 시도 후 `FAILED`가 된다. 재시도 간격은 실패 횟수에 따라 증가하며 상한은 300초다. 상태 조회의 `availableAt`·`completedAt`은 UTC 기준이다. 실행기가 없는 유형의 작업은 소비하지 않는다. 제품 구성 변경 시 제외된 기능의 미처리 작업이 없는지도 확인해야 한다.

`nuri.durable-work.enabled` 기본값은 `true`이며, `poll-ms` 기본값은 5000, `initial-delay-ms` 기본값은 10000이다. 실행 비활성화는 의도 저장을 끄지 않는다. 장애 조사에서 일시 정지한 실행기는 원인 수정 후 다시 활성화한다.

## 운영자 재처리

1. `DWORK_READ` 권한으로 `GET /api/v1/admin/system/durable-jobs?page=0&size=20`을 조회한다. 페이지 크기 상한은 100이다. 응답은 작업 ID·유형·상태·횟수·시각과 서버가 판정한 재처리 가능 여부(`retryable`)만 제공하며, 파일 경로나 알림 본문을 노출하지 않는다. 화면은 이 판정으로만 재처리 단추를 보인다.
2. 저장소·전달 채널 장애의 원인을 확인한다. 파일 식별자 불일치와 현재 첨부 참조가 있는 경우에는 재시도를 반복해도 원인이 해소되지 않는다.
3. `DWORK_RETRY` 권한으로 `POST /api/v1/admin/system/durable-jobs/{jobSn}/retry`를 호출한다. payload가 남아 있는 `FAILED` 작업만 가능하며 다른 상태나 payload가 삭제된 작업은 거절한다. 업무 재처리 상태 변경과 `DURABLE_WORK_RETRY` 감사 기록이 함께 커밋된다. 감사 저장 실패 시 상태도 바뀌지 않는다. 종료 시 암호화된 수신 주소를 삭제한 메일 작업은 이 API로 되살릴 수 없으며, 발신자가 주소와 결과를 확인한 뒤 새로 접수해야 한다.
4. 새로운 시도의 결과를 다시 조회한다. 권한은 카탈로그에만 등록하며 기본 그룹이나 실계정에 자동 배정하지 않는다.

`EgovDurableWorkFailed`는 committed DB 상태의 `nuri_durable_work_jobs{status="FAILED"}`를 보므로 재기동 전 적체도 탐지한다([관측성 기본값](observability-baseline.md)). 30초 주기의 읽기 집계를 캐시하고 scrape는 DB를 조회하지 않는다. 기존 `nuri_durable_work_failed_total{type=...}` 전이 카운터는 발생 추이의 보조 신호다.

`EgovDurableWorkDueBacklog`는 PENDING·RETRY의 예정 시각과 RUNNING의 만료된 임대를 기준으로 오래된 대기를 본다. 미래 예약·정상 임대는 제외한다. 실행기가 비활성화돼도 상태 조회는 유지되며, DB 조회 실패는 마지막 정상 집계를 보존하고 별도 관측 실패 경보로 알린다.

## 앱 알림의 보장과 한계

결재의 순서 도래·회수·결과, 쪽지 도착, 메모보고·지시, 부서업무 배정, 커뮤니티 가입 신청·결정, 게시글의 새 댓글과 직접 생성·관리자 발송 알림을 대상으로 한다. 현재 발행 경로는 업무 트랜잭션 안에서 알림 행과 `NOTIFICATION_DELIVERY` 작업을 함께 저장한다. 어느 저장이든 실패하면 같은 업무 변경도 롤백한다. 커밋 후 worker는 저장된 알림을 개인 WebSocket 큐에 전달하며, 전송 실패는 이미 성공한 업무를 되돌리지 않는다. 알림은 worker 전송 전에도 본인의 REST 알림함에서 조회할 수 있다.

작업에는 알림 ID·수신자 식별자·요청 지문만 저장한다. 제목·본문·링크를 작업 원장에 복제하지 않는다. 같은 `eventId`와 수신자는 같은 의도 키를 사용하며 PostgreSQL 트랜잭션 잠금으로 동시에 재발행되어도 알림과 작업을 한 건만 만든다. 같은 키의 제목·본문·링크가 달라지면 기존 요청을 덮어쓰지 않고 거절한다. 이는 같은 사건의 재발행에 대한 보장이며, 별도 업무 요청에 새 사건 ID를 발급한 경우까지 같은 요청으로 추정해 합치지 않는다.

worker 재시도는 기존 알림 ID를 그대로 사용하므로 알림함에 새 행을 추가하지 않는다. 전송 직후 완료 기록 전에 중단되면 같은 WebSocket 메시지가 다시 전달될 수 있다. 클라이언트는 알림 ID로 중복을 제거하고 REST 목록·미읽음 수로 보정한다. WebSocket 처리 성공은 사용자의 실제 수신·열람 확인이 아니다. 사용자가 삭제했거나 계정 삭제·승인된 보존 정책으로 정리한 알림은 재시도로 되살리지 않고 해당 작업을 종료한다.

완료 작업은 사건 재발행의 중복 방지 근거다. 성공 작업을 별도 보존·멱등 기간 정책 없이 삭제하면 오래된 사건의 재발행이 새 알림을 만들 수 있다. 기본 구현은 작업 원장을 자동 파기하지 않는다. 단순 화면 갱신·접속 신호는 이 원장의 대상이 아니다.

## 메일·SMS 접수 이후의 복구 경계

[메일 접수](../../business-app/src/main/java/nuri/business/service/mail/MailService.java)는 발송 이력과 `MAIL_DELIVERY` 의도를, [SMS 접수](../../business-app/src/main/java/nuri/business/service/sms/SmsService.java)는 헤더·수신자와 `SMS_DELIVERY` 의도를 각각 같은 트랜잭션에 저장한다. 의도 저장이 실패하면 접수도 롤백한다. 커밋 후 실행기 제출 전에 프로세스가 종료되어도 저장된 의도를 다시 읽을 수 있다. 작업자는 외부 발송 실행기의 Future가 끝난 뒤 작업 완료를 기록한다. 원장의 `SUCCEEDED`가 수신자의 실제 배달·열람까지 뜻하지는 않는다.

이 보장은 **발송 서비스의 접수 트랜잭션부터** 시작한다. 결재 업무 커밋 후 이벤트 listener가 `MailService` 또는 `SmsService`를 호출하기 전에 종료되는 공백까지 업무 트랜잭션과 묶은 것은 아니다. 그 단계는 별도의 최선형 이벤트 전달 경계로 남는다.

| 유형 | 자동 복구가 발송을 시작할 수 있는 상태 | 복구 시 제외하는 상태 |
|---|---|---|
| 메일 | 접수 시각까지 일치하는 `Q`를 별도 트랜잭션으로 `P`로 선점한 경우 | 이미 선점된 `P`, 완료·실패 행, 삭제된 행, 더 새로운 접수 시각의 행 |
| SMS | 수신자 결과가 `P`이고 내부 receipt가 `NULL`인 미선점 행 | claim·접수·결과 불명 receipt가 있거나 종료·삭제된 수신자 |

메일은 접수 당시 수신 주소를 작업 payload에 암호화하여 보관하고 자동 복구에 사용한다. 이력의 표시명이나 잘린 주소를 발송 주소로 추정하지 않는다. 성공 또는 재시도 예산 소진으로 작업이 종료되면 암호화 주소를 포함한 payload를 비운다. 예산 소진 시 같은 접수의 미선점 `Q`만 `F`로 바꾸며, 선점된 `P`는 결과 불명으로 보존한다. 키 손실·복호화 실패는 수신 주소를 추정하여 우회하지 않는다.

메일의 durable 재실행은 `P`를 다시 SMTP로 보내지 않는다. 다만 기존 `MailAsyncProcessor.deliverMail`의 SMTP 호출 재시도 최대 3회는 유지되므로 외부 발송 exactly-once 보장은 없다. 발신자 본인의 수동 재발송은 `F` 또는 10분 이상 지난 `P`를 새로 접수하는 기존 경로다. 결과 불명 건은 외부 채널 결과를 확인한 뒤 판단해야 한다. 사용자 수신자는 현재 등록 주소를 다시 해석하지만, `rcvrId` 없는 과거 이력에는 100자 미만의 주소 형태 표시값을 직접 주소로 해석하는 분기가 남아 있다. 이는 자동 복구 주소의 정본으로 사용하지 않으며 수동 재발송의 이력 해석 한계다.

SMS 작업에는 전송 ID와 발신자 식별자만 저장하고 전화번호·본문을 복제하지 않는다. 결과 불명 수신자에 대한 자동 POST 재시도는 금지하며, 저장된 접수 receipt의 조회와 상태 기록만 수행한다. 상세 절차는 [SMS 공급자 운영 문서](sms-provider-operations.md)를 따른다.

메일의 확정 실패 `F`와 발신자 알림은 같은 결과 기록 트랜잭션에서 저장하며, 기록 재시도는 SMTP를 다시 호출하지 않는다. 알림 사건 ID는 발송 ID와 의도에서 전달받은 접수 시각으로 고정한다. 발신자 삭제 등으로 알림 저장이 끝내 실패하면 별도 트랜잭션에서 현재 시도의 `P→F` 결과만 한 번 더 저장한다. 이 CAS가 성공했고 발신자 식별자가 있을 때만 알림 미기록을 로그와 `mail.dispatch.failure.notices.lost` 카운터에 남기며, 오래된 시도이거나 이미 커밋된 결과여서 CAS가 0이면 알림 유실로 단정하지 않는다. 기록 재시도 소진은 기존 `mail.dispatch.recording.failures`로도 관측한다. 결과 전용 저장도 실패하거나 결과 기록 전 프로세스가 종료되면 기존 `P`의 불확실성은 남는다. 성공 결과 기록과 암호화 payload의 종료 시 정리 정책은 그대로다.

SMS 실패 알림은 저장된 초기 POST 거절(`F`, 유효한 내부 `REJECTED` receipt, 요청 ID 없음)만 다시 집계한다. 전송 ID로 고정한 사건 ID를 사용하므로 알림 저장 실패나 완료 기록 전 재실행에서도 알림을 중복 생성하지 않는다. 미선점 `P/NULL`, `CLAIMED` 또는 이번 실행의 DB 오류가 남으면 실패 수가 0이어도 완료와 요약을 유보한다. 늦은 영수증 조회의 거절은 초기 실패 수에 더하지 않고, 옛 문자열 결과도 초기 거절로 추측하지 않는다. 재시도 한도를 넘으면 작업은 `FAILED`가 된다. 기존 receipt 조정으로 상태가 확정된 후 `DWORK_RETRY`로 재개할 수 있으며, `provider=none`에서는 조정 스케줄러가 없어 수동 재시도만으로 버려진 `CLAIMED`가 해소되지는 않는다.

발신자 계정이 하드 삭제되어 SMS 실패 알림의 수신자 FK가 더는 유효하지 않으면 알림 저장 재시도도 계속 실패한다. 수신자별 확정 결과는 보존되고 POST를 다시 보내지 않지만, 작업은 재시도 한도 뒤 `FAILED`로 남을 수 있다. 이 경우 `DWORK_RETRY`만 반복해도 해결되지 않으므로 발송 결과와 알림 실패를 구분해 운영 점검한다.

## 파일 삭제의 복구 경계

파일 메타데이터 삭제 전에 별도의 하드링크 `.deletions/{preparation UUID}.anchor`와 내용·속성 지문으로 저장 객체의 식별 정보를 확보한다. Windows처럼 Java의 `fileKey`가 없는 환경에서도 `Files.isSameFile`로 실제 객체를 비교한다. 객체가 원래 없었다면 나중에 같은 경로에 생긴 파일을 지우지 않는다. 저장 이름은 새 UUID로 생성하며 기존 파일을 덮어쓰지 않는다.

삭제 작업은 현재 첨부 참조를 다시 확인하고, 원래 객체만 저장소 내부 `.deletions/{intent UUID}.object`로 원자 이동한 뒤 식별 정보를 재확인한다. 이동 뒤 프로세스가 중단되면 같은 의도로 재개한다. 원래 위치에 생긴 새 객체는 지우지 않는다. 식별 정보가 달라졌다면 삭제하지 않고 복원 가능한 원래 위치로 되돌리며, 그 위치도 점유되어 있으면 격리 객체를 보존한다.

`.deletions`는 자동 TTL·고아 파일 일괄 정리 대상이 아니다. 작업별 `.lock` 파일은 다중 프로세스의 동일 삭제 작업을 조정하므로 실행 중 임의로 지우지 않는다. `.done` 영수증은 삭제 직후 프로세스 종료로 DB 완료 기록이 남지 않았을 때 재시도를 안전하게 끝낸다. 의도 저장 전 준비물은 정상 롤백 시 보상 제거하며, 준비 중 프로세스가 종료되어 의도 없이 남은 anchor는 운영 점검 대상으로 보존한다. 하드링크나 원자 이동을 지원하지 않는 저장소는 자동으로 안전하지 않은 삭제 방식으로 전환하지 않는다. 다른 저장소 어댑터도 `captureDeletionIdentity`·`deleteCaptured`·`releaseDeletionIdentity`의 계약을 구현해야 한다.

완료된 의도는 이벤트 재발행의 중복 방지 근거이기도 하다. 성공 작업과 삭제 영수증을 별도 정책 없이 일괄 삭제하지 않는다.

## 검증의 범위

`DurableWorkIntegrationTest`의 검사 범위는 격리 PostgreSQL의 업무 롤백·중복 의도·임대 만료·복수 작업자·시도 한도·재처리 감사와 현재 시도만 가능한 임대 갱신, 종료 시 payload 정리다. `DurableWorkSchedulingConfigTest`와 `DurableWorkDispatcherTest`는 실행기 포화·선점 시점·스케줄러 진행·heartbeat 취소, 유형별 선점·슬롯 확보의 원자성, 긴 작업 중 다른 유형의 진행과 예외 후 슬롯 반환을 다룬다. `LocalFileStorageServiceTest`와 `FileDeletionTransactionTest`는 실제 임시 파일의 교체·중단·롤백 경계를 확인한다. 테스트 파일의 존재는 통과 증거가 아니며 실행 결과는 해당 변경의 검증 기록에서 확인한다. 운영 저장소에서의 중단·복구 리허설과 배포는 별도 승인 범위다.

`SmsDeliveryStateIntegrationTest`는 접수·의도의 원자 롤백, 저장된 의도를 읽는 새 handler, 재실행 시 중복 POST 방지, 실제 수신자 잠금과 receipt 상태 전이를 다룬다. 메일의 서비스·processor·handler 단위시험은 접수 의도, 선점 상태, 암호화 주소 복구와 종료 처리를 검사한다. 이 범위만으로 실제 SMTP/SENS 계정의 배달이나 발송 중 JVM 종료를 검증했다고 해석하지 않는다.

`MailFailureNotificationIntegrationTest`와 `SmsFailureNoticeIntegrationTest`는 실제 PostgreSQL 알림 저장 오류·재시도·중복 의도와 외부 발송 횟수를 확인한다. 메일은 삭제된 발신자, 비DB 예외, 실제 커밋 후 응답 예외와 새 수동 접수의 보호를, SMS는 부분 요약 유보, 조회 후 거절, 재시도 소진과 기존 조정·감사된 재처리를 포함한다. 두 시험은 각각 mail+notification, sms+notification 구성에서 유지하며 기존 발송 상태 시험의 기능 범위를 좁히지 않는다.

`NotificationDurabilityIntegrationTest`는 격리 PostgreSQL에서 알림·의도의 원자 롤백, 실제 advisory 잠금 대기를 동반한 동시 재발행, 요청 지문 불일치, 삭제 후 재발행, 전송 실패 재시도와 새 dispatcher의 만료 임대 회수를 검증한다. `AssignmentRecipientIntegrityIntegrationTest`는 실제 쪽지·부서업무 경로의 수신자 정합과 원자 저장을 다루며, `MemoReportRecipientIntegrityIntegrationTest`는 메모 수신자의 활성 상태·고정과 최초 열람의 동시성을 검증한다.

2026-09-28에는 격리 PostgreSQL 17과 임시 저장소에서 실제 JVM 강제 종료·재시작도 검증했다. 실행기를 끈 상태에서 정상 쪽지 전송·파일 업로드/삭제 API로 두 `PENDING` 의도를 커밋하고 해당 JVM만 강제 종료했다. 같은 JAR·DB·저장소·키로 실행기를 켜 재시작한 뒤 두 작업은 한 번의 시도로 완료됐다. 쪽지 내용과 기존 알림 한 건이 유지됐고 파일 실물·anchor는 제거되며 삭제 영수증이 남았다. 추가 polling에도 상태가 변하지 않았다. 이는 **커밋된 대기 작업 이후의 종료**에 대한 증거다. 전달 중이나 파일 격리 이동·삭제·영수증 기록 사이의 실제 프로세스 종료, 운영 저장소의 복구, WebSocket 클라이언트 수신 확인까지 증명하지 않는다.
