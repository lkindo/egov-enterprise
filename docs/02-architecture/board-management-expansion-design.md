# 게시판 운영 관리 확장 설계

> 상태: **설계 확정 · 구현 완료(A0~B3 병합, 공유 OCI V2_142 적용)** · 결정: [ADR-0040](decisions/ADR-0040-board-operations-management.md) · 작성일: 2026-10-22 · 기준 소스: `82e5e25a7`
>
> 같은 날 작성된 Codex 초안을 적대적 검토(기존 지적 13건을 3관점으로, 신규 지적 46건을 2관점으로 반박 검증, 확정 27항목)와 6개 주제의 코드·원장·live 메타 조사로 다시 썼다. 확정본은 다시 5관점으로 검토해 지적 50건 가운데 반박되지 않은 것을 반영했다. 결정은 사용자가 2026-10-22 권고안으로 설계를 완성하도록 위임한 데 따른 권고안이다(사용자 발화 원문은 ADR-0040 승인 줄에 있다).
>
> 이 문서는 구현 범위·계약·검증 기준을 정한다. 2026-10-23 사용자는 A0~B3를 이어서 구현하도록 하고 다음을 함께 정했다(§7). ADR-0040의 스키마 변경은 저장소 Flyway로 일괄 승인한다. 공유 OCI 적용은 PR이 병합될 때마다 하고 [적용 로그](../04-operations/shared-oci-migration-apply-log.md)에 남긴다. 예약 집행 전 진단에서 미래 시작일 글이나 형식이 깨진 날짜가 나와도 데이터를 보정하지 않고 집행한다. 그 밖의 코어 데이터 변경은 따로 승인받는다.

## 1. 결론

1. **마스터 목록을 입구로 두고, 고른 게시판의 운영 화면에서 일을 끝낸다.** 운영 화면은 `/admin/community/boards/master/[id]`에 두고 `?tab=posts|settings|access` 세 탭으로 나눈다. 새 최상위 메뉴는 만들지 않는다.
2. **"사용 안 함" 게시판은 이용자에게 읽기·쓰기 모두 닫힌다.** 지금은 조회만 닫히고 등록·수정·삭제·해결 표시는 열려 있다. 운영자(게시글 조회 대행 권한)는 사용 안 함 게시판의 글을 읽고 정리할 수 있다. 새 게시판은 사용 안 함으로 만들어 공개 준비를 마친 뒤 연다.
3. **예약 게시는 날짜 기준으로 모든 경로에서 서버가 집행한다.** 게시 상태(예약·게시 중·게시 종료)는 서버가 한 번 계산해 응답에 싣는다. 목록은 작성자가 바꿀 수 없는 게시 기준일로 정렬한다.
4. **상단 고정은 표준 용어 컬럼과 새 기능 권한(`BOARD_PIN`)으로 둔다.** 기존 `ntc_yn`(공지 여부)은 재사용하지 않는다.
5. **설정은 게시판 마스터 한 곳에 두고 버전으로 동시 수정을 막는다.** 운영 처리는 게시판이 소유하는 변경 이력에 남긴다.
6. **구현은 A0(결함 수정) → A1 → A2 → B1 → B2 → B3 순서다.** C·D 배치(안내문·양식·분류, 초안·이력, 이동·복사, 답글·신고·개인정보 점검, 검토·필독)는 선행 설계가 필요한 후속 대상으로 남긴다.

## 3. 확인한 현행 동작

검토와 조사로 확정한 사실이다. 설계 판단은 모두 이 사실에 기댄다.

### 3.1 권한과 접근

- 게시글 권한은 게시판마다 나뉘지 않는다. `BOARD_READ`·`BOARD_CREATE`·`BOARD_UPDATE`·`BOARD_DELETE`·`BOARD_LIKE`는 `ROLE_USER` 기본 배정이고, `*_ALL`(대행)은 `ROLE_ADMIN`·`ROLE_SYSTEM`에만 있다([권한 원장](../../config/governance/permission-catalog.json)).
- 게시판별 제한 수단은 커뮤니티 귀속 하나다. 귀속 게시판은 승인 회원과 `BOARD_READ_ALL` 보유자만 지난다([BoardService.java:258-273](../../business-app/src/main/java/nuri/business/service/board/BoardService.java#L258-L273)).
- 공지 게시판 ID와 FAQ 게시판 ID의 기본값이 같다(`BBSMSTR_AAAAAAAAAAAA`). 그래서 이 게시판의 등록·답글(서비스 메서드만 있고 API는 없다)·해결 표시·수정·삭제에는 `NOTICE_EDIT`와 `FAQ_EDIT`가 모두 필요하다. 두 권한은 기본 배정 그룹이 없고 [게시판·커뮤니티 운영 묶음](../../config/governance/permission-bundles.json)에 들어 있다([BoardIdProperties.java:29-35](../../business-core/src/main/java/nuri/business/core/config/BoardIdProperties.java#L29-L35)).
- 메뉴는 길 안내일 뿐 접근을 막지 않는다. 게시판 이용 화면(`select-board-list`)은 인증만 요구한다. 현재 마법사 3단계의 "이 게시판의 접근 권한은 메뉴 권한을 따릅니다"는 사실과 다르다([BoardMakerWizard.tsx:635](../../frontend/src/app/admin/community/boards/maker/components/BoardMakerWizard.tsx#L635)).

### 3.2 게시판 사용(use_yn)의 현재 의미

| 경로 | 사용 안 함 게시판에서 |
|---|---|
| 목록·통계·통합 검색 | 닫힘(`assertActiveBoardMaster`, 마스터 조인) |
| 상세·댓글 조회·등록·추천·만족도 등록 | 닫힘(상세 질의가 마스터 `use_yn='Y'`를 건다). 운영자도 404 |
| 게시글 등록·수정·삭제·해결 표시 | **열림**. 사용 여부를 보지 않는다(등록 [BoardService.java:305-386](../../business-app/src/main/java/nuri/business/service/board/BoardService.java#L305-L386), 해결 표시 [:534-545](../../business-app/src/main/java/nuri/business/service/board/BoardService.java#L534-L545), 수정·삭제 [:643-753](../../business-app/src/main/java/nuri/business/service/board/BoardService.java#L643-L753)) |
| 만족도 수정·삭제 | 게시판·게시글 가드 자체가 없다. 경로의 게시판·글이 평가의 실제 소속과 같은지도 보지 않는다([SatisfactionApiController.java:105-133](../../api-server/src/main/java/nuri/api/controller/business/board/SatisfactionApiController.java#L105-L133)) |
| 게시판 메타 | 열림(존재만 확인) |

- 현재 마법사는 게시판을 `use_yn='Y'`로 만들고 메뉴만 비활성으로 등록한다([BoardMakerWizard.tsx:281](../../frontend/src/app/admin/community/boards/maker/components/BoardMakerWizard.tsx#L281)). 만든 직후부터 주소를 아는 사용자는 읽고 쓴다.
- 글 삭제는 논리 삭제뿐이라, 글 행이 한 번이라도 생긴 게시판은 영구 삭제할 수 없다(FK). 단건 판정(`countAllByBbsId`, JPQL)은 서비스 안에서 soft-delete 필터가 늘 켜져 있어 논리 삭제 글을 빼고 센다. 그래서 논리 삭제 글만 남은 게시판은 단건 판정을 통과한 뒤 물리 삭제 단계에서 FK로 실패한다. 일괄 판정(네이티브 질의)은 논리 삭제 글도 센다. 마스터 목록의 "관련 게시글을 먼저 모두 삭제해주십시오" 안내는 글을 지워도 행이 남으므로 따를 수 없다([BoardMasterService.java:190-250](../../business-app/src/main/java/nuri/business/service/board/BoardMasterService.java#L190-L250)).

### 3.3 메뉴 연결

- 메뉴 원장에 게시판 주소(`select-board-list?bbsId=`)를 가리키는 메뉴는 없다. 시드 게시판은 지식 허브의 `?tab=` 메뉴로 열린다. 위키·FAQ·질의응답 메뉴는 `/admin/help/faq?tab=WIKI|FAQ|QNA`이고, 커뮤니티 메뉴는 `/admin/help?tab=COMMUNITY`다. `/admin/help`·`/admin/help/faq`·`/admin/help/qna`는 같은 허브다(`knowledge-tabs.ts`의 `TAB_HUB.routes`). FAQ 탭은 공지사항(AAAA), 위키 탭은 일정 게시판(EEEE), 질의응답 탭은 Q&A 게시판(DDDD)을 연다. 이 셋은 셸 탭이다([KnowledgeHubClient.tsx:51-55](../../frontend/src/app/admin/help/KnowledgeHubClient.tsx#L51-L55)). 커뮤니티 탭은 커뮤니티 기능의 기여로 업무게시판(CCCC)을 연다(`knowledge-community-tab.tsx`, `extensions/community/hub-tabs-knowledge.ts`). 허브는 `?bbsId=` 진입도 받는다. `?tab=`은 처음 열 탭만 고르므로 메뉴와 게시판은 1:1이 아니다.
- 메뉴가 보이려면 활성화와 그룹별 표시 배정(상위 메뉴 포함)이 모두 필요하다. 새 메뉴는 상위가 관리자 그룹에 보일 때 `ROLE_ADMIN`에만 자동으로 보인다. FAQ·질의응답·위키 메뉴는 `ROLE_ADMIN`·`ROLE_USER`에, 커뮤니티 메뉴와 "관리 센터 › 업무 지원"은 `ROLE_ADMIN`에만 보인다([메뉴 스냅숏](../../config/project-composer-menus.json)).
- 메뉴 활성화와 그룹 표시는 메뉴 구조 저장(`PUT /api/v1/admin/system/menus/structure`) 한 번으로 바뀐다. `MENU_UPDATE`가 필요하고, 그룹 변경이 있으면 `AUTHRT_GRANT`도 필요하다([MenuService.java:345-374](../../business-core/src/main/java/nuri/business/service/menu/MenuService.java#L345-L374)).
- 활성 메뉴 판정은 현재 URL의 `?bbsId`와 같은 메뉴에 가장 높은 점수를 준다([active-menu.ts:40-69](../../frontend/src/lib/navigation/active-menu.ts#L40-L69)). 운영 화면 URL에 `?bbsId`를 실으면, 활성화된 이용자 게시판 메뉴가 관리 메뉴를 이긴다.

### 3.4 게시 기간과 정렬

- 게시 종료일은 목록·검색·게시판 통계(`BoardPredicate`)와 상세·댓글·추천·만족도 목록·평균·등록(`assertPostingVisible`)에서만 집행된다. 공개 FAQ 목록·상세와 첨부 내려받기 판정에는 없다(공개 FAQ 상세 [BoardRepositoryImpl.java:40-64](../../business-app/src/main/java/nuri/business/domain/board/BoardRepositoryImpl.java#L40-L64), 목록 [:234-273](../../business-app/src/main/java/nuri/business/domain/board/BoardRepositoryImpl.java#L234-L273), [JdbcAttachmentReferenceResolver.java](../../business-core/src/main/java/nuri/business/service/file/JdbcAttachmentReferenceResolver.java)). 그래서 종료 글의 첨부는 번호만 알면 받을 수 있다.
- 게시 시작일은 어디서도 집행되지 않는다. 작성 화면도 "시작일은 기록만 한다"고 밝히고, 정직성 계약이 이 문구를 고정한다.
- 목록 응답은 게시 기간을 싣지 않는다. 그래서 목록 템플릿의 "게시 종료" 배지는 그려질 수 없다([BoardRepositoryImpl.java:161-178](../../business-app/src/main/java/nuri/business/domain/board/BoardRepositoryImpl.java#L161-L178)). 상세 배지는 브라우저 시간대의 오늘로 판정해, 서버 판정과 어긋날 수 있다.
- 대표 목록의 "최신순"은 작성일시(`crt_dt`) 내림차순이다. 정렬값을 보내지 않는 경로(업무 홈·통합 검색·공개 FAQ)는 작성 순번(`sort_ordr`) 내림차순이다.
- 게시 기간 입력에는 길이 검사만 있고 형식·달력·순서 검사가 없다. 수정 요청에서 날짜를 비우면 "변경 없음"으로 무시된다.
- 서버의 기준일은 `LocalDate.now(Asia/Seoul)`를 호출할 때마다 계산한다. 주입할 시계가 없다([BoardPolicySupport.java:116-147](../../business-app/src/main/java/nuri/business/service/board/BoardPolicySupport.java#L116-L147)).
- 관리 센터 통계 가운데 날짜별 집계와 실시간 오늘 게시글은 작성일 기준이다. 요약 카드의 "누적 게시물"은 기간 조건이 없는 전체 건수다. 셋 다 마스터를 조인하지 않아 비밀·종료·미래 시작일·사용 안 함 게시판 글을 센다.

### 3.5 지정 게시판과 Q&A

- 도움말 센터(`/help`) 1:1 문의는 화면이 `scrtYn='Y'`를 보내 비밀글로 등록한다([HelpUserService.ts:207-218](../../frontend/src/services/business/user/help/HelpUserService.ts#L207-L218)). 지식 허브 질의응답 탭과 일반 작성 화면은 공개로 등록한다. 서버는 비밀글을 강제하지 않는다. 그래서 Q&A 게시판에는 비밀 문의와 공개 질문이 섞인다.
- 공개 FAQ API도 `BOARD_READ`, 즉 로그인이 필요하다.
- Q&A 분류값 `CAT01`은 어떤 코드 표에도 없는 프런트 상수이고, 상세 화면에 그대로 보인다.

### 3.6 마스터 화면과 마법사

- 마스터 목록은 첫 10건만 보이고 페이저가 없다.
- 설정 모달은 이름·소개·댓글·만족도·첨부·파일 수·파일당 크기·사용 여부를 고친다. 유형·속성 코드(`bbsTypeCd`·`bbsAtrbCd`)는 수정 요청에서 버려진다. 템플릿 ID(`tmpltId`)는 요청값이 있으면 그 값으로 바뀐다(화면은 기존 값을 다시 보낸다). 그래서 API로 화면 유형의 짝(DEC-OPS-332)을 깰 수 있고, Q&A 해결 표시 판정도 `tmpltId`로 하므로 함께 바뀐다.
- 마법사는 게시판 생성 뒤 메뉴를 별도 요청으로 등록하고, 실패하면 게시판을 다시 만들지 않고 메뉴만 다시 시도한다. 다시 시도하려면 전체 메뉴 조회(`MENU_READ`)가 필요한데, 사전 권한 점검은 `BBS_MST_CREATE`·`MENU_CREATE`만 본다.
- 다른 관리 화면으로 대상을 넘기는 장치는 [target-handoff](../../frontend/src/lib/navigation/target-handoff.ts) 하나다. 메뉴 관리는 "새 메뉴 추가" 인계만 받고, 기존 메뉴를 골라 여는 인계는 없다.

### 3.7 데이터·감사·동시성

- 게시판 마스터에는 버전 컬럼이 없다. 게시글은 `@Version`이 있지만 수정 요청이 버전을 싣지 않아, 화면에서 읽은 뒤 다른 사람이 고친 내용을 덮는다. `tb_bbs_item.version`은 NULL을 허용한다.
- 댓글·만족도 사용 여부(`ans_yn`·`stsfdg_yn`)는 마스터와 옵션 표(`tb_bbs_master_optn`) 양쪽에 저장되고 `syncOption()`이 맞춘다.
- 게시판 마스터의 수정·일괄 상태 변경·영구 삭제는 이력을 남기지 않는다. 민감 작업 원장(`tb_sys_adt_log`)은 전후 값을 싣지 못하고, 한 요청에 완료 행을 하나만 남긴다. 단건 비활성화(`DELETE …/board-masters/{bbsId}`, `BBS_MST_DELETE`)도 `use_yn`을 N으로 바꾸고 이력을 남기지 않는다. 마스터 목록의 삭제 단추가 활성 게시판에서 이 경로를 부른다. 같은 전이를 하는 일괄 상태 변경의 권한은 `BBS_MST_UPDATE`다.
- 본문은 편집기 HTML로 저장되고 서버 정제는 없다. 정제는 렌더 시점의 DOMPurify가 한다. `pst_cn` 4,000자 한도는 마크업을 포함한다.

## 4. 결정

각 결정의 근거와 기각한 대안을 함께 적는다. ADR-0040이 같은 결정을 같은 번호로 기록한다(설계 Dn = ADR-0040 결정 n).

### D1. 사용 안 함 게시판은 이용자에게 읽기·쓰기 모두 닫는다

- 게시글 등록·수정·삭제·해결 표시와 만족도 수정·삭제는 게시판이 사용 안 함이면 거부한다. 거부는 `BOARD_NOT_FOUND`(404)다. 목록과 같은 응답이라 게시판의 존재를 드러내지 않는다.
- 운영자 예외: `BOARD_READ_ALL` 보유자는 사용 안 함 게시판의 목록·상세를 읽는다. 해당 동작 권한(`BOARD_CREATE`·`BOARD_UPDATE_ALL`·`BOARD_DELETE_ALL`)이 있으면 글을 준비하거나 정리할 수 있다. 공개 전 콘텐츠를 미리 올리고, 운영을 마친 게시판의 글을 정리하려는 것이다. 운영자 예외의 열람에는 상세 화면의 댓글·만족도 목록·평균 조회도 들어간다. 사용 안 함 게시판에서 댓글·만족도 등록과 추천은 운영자에게도 닫는다(지금과 같다).
- 게시판 메타는 사용 안 함이면 운영자에게만 준다. 메타·상세·댓글 열람도 사용 여부를 커뮤니티 가드보다 먼저 본다.
- 서버 구현은 쓰기 진입 판정 한 곳(`loadWritableMaster`)에 모은다. 지정 게시판 편집 가드, 사용 여부(`BOARD_READ_ALL` 운영자 예외, 거부는 404), 커뮤니티 가드, 글 소속(`findPostInBoard`)·논리 삭제 글 거부를 이 순서로 보고, 파일 업로드보다 먼저 부른다. 사용 여부를 커뮤니티 가드보다 먼저 보는 것은 읽기 경로 `assertActiveBoardMaster`와 같은 상대 순서다. 지정 게시판 편집 가드는 설정으로 알려진 ID만 보므로 맨 앞에 두어도 게시판의 존재를 드러내지 않는다. 등록·수정 가운데 파일을 함께 받는 경로는 경로의 게시판 ID와 본문의 게시판 ID가 같은지도 본다.
- 마법사는 게시판을 **사용 안 함**으로 만든다. "공개 준비"와 "사용 중지"는 저장값이 같고 따로 구분하지 않는다. 이를 위한 상태 컬럼은 두지 않는다.
- 기각: ① 새 상태 컬럼(준비·운영·중지·보관). 구분이 주는 이득보다 상태 전이 설계와 마이그레이션 비용이 크다. ② 사용 안 함에서 작성자 본인의 정리 허용. 이용자에게 보이지 않는 게시판에서 본인 글만 고칠 길을 두면 존재 노출 경로가 생긴다.

### D2. 운영 화면은 동적 경로와 승인된 탭 키를 쓴다

- 경로는 `/admin/community/boards/master/[id]`다. 세그먼트 이름은 URL 상태 승인 원장의 자원 식별자 부류에 이미 있는 `[id]`를 쓴다. 값은 `BBSMSTR_` 뒤 12자 형식만 받고, 아니면 `notFound()`로 끝낸다.
- 탭은 `?tab=posts|settings|access`이고 공용 `StandardTabs`로 그린다. 탭 해석은 `board-operations-tabs.ts`의 `TAB_HUB`로 둔다. URL을 다시 쓸 때는 `pickAllowedParams` 재조립을 쓴다. 메뉴나 별칭에 구체 ID가 든 운영 화면 주소를 등록하지 않는다.
- 기본 탭은 `settings`다. 권한이 없어 숨긴 탭(`posts`)을 요청하면 모르는 값과 같이 기본 탭으로 내린다. URL 키는 `[id]`·`tab`(필요하면 `page`)으로 한정하고, 게시물 탭과 마스터 목록의 조회 조건은 URL 밖 상태로 둔다. 조회 조건을 URL에 싣기로 하면 URL 상태 승인 부류와 routeKeyBindings를 같은 배치에서 원장에 더한다. 운영 화면 주소는 `board-operations-tabs.ts`가 내보내는 import 없는 도우미(`boardOperationsHref(bbsId, tab)`)로만 만든다. 탭 목적지 계약이 경로에 식 자리가 든 템플릿 리터럴을 세지 않으므로, 탭 값을 타입으로 묶기 위해서다.
- 진입 권한은 `BBS_MST_READ`다. 게시물 탭은 `BOARD_READ_ALL`이 있을 때만 보이고, 메뉴·접근 탭의 그룹 표시는 `AUTHRT_READ`가 있을 때만 읽는다.
- 기각: ① `master?bbsId=`. 활성 메뉴 판정이 이용자 게시판 메뉴를 고르게 된다(§3.3). ② `view=` 탭 키. 승인 원장에서 폐기된 키다. ③ `[bbsId]` 세그먼트 이름. 승인 원장의 부류를 바꿔야 한다.

### D3. 예약 게시는 날짜 기준 전역 집행이다

- 게시 시작일이 오늘(Asia/Seoul)보다 뒤인 글은 작성자와 `BOARD_READ_ALL` 보유자 외에게 보이지 않는다. 대상 경로는 목록·통합 검색·게시판 통계·업무 홈 카드·상세·댓글·추천·만족도·공개 FAQ·첨부 내려받기다. 직접 접근하면 게시 종료 글과 같이 404다(첨부 내려받기 거부는 첨부 정책대로 403).
- 판정은 공통 지점 세 곳에서 같은 기준일로 한다. 단건은 `assertPostingVisible`를 기간 전체로 넓힌다. 목록 술어는 `BoardPredicate`에 시작일 조건을 더하고, 공개 FAQ 목록·상세도 같은 술어를 쓴다(A0). 모듈 경계 밖에 있는 첨부 판정만 따로 판정하고, 기준일은 Java에서 계산한다. 첨부의 공유 근거는 본문과 같은 기간·사용 여부 판정을 쓴다. `BOARD_READ_ALL` 보유자는 본문처럼 기간 조건(A0 종료일, B1 시작일)과 게시판 사용 여부(A2)만 면제받는다(DEC-OPS-206 ①, ADR-0040 결정 1·3, 일정 `SCHEDULE_READ_ALL` 공유 근거 선례). 비밀글·논리 삭제 글의 첨부는 지금처럼 `FILE_READ_ALL`만 관리자 경로다. 본문 판정과의 일치는 대조 시험(`BoardAttachmentAccessTest`, `ScheduleAttachmentAccessTest` 선례)으로 묶는다. 비밀·삭제 글에서는 "`BOARD_READ_ALL`만 있으면 본문은 열리고 첨부는 403"을 의도된 비대칭으로 고정한다.
- 기준일은 요청마다 한 번 계산한다. 게시판 정책에 Asia/Seoul 기본 `Clock`과 같은 패키지 전용 `useClock`을 둔다(`RealTimeDashboardService` 선례).
- 게시 상태(`SCHEDULED`·`POSTING`·`ENDED`)는 서버가 계산해 목록·상세 응답에 싣는다(`BoardDto.recommended`와 같은 읽기 전용 필드). 화면은 날짜를 다시 계산하지 않는다(DEC-OPS-140). 목록 응답에 게시 시작일·종료일도 싣는다.
- 게시판 설정 "예약 게시"(`rsvt_pstg_psblty_yn`)는 **새 미래 시작일을 받을지**만 정한다. 꺼져 있으면 서버가 새 미래 시작일을 거부한다. 설정을 켜거나 꺼도 기존 글의 가시성은 바뀌지 않는다.
- 작성자는 글이 공개되기 전(시작일이 미래인 동안)에만 시작일을 바꿀 수 있다. 공개 뒤의 시작일 변경은 `BOARD_UPDATE_ALL` 보유자만 한다. 정렬 조작을 막기 위해서다(D4). 이 두 규칙에서 시작일 "변경"은 정규화한 8자리 요청값이 저장값과 다른 경우를 말한다. 저장값과 같은 시작일을 다시 보낸 수정은 변경이 아니므로 예약 설정과 공개 뒤 변경 제한 어디에도 걸리지 않는다.
- 집행을 켜기 전에 환경마다 읽기 집계로 기존 미래 시작일 글을 진단한다(게시판·작성자별 건수, 형식이 깨진 값, 시작>종료). 진단 결과는 PR과 적용 로그에 남긴다. 2026-10-23 사용자 결정으로 해당 행이 있어도 데이터를 보정하지 않고 집행한다. 기록용 미래 시작일 글은 시작일까지 작성자·조회 대행 권한자에게만 보인다. 새로 만드는 재사용 DB에는 이 데이터가 없다.
- `PostCreatedEvent`는 "생성"을 뜻하며 공개를 뜻하지 않는다. 이 사실을 이벤트 설명에 적는다. 파생 제품의 구독자는 가시성을 다시 판정해야 한다. 공개 시점 이벤트는 만들지 않는다.
- 관리 센터 통계는 등록 건수라는 의미를 유지하고, 화면 이름으로 그 의미를 밝힌다. 날짜별 집계는 "등록 건수(작성일 기준)", 실시간 "오늘 게시글"은 "오늘 등록된 글"로 부른다. 요약 카드 "누적 게시물"은 기간 조건이 없으므로 "전체 등록 건수"로 부른다. 게시 시작일 기준 계열은 만들지 않는다.
- 기각: ① 게시판별 예약 표지(글마다 예약 여부 컬럼). 새 컬럼·백필이 필요하고, 설정 저장이 게시글 대량 갱신이 된다. ② 공개 시점 알림 이벤트. 시각 기반 작업이 필요해 범위를 넘는다.

### D4. 목록은 게시 기준일로 정렬한다

- 일반 정렬 키는 **게시 기준일 = 작성일자(KST)와 게시 시작일 중 늦은 값**이다. 동률이면 작성일시, 작성 순번 내림차순으로 정한다. 대표 목록의 "최신순"과 정렬값 없는 경로에 같이 쓴다. 고정 글은 그 앞에 둔다(D5). 이용자 목록·업무 홈의 표시 날짜는 지금처럼 작성일(`crtDt`, DEC-OPS-140 ①)이다. 그래서 예약 글은 정렬 위치에 비해 표시 날짜가 이를 수 있다(예약 게시 기본값은 N). 이용자 목록에 게시 시작일을 함께 보일지는 B1 화면 세부에서 정한다.
- 질의에서 계산하므로 새 컬럼이 없다. D3의 "공개 뒤 시작일 변경 제한" 덕분에 작성자가 기준일을 끌어올릴 수 없다. 구현 시 공유 OCI에서 읽기 전용 실행 계획을 확인하고, 필요할 때만 식 인덱스를 둔다.
- 기각: 게시 시작일 그대로 정렬. 작성자가 시작일을 바꿔 목록 맨 위로 올라갈 수 있다.

### D5. 상단 고정은 표준 용어 컬럼과 새 권한으로 둔다

- 게시글: `upend_fix_yn`(기존 표준 용어 "상단고정여부", `varchar(1) NOT NULL DEFAULT 'N'` + CHECK)과 `upend_fix_end_ymd`(신규 용어 "상단고정종료일자", `varchar(8)`)를 둔다. `ntc_yn`은 표준 정의가 "공지 여부"라 재사용하지 않고 그대로 둔다. 고정할 때 고정 종료일은 필수다. 비우면 서버가 오늘 + `upend_fix_bsc_day_cnt`로 채운다. CHECK(`upend_fix_yn='N' OR upend_fix_end_ymd IS NOT NULL`)를 함께 둔다.
- 게시판: `upend_fix_psblty_yn`(상단고정가능여부), `upend_fix_uplmt_nocs`(상단고정상한건수, `numeric(10)`), `upend_fix_bsc_day_cnt`(상단고정기본일수, `numeric(7)`)를 둔다. 모두 신규 용어다.
- 고정 순서 컬럼은 두지 않는다. 고정 글끼리는 게시 기준일 순이다. 만료된 고정은 질의 조건으로 저절로 빠지고, 별도 작업은 없다.
- 상한은 서버가 게시판 마스터를 비관 잠금한 상태에서 검사한다. 세는 글은 정렬의 고정 판정과 같은 술어(`upend_fix_yn='Y'`, 고정 종료일 ≥ 기준일)를 만족하면서 논리 삭제되지 않은 글(`use_yn='Y'`)이다. 게시 기간(예약·종료)과 비밀 여부로는 거르지 않는다. 그래서 보이는 고정 글은 언제나 센 글의 부분집합이 되고, 종료일 해제나 시작일 당김으로 글이 다시 보여도 상한을 넘지 않는다. 종료·예약 글의 고정은 고정 종료일이 지나거나 해제될 때까지 상한을 차지한다.
- 권한은 새 기능 권한 `BOARD_PIN`("게시글 · 상단 고정")이다. 기본 배정은 비우고 게시판·커뮤니티 운영 묶음에 넣는다(`NOTICE_EDIT`·`FAQ_EDIT` 선례). 공지·FAQ 지정 게시판에서는 두 편집 권한도 함께 필요하다.
- 고정·해제는 게시글 버전을 올리지 않는다. 작성자 폼이 쓰지 않는 컬럼이고, 올리면 작성자가 예상하지 못한 충돌을 받는다. 대신 운영 이력에 남긴다(D9).
- 기각: ① `ntc_yn` 재사용. 표준 정의와 어긋나고 특수 공지 게시판 개념과 섞인다. ② 기본 배정 `ROLE_ADMIN`. 시드 재생성, 메뉴 스냅숏 갱신, 기존 DB 배정 마이그레이션(코어 데이터 변경)까지 번진다.

### D6. 설정은 게시판 마스터 한 곳에 두고 기존 동작을 기본값으로 한다

| 설정 | 컬럼(표준 용어) | 기존 게시판 기본값 | 배치 |
|---|---|---|---|
| 예약 게시(새 미래 시작일 허용) | `rsvt_pstg_psblty_yn` (신규 "예약게시가능여부") | N | B1 |
| 상단 고정 허용·상한·기본 일수 | `upend_fix_psblty_yn`·`upend_fix_uplmt_nocs`·`upend_fix_bsc_day_cnt` (신규) | N · 5 · 30 | B2 |
| 비밀글 정책 | `prvt_pst_plcy_cd` (신규 "비공개게시물정책코드", 코드C12) | `NONE` | B3 |
| 추천 사용 | `rcmdtn_use_yn` (기존 "추천사용여부") | Y | B3 |
| 목록 상단·하단 안내 | `bbs_upend_cn`·`bbs_lwpt_cn` (기존 용어) | 없음 | C1 |
| 새 글 본문 양식 | `form_cn` (기존 "양식내용") | 없음 | C1 |

- 옵션 표(`tb_bbs_master_optn`)는 넓히지 않는다. 이중 저장을 늘리지 않기 위해서다.
- 기본값은 지금의 동작을 그대로 유지한다. 지금 모든 게시판이 추천을 받으므로 추천은 Y다. 일반 작성 화면에 비밀글 선택이 없으므로 비밀글 정책은 `NONE`이다.
- 신규 표준 용어 6건(`RSVT_PSTG_PSBLTY_YN`, `UPEND_FIX_PSBLTY_YN`, `UPEND_FIX_UPLMT_NOCS`, `UPEND_FIX_BSC_DAY_CNT`, `PRVT_PST_PLCY_CD`, `UPEND_FIX_END_YMD`)은 단어가 모두 대표어로 이미 있어 용어만 등록한다. 등록은 V2_131 형식으로 컬럼을 추가하는 같은 Flyway에서 한다(단어 대표성 확인 → 용어 INSERT → 용어·도메인 검증 → ADD COLUMN·CHECK). `NOT NULL` 컬럼은 `DEFAULT`를 함께 둔다(무중단 Expand).
- 수량 컬럼은 도메인대로 `numeric(10)`·`numeric(7)`을 쓰고, 엔티티는 `DurableJob`처럼 precision을 매핑한다.

### D7. 비밀글 정책은 세 값이다

- `NONE`: 작성 화면에 비밀글 선택이 없다. 서버는 요청값을 그대로 저장하고, 요청값도 저장값도 없으면 공개('N')로 저장한다. 옛 NULL 행은 공개로 판정하고 응답에서 'N' 으로 낸다(DEC-OPS-388 ⑦).
- `OPTIONAL`: 작성 화면에 비밀글 선택을 둔다.
- `REQUIRED`: 서버가 항상 비밀글로 저장한다(문의형 게시판).
- Q&A 게시판은 `NONE`으로 둔다. 도움말 센터 1:1 문의(비밀)와 지식 허브 질의응답(공개)이 같은 게시판을 쓰는 지금 동작이 의도이기 때문이다. 정책을 바꾸면 기존 비밀글은 계속 보호된다.
- 기각: 여부 두 개(허용·강제). "강제인데 선택 안 함" 같은 모순 조합이 생긴다.

### D8. 메뉴 연결·공개 준비는 운영 화면이 계산해 보이고, 바꾸기는 메뉴 관리에서 한다

> [2026-10-26] 이 절의 마법사 메뉴 단계·결과 화면 순서·메뉴 경로 인계 범위와 D8의 공개 준비 통과 기준은 [ADR-0043](decisions/ADR-0043-board-publish-flow-and-designated-boards.md)이 대체했다. 아래 원문은 당시 결정 기록으로 둔다.

- 판정 근거는 두 가지다. 메뉴 주소가 이 게시판 주소(`bbsId`)를 가리키거나, 허브 탭 설정이 이 게시판을 연다. 허브 탭 대응은 core 게시판 ID 상수(`config/board-ids.ts`)와 각 허브 `TAB_HUB`의 `routes`·탭 키(셸 탭과 `contributable`)·`?bbsId=` 진입으로 만든다. 커뮤니티 같은 기능 소유 모듈과 생성 슬롯 레지스트리는 import하지 않는다(`knowledgeService.ts`의 COMMUNITY → `COMMUNITY_BOARD_ID` 선례). 기여 탭이 없는 구성에서는 그 메뉴가 투영으로 빠진다. 그 밖의 주소는 **확인 불가**로 둔다.
- 메뉴 상태는 다음 중 하나다: 연결 없음 / 비활성 / 관리자 그룹만 표시 / 일반 그룹 표시 / 확인 불가. 그룹을 읽을 권한(`AUTHRT_READ`)이 없으면 **확인 권한 없음**으로 보이고, 모두 허용으로 추정하지 않는다. 메뉴 원장을 읽을 권한(`MENU_READ`)이 없으면 메뉴 연결 전체(메뉴·접근 탭과 §5.2 목록의 메뉴 연결 칸)를 확인 권한 없음으로 보이고, "연결 없음"으로 추정하지 않는다. 이때 공개 준비 점검은 통과가 아니라 확인 불가로 끝난다. 관리자 그룹은 `ROLE_ADMIN`·`ROLE_SYSTEM`이다(§3.3). 그 밖의 그룹(사용자 정의 그룹 포함)에 하나라도 보이면 "일반 그룹 표시"이고, 보이는 그룹 이름을 나열한다.
- 공개 준비 점검은 세 항목을 모두 통과해야 통과다. 게시판 사용 중이어야 하고, 일반 그룹에 보이는 활성 메뉴가 있어야 한다. 공지·FAQ 지정 게시판이면 편집 권한 배정도 확인돼야 한다.
- 메뉴 활성화와 그룹 표시는 새 API 없이 기존 메뉴 구조 저장으로 한다. 운영 화면은 대상 메뉴를 고른 상태로 메뉴 관리를 연다. 이를 위해 target-handoff에 사용자 인계·화면 인계와 다른 세 번째 인계 종류 `menu-focus`를 더한다. 저장 키를 따로 두고, `{ menuSn: number }` 형식 검사, 같은 1분 수명, 적용 뒤 삭제를 따른다. 그리고 메뉴 관리가 그 메뉴를 선택해 연다. 필요한 권한(메뉴 관리 진입 `MENU_READ`, 저장 `MENU_UPDATE`, 그룹 표시 읽기 `AUTHRT_READ`·변경 `AUTHRT_GRANT`)과 "상위 메뉴도 같은 그룹에 보여야 한다"는 조건을 운영 화면에서 미리 알린다.

### D9. 운영 처리는 게시판 변경 이력에 남긴다

- 게시판이 소유하는 추가 전용 이력 표를 둔다. 형태는 공통코드 변경 이력(V2_110)을 따른다. 대상 유형(게시판·게시글), 변경 유형, 변경 항목, 변경 전후 값, 변경자, 생성일시를 두고 FK는 두지 않는다. 표 이름과 컬럼은 A2 착수 때 표준 메타와 대조해 정한다.
- 기록 대상은 게시판 설정 변경, 사용 여부 변경(설정 저장·일괄 상태 변경·단건 비활성화 모든 경로), 고정·해제, 운영 화면에서 한 게시 기간 변경(빠른 편집 단건과 일괄)이다. 후속 배치에서는 이동·복사도 포함한다. 작성 화면을 통한 일반 수정의 이력은 C2 수정 이력 범위다. 값이 바뀐 경우에만 같은 트랜잭션에서 한 건씩 INSERT한다. 조회는 운영 화면의 "변경 이력" 대화상자에서 `BBS_MST_READ`로 한다. 대상 유형이 게시글인 행은 `BOARD_READ_ALL`이 있을 때만 응답에 싣는다(게시물 탭과 같은 조건, D2).
- 되돌릴 수 없는 게시판 영구 삭제는 민감 작업 원장(`@SensitiveOperation`)에도 남긴다.
- 불변 트리거와 보존 정리는 두지 않는다. 공통코드 이력과 같은 수준이며, 필요해지면 따로 결정한다.
- 확정(2026-10-23, A2 착수):
  - **표:** 이름은 `tb_bbs_chg_hstry`, PK는 `bbs_chg_hstry_sn`이다. PK 용어는 등록하지 않는다(V2_110 선례, GAP-STD-001 A 후보). 승인된 신규 용어 6건 밖이다.
  - **기존 표준 용어 컬럼:** `chg_trgt_type_cd`, `chg_type_cd`, `chg_artcl_nm`, `chg_bfr_cn`, `chg_aftr_cn`, `chg_user_idntfr`, `frst_rgtr_id`, `crt_dt`. `bbs_id`·`pst_sn`은 기존 게시판 표와 같은 처리다.
  - **대상 유형:** `BBS`·`PST`.
  - **변경 유형:** `SETTING`(설정), `USE`(사용 여부), `PERIOD`(게시 기간), `PIN`·`UNPIN`(고정). B1·B2 값을 미리 넣어 제약을 다시 바꾸지 않는다.
  - **행 단위:** 바뀐 항목마다 한 행이다.
  - **영구 삭제:** 이 표에 남기지 않는다. 지운 게시판은 운영 화면이 없어 볼 수 없으므로 민감 작업 원장이 맡는다.
  - **기록기:** 게시판 서비스 패키지의 컴포넌트 하나다. B1·B2가 다시 쓴다.

### D10. 동시 수정은 버전으로 막는다

- 게시판 마스터에 `version integer NOT NULL DEFAULT 0`과 CHECK를 둔다(V2_133·DEC-OPS-359 형식). 설정 응답에 버전을 싣고, 저장 요청이 그 버전을 보낸다. 버전이 없으면 400, 다르면 409다. 화면은 409를 받으면 최신 값을 다시 읽어 비교하게 한다.
- 게시글 수정 요청도 버전을 싣는다(B1). 착수 전에 `tb_bbs_item.version IS NULL` 행을 읽기 집계로 확인하고, 있으면 보정·`NOT NULL` 마이그레이션을 승인 대상으로 올린다.
- 일괄 처리(고정·종료일 변경)는 대상별 버전을 받지 않는다. 서버가 모든 대상을 다시 판정하고 하나라도 맞지 않으면 전체를 적용하지 않는다. 종료일 일괄 변경은 작성자 폼과 같은 컬럼을 쓰므로 버전을 올린다.
- 단건 비활성화와 일괄 사용 상태 변경은 요청 버전을 받지 않는다. 그래도 `@Version`을 올리므로, 그 사이에 들어온 설정 저장은 409를 받는다.

### D11. 사용자용 게시판 선택지는 서버가 가시성으로 거른다

- `GET /api/v1/boards/options`(`BOARD_READ`)는 호출자가 이용할 수 있는 게시판만 준다. 사용 중이어야 하고, 커뮤니티 귀속이면 승인 회원이어야 한다. 시드 폴백 상수를 일반 사용자 경로에서 걷는다.
- 관리자 선택지(`BBS_MST_READ`)는 지금처럼 관리 API를 쓴다.

### D12. 게시 기간 입력 계약과 해제

- 화면은 날짜를 8자리(`yyyyMMdd`)로 바꿔 보낸다. 서버는 `@Pattern(Ymd.OPTIONAL_PATTERN)`과 클래스 단위 `@YmdRange`로 형식·달력·순서를 검사한다. 두 필드를 입력 계약 원장의 날짜 바인딩에 등재한다.
- 일반 수정의 "null = 변경 없음"은 유지한다. 종료일 해제(기한 없음)는 운영 일괄 처리의 명시적 동작(`CLEAR_END`)으로 둔다. 작성자 화면의 해제는 요구가 확인될 때 명시 플래그로 더한다.

## 5. 화면 설계

시연 화면은 검토용 아티팩트(저장소 밖, 비규범)로 만들었다. 이 절이 정본이다.

### 5.1 정보구조

```text
관리 센터 › 콘텐츠 운영
└─ 게시판 관리                         /admin/community/boards/master
   ├─ 게시판 만들기                     /admin/community/boards/maker
   └─ 게시판 운영 화면                  /admin/community/boards/master/[id]
      ├─ ?tab=posts      게시물         (BOARD_READ_ALL)
      ├─ ?tab=settings   설정           (BBS_MST_READ, 저장은 BBS_MST_UPDATE)
      └─ ?tab=access     메뉴·접근      (그룹 표시는 AUTHRT_READ)
```

메뉴 표시명은 "통합 게시판 마스터 콘솔"을 "게시판 관리"로 바꾼다(A1). 경로와 메뉴 번호는 그대로다.

### 5.2 게시판 관리 목록

- `WorkListPage` 문법을 따른다. 조회 조건은 게시판 이름과 게시판 사용(전체·사용·사용 안 함)이고, `조회`나 Enter로 적용한다. 메뉴 연결은 서버 조회 조건이 아니다. 화면이 현재 쪽의 행에 대해 계산해 보이는 열이다. D8 판정은 프런트 상수와 메뉴 원장으로 하므로 서버 페이지를 거를 수 없다. `MENU_READ`가 없으면 이 열은 확인 권한 없음이다.
- 열은 선택 / 게시판(이름·ID·지정 게시판 표지(응답의 지정 용도)) / 화면 유형 / 게시판 사용 / 메뉴 연결 / 작업이다. 게시판 사용과 메뉴 연결을 한 칸에 합치지 않는다.
- 화면 유형은 `board-types.ts` 정본의 짝이 맞을 때만 이름을 보인다. 짝이 맞지 않으면 저장값을 그대로 보이고 "템플릿 짝 불일치"를 덧붙인다(DEC-OPS-332).
  > [2026-10-26] 이 줄은 [ADR-0043](decisions/ADR-0043-board-publish-flow-and-designated-boards.md) 결정 5가 대체했다 — 화면 유형 이름은 템플릿(`tmpltId`) 기준이고, 짝이 맞지 않으면 "유형 코드 짝 불일치(저장된 코드 …)"를 덧붙인다.
- 메뉴 연결 칸은 메뉴마다 근거(게시판 주소 또는 `허브 탭 ?tab=…`)와 위치를 보인다. 메뉴 이름과 게시판 이름이 다르면 알린다(예: 위키 메뉴 → 일정 게시판).
- 페이지는 1 기반 `page`·`size`이고(ADR-0036), 조회 시점을 보인다.
- 일괄 사용 상태 변경은 대상·영향을 확인받는다. 사용 안 함으로 바꾸는 대상에 앱이 ID로 직접 쓰는 게시판이 있으면 사용처를 나열한다(공지·FAQ 지정, 업무 홈 카드, 지식 허브 탭, 공개 FAQ). 사용처는 게시판 마스터 응답의 지정 용도와 프런트 허브 탭 대응(D8)으로 계산한다. 지정 용도는 서버가 `nuri.boards.*`로 계산한다(공지·FAQ 지정과 공개 FAQ, 업무 홈 카드). 행의 단건 비활성화(지금의 삭제 단추)는 일괄 사용 상태 변경으로 흡수해 같은 영향 확인과 사용처 나열을 거친다. 서버의 단건 비활성화 경로(`DELETE …/board-masters/{bbsId}`, `BBS_MST_DELETE`)를 걷을지, 같은 전이의 권한(`BBS_MST_UPDATE`·`BBS_MST_DELETE`)을 통일할지는 A2에서 H3 판정과 함께 정한다.
- 영구 삭제는 목록 툴바에 두지 않는다. 설정 탭의 별도 절차로 두고, "글이 한 번이라도 있었던 게시판은 영구 삭제할 수 없다"는 사실을 미리 알린다.
- 머리 안내: "메뉴가 보인다고 게시판을 쓸 수 있는 것은 아닙니다. 게시글 권한은 모든 게시판에 함께 적용됩니다."

### 5.3 게시판 만들기(4단계)

| 단계 | 내용 |
|---|---|
| 1. 용도·기본정보 | 용도(공지형·자료실형·자유형·질의응답형)는 아직 직접 바꾸지 않은 설정만 채운다. 이름(100자), 소개, 커뮤니티 귀속. 귀속은 만든 뒤 바꿀 수 없다고 경고한다. 이름에 "공지"가 들어가도 공지 게시판 편집 권한이 적용되지 않는다고 알린다 |
| 2. 화면·기능 | 7개 화면 유형 전부. 댓글·만족도·첨부(파일 수, 파일당 크기 ≤ 서버 상한 10MB, 비우면 전역 상한=저장값 0). 미리보기는 좁은 폭에서도 보인다. 예약·고정은 해당 배치가 구현된 뒤에만 보인다 |
| 3. 메뉴·접근 확인 | 메뉴 위치(관리자 전용 상위를 고르면 사용자용 게시판 위치로 맞지 않다고 경고), 메뉴 이름·순서. 접근을 정하는 세 축(메뉴 노출·게시글 권한·회원 범위)을 사실대로 설명한다. 필요한 권한: `BBS_MST_CREATE`·`MENU_CREATE`·`MENU_READ` |
| 4. 최종 확인 | 요약(만든 직후 상태 = 사용 안 함, 메뉴 = 비활성·관리자 그룹에만 자동 표시, 권한 = 새로 주지 않음) |

용도마다 채우는 값은 다음과 같다(2026-10-23 A2 착수 때 확정). 용도는 사용자가 아직 직접 바꾸지 않은 칸만 채운다. 예약·고정·비밀글·추천 칸은 해당 배치(B1~B3)가 구현된 뒤에만 채운다.

| 용도 | 화면 유형(`tmpltId`) | 댓글 | 만족도 | 첨부 | 파일 수 | 이후 배치 기본값 |
|---|---|---|---|---|---|---|
| 공지형 | Enterprise List(`TMPLT_LIST`) | 받지 않음 | 받지 않음 | 허용 | 3 | 예약 허용, 상단 고정 허용(상한 5·기본 30일), 비밀글 `NONE`, 추천 사용 안 함 |
| 자료실형 | Enterprise List(`TMPLT_LIST`) | 받음 | 받음 | 허용 | 10 | 예약 안 함, 고정 안 함, 비밀글 `NONE`, 추천 사용 |
| 자유형 | Enterprise List(`TMPLT_LIST`) | 받음 | 받지 않음 | 허용 | 3 | 예약 안 함, 고정 안 함, 비밀글 `NONE`, 추천 사용 |
| 질의응답형 | Professional Q&A(`TMPLT_QNA`) | 받음 | 받음 | 허용 | 3 | 예약 안 함, 고정 안 함, 비밀글 `OPTIONAL`, 추천 사용 |

파일당 크기는 용도와 무관하게 비워 둔다(전역 상한). 용도를 고르지 않으면 지금 기본값(지식 허브 화면, 댓글·만족도·첨부 받음, 파일 3)을 쓴다.

결과 화면은 다음과 같다.
- **성공:** "게시판 만들기 완료 / 메뉴 등록 완료(비활성) / 남은 일"을 보인다. 남은 일은 두 가지다. 하나는 메뉴 관리에서 메뉴를 활성화하고 관리자 그룹이 아닌 이용자 그룹에 보이도록 함께 저장하는 것이다(`MENU_READ`·`MENU_UPDATE`·`AUTHRT_READ`·`AUTHRT_GRANT` 필요). 다른 하나는 운영 화면 설정 탭에서 게시판을 사용으로 바꾼 뒤 공개 준비 점검이 통과하는지 확인하는 것이다(`BBS_MST_UPDATE` 필요). 공개 준비 점검은 게시판 사용 여부도 보므로 사용으로 바꾼 뒤에야 통과한다. 권한이 없는 일은 권한이 있는 관리자에게 요청하라고 안내한다. 주 동작은 "이 게시판 공개 준비 계속하기"(운영 화면 `?tab=access`)다.
- **메뉴 등록만 실패:** 게시판을 다시 만들지 않고 메뉴 등록만 다시 시도한다. 다시 시도는 비활성 메뉴까지 포함한 전체 메뉴에서 이 게시판 주소를 먼저 찾는다.

현행 정직성 계약이 요구하는 메뉴 비활성 등록과 "메뉴 관리에서 활성화" 문구는 유지한다.

### 5.4 운영 화면: 게시물 탭

게시물 탭은 `WorkListPage` 문법을 따른다(§5.2와 같다). 탭의 기능은 배치마다 더한다. A2에서는 D1 운영자 예외로 목록(제목·작성자·작성일·게시 기간)만 보인다. B1이 게시 상태, 조회 조건, 일정 빠른 편집, 종료일 일괄 처리를 더하고, B2가 고정 열·조건·편집과 일괄 고정을 더한다. 해당 배치를 구현하기 전에는 그 열·조건·단추를 보이지 않는다(§5.3·§5.5와 같다).

- 머리: 게시판 이름, 사용 상태, 메뉴 상태, 지정 게시판 표지, "이용 화면 열기". 사용 안 함이면 "이용자에게 닫혀 있다, 운영자는 정리할 수 있다"를 알린다.
- 조회 조건: 제목, 게시 상태(게시 중·예약·게시 종료 — 서버 값), 상단 고정. `조회`/Enter로 적용하고, 조건이 바뀌어 선택이 해제되면 알린다.
- 표: 선택 / 제목(고정·비밀 표지) / 게시 상태 / 게시 기간 / 상단 고정(종료일) / 작성자·작성일 / 빠른 편집. 기본 정렬은 고정 → 게시 기준일 → 작성 순번(D4)이다.
- 빠른 편집(한 건): 게시 시작일·종료일·상단 고정·고정 종료일. 저장 전 변경 전후를 보인다. 게시 중인 글의 시작일을 미래로 옮기면 "그날까지 숨겨진다"를 따로 확인받는다. 예약 게시가 꺼진 게시판에서 시작일을 바꿀 때는 오늘 이전만 받는다(같은 값을 다시 보내는 것은 변경이 아니다, D3). 이미 예약된 글은 오늘로 당겨 바로 공개할 수 있다. 종료일 편집은 예약 설정과 무관하다.
- 선택 처리(현재 페이지): 상단 고정·고정 해제·종료일 변경·종료일 해제. 오늘 이전 종료일은 받지 않는다(바로 내리기는 범위 밖). 서버가 모든 대상을 다시 판정하고 하나라도 맞지 않으면 전체를 적용하지 않는다. 고정 상한을 넘으면 거부한다.
- 본문·첨부 편집은 기존 작성 화면에서 한다. 이용 화면에는 운영 도구를 섞지 않는다.

### 5.5 운영 화면: 설정 탭

- 위에 고정 제약을 둔다. 공지·FAQ 지정이면 두 편집 권한이 필요하고, 공개 FAQ는 비밀글이 아닌 글만 싣는다(로그인 필요). Q&A 게시판이면 비밀 문의와 공개 질문이 섞여 있다고 알린다.
- 기본: 이름·소개·게시판 사용. 화면 유형과 커뮤니티 귀속은 읽기 전용이다.
- 참여·첨부(현행): 댓글·만족도·첨부·파일 수·파일당 크기. 끄면 새 입력만 막고 기존 내용은 유지한다.
- 새 설정(해당 배치 구현 뒤): 예약 게시, 상단 고정(상한·기본 일수), 비밀글 정책, 추천 사용. 항목마다 "기존 게시판 기본값"을 적는다. 예약 게시를 켤 때는 기록용 미래 시작일 글이 "전환 진단 대상"이며 설정으로는 바뀌지 않는다고 알린다.
- 저장: "변경 n건 · 변경 취소 · 변경 내용 확인" 순으로 진행한다. 확인 표에 항목·현재·변경 후·영향을 보이고, 버전 충돌이면 최신 값과 비교한다. 이동 전 미저장 확인을 둔다(DEC-OPS-188).
- 변경 이력 대화상자(D9)와 영구 삭제 절차를 둔다.

### 5.6 운영 화면: 메뉴·접근 탭

> [2026-10-26] 이 절의 마법사 메뉴 단계·결과 화면 순서·메뉴 경로 인계 범위와 D8의 공개 준비 통과 기준은 [ADR-0043](decisions/ADR-0043-board-publish-flow-and-designated-boards.md)이 대체했다. 아래 원문은 당시 결정 기록으로 둔다.

- 공개 준비 점검(D8)을 둔다. 대상을 고른 상태로 메뉴 관리를 여는 것은 연결된 메뉴가 있는 행뿐이다(target-handoff `menu-focus`). "연결 없음" 행은 메뉴 관리의 새 메뉴 추가로 안내하고, 등록할 게시판 주소를 복사할 수 있게 보인다. 이 주소에는 쿼리가 들어 있어 화면 인계로 넘기지 않으며, `isHandOffScreenRoute`는 넓히지 않는다. 편집 권한 배정 항목은 인계 없이 권한 화면 링크만 둔다.
- 메뉴 연결 표: 메뉴 위치 / 연결 근거(게시판 주소·허브 탭, 경로) / 메뉴 상태 / 메뉴가 보이는 그룹(또는 확인 권한 없음) / 고치는 곳.
- 게시글 권한 표(모든 게시판 공통): 글 보기 · 공개 FAQ 보기(지정 게시판) · 글 쓰기 · 내 글 고치기·지우기 · 남의 글 고치기·지우기 · 비밀글·종료 글 보기 · 삭제 글 보기(상세만) · 추천 · 댓글 보기·쓰기 · 상단 고정. 행마다 필요한 권한, 기본 배정 그룹, 이 게시판의 추가 조건을 적는다. 추가 조건은 지정 게시판의 편집 권한, 커뮤니티 승인 회원, 게시 기간, 사용 여부다.
- 안내: "게시판별로 이용자를 나누는 수단은 커뮤니티 귀속 하나뿐입니다."

### 5.7 문구·접근성

- 용어: 게시판 사용 / 사용 안 함, 상단 고정(공지·필독과 구분), 게시 중 / 예약 / 게시 종료, 확인 권한 없음, 확인 불가를 쓴다. 동작 단추는 대상을 밝힌다(예: "사용 상태 바꾸기", "고정하기", "종료일 바꾸기", "일정·고정 저장"). "적용"처럼 대상 없는 말은 쓰지 않는다.
- 탭은 `StandardTabs`, 확인은 화면 안 대화상자로 한다. 오류는 필드와 연결하고 고정 노드의 라이브 영역에 알린다. 키보드만으로 생성·설정·선택 처리·취소를 끝낼 수 있어야 한다.

## 7. 구현 배치와 검증

각 배치는 AGENTS.md의 범위별 최소 검증을 따른다. 갱신 순서는 다음과 같다.

1. 원장을 손으로 편집한다(URL 상태 승인 부류·routeKeyBindings, gates.json 게이트 등록 포함).
2. 백엔드를 바꿨으면 `api-docs.json`을 절대 경로로 추출한다.
3. `npm run regen`을 실행한다.
4. 메뉴 SQL이나 기본 배정이 바뀌었으면 `npm run project:menus:refresh` 뒤 `npm run regen`을 한 번 더 실행한다.
5. regen 밖의 수치와 레코드를 손으로 맞춘다: operation census, 폼 census, IA 처분 레코드와 해시. URL 승인 해시는 regen이 다시 결속한다.
6. 표·시퀀스·표준 용어 행을 바꾼 배치는 같은 변경에서 `config/modules/core.json` `databaseSnapshot`을 DB 생성기 실측으로 갱신한다. 대상은 source의 "through V2_NNN", checkedAt, physicalTableCountExcludingFlyway, physicalSequenceCount, metaRows.meta_standard_terms다(base:census와 DB 생성기가 대조한다. CMS #961 선례).
7. api-server에 board 타입을 참조하는 파일(컨트롤러·DTO·시험)을 새로 두거나 옮긴 배치는 생성기 정밀 점검 실측으로 core·survey·approval의 `expected.javaCascade`를 같은 변경에서 갱신한다. 그 파일이 게이트 시험이면 `expected.gates`와 사유도 갱신한다.

구현 결정(2026-10-23, 착수 전 조사 반영):
- **판정 경계 세 가지.**
  - 엄격(`assertActiveBoardMaster`): 업무 홈 카드, 통계, 통합 검색, 공개 FAQ가 쓴다.
  - 열람(`loadReadableMaster`, `BOARD_READ_ALL`이 사용 여부를 면제): 목록·상세·메타가 쓴다.
  - 쓰기(`loadWritableMaster` = 지정 게시판 편집 가드 → 열람 판정): 쓰기 8곳이 쓴다.
- **댓글·만족도 경계.**
  - 엄격 `assertCommentAccess`: 댓글 등록·수정·삭제, 만족도 등록, 추천.
  - 열람 `assertCommentReadAccess`: 댓글 목록, 만족도 목록·평균, 만족도 수정·삭제.
  - 만족도 수정·삭제에 쓰기 판정을 쓰지 않는 것은 지정 게시판 편집 가드가 일반 사용자의 '내 평가 수정'을 새로 막기 때문이다(H3).
- **논리 삭제 글:** 수정·삭제·해결 표시를 거부한다(404).
- **게시판 ID 대조:** 파일 경로의 경로·본문 게시판 ID가 다르면 400이다.
- **메타:** 사용 상태(`inUse`)를 싣는다. 운영자가 사용 안 함 게시판 글을 열면 댓글·평가·추천 입력을 감춘다.
- **수정 요청:** 생성과 나눈 전용 DTO다. 버전은 필수이고, `tmpltId`·유형·속성 코드·커뮤니티 귀속은 받지 않는다(모르는 필드는 400).
- **선택지 API:** 모든 이용 화면이 하나를 쓴다. 관리자 분기와 시드 폴백을 걷는다.
- **응답 위치:** 선택지 응답과 수정 요청은 business-app에 둔다. 시작 구성의 Java 연쇄는 바뀌지 않는다.
- **허브 탭 대응:** 허브 셸 탭과 게시판의 대응은 탭 해석 모듈이 아닌 중립 모듈(`knowledge-tab-boards.ts`)로 꺼내 허브와 운영 화면이 함께 쓴다.

구현 기록(2026-10-23):
- **단건 비활성화(H3 판정):** 화면은 목록의 일괄 사용 상태 변경(`BBS_MST_UPDATE`)과 설정 탭의 사용 여부 저장으로만 끈다. 서버 `DELETE …/board-masters/{bbsId}`(`BBS_MST_DELETE`)는 API 소비자를 위해 남긴다. 이미 사용 안 함이면 아무것도 바꾸지 않고, 바꾸면 이력과 버전을 남긴다. 두 전이의 권한은 통일하지 않는다. 통일하면 기존 그룹 배정의 의미가 바뀐다. 화면이 부르지 않는 서비스 메서드는 걷고 operation 원장에 대체된 표면으로 적었다.
- **일괄 영구 삭제:** 목록 툴바에서 걷었다. 영구 삭제는 설정 탭의 한 건 절차(삭제 가능 판정 뒤 `…/physical`)다. 서버 일괄 경로도 대체된 표면으로 남긴다. 단건·일괄 영구 삭제 핸들러는 민감 작업 원장(`@SensitiveOperation`)에 남는다(결정 9).
- **설정 탭의 폼 그릇(A3-1):** 탭 본문이 곧 편집 면이라 모달이 아니라 인라인 폼이다. 저장 전에 항목·현재·변경 후·영향을 보이는 확인 대화상자를 거친다. 파일당 크기 0은 전역 상한을 따른다는 뜻이다.
- **이력 표:** `tb_bbs_chg_hstry`(V2_139)는 추가 전용이고 식별 시퀀스는 표가 소유한다. 같은 값으로 저장하면 이력도 버전도 바뀌지 않는다. 비어 있는(NULL) 옛 값과 뜻이 같은 요청값(소개 `''`, 파일당 크기 0 이하, 답글 허용 N)도 저장값을 그대로 둔다 — 설정 탭이 건드리지 않은 칸을 정규화해 보내도 이력이 쌓이지 않는다. 원본 스키마 실측(`core.json` databaseSnapshot)은 격리 PostgreSQL 17에서 V2_139까지 다시 쟀다(표 98·시퀀스 62·독립 시퀀스 6, 메뉴 스냅숏 변화 없음).
- **메시지 번들 하한:** 설정 수정 요청이 Bean Validation 참조 5개를 더해 실측이 19가 됐다. 게시판을 걷는 투영은 10개를 내리므로 원본 하한을 15로 올려 여유 폭 4를 그대로 둔다.
- **UI 품질 실행기:** 합성 게시판 흐름을 새 4단계 제목과 생성 직후 상태(게시판·메뉴 모두 사용 안 함)로 맞췄다. 읽기 되돌림은 사용 여부 조건 없이 전체를 조회한다.
- **게시판 목록의 기본 게시판:** `bbsId` 없이 들어오면 선택지 API 의 첫 게시판을 쓴다(관리 목록 API 는 일반 사용자에게 403 이라 늘 공지 게시판으로 떨어졌다). 선택지가 비거나 받지 못하면 공지 게시판 ID 로 가고, 본 조회가 그 게시판의 실제 상태를 보인다.
- **캐시:** 설정 저장·일괄 사용 상태 변경·영구 삭제 뒤에는 게시판 관리 뿌리 키 전체(목록·상세·이용 화면 메타·선택지·변경 이력)와 커뮤니티 상세의 귀속 게시판 목록을 다시 읽는다. 영구 삭제는 지운 게시판의 상세를 먼저 캐시에서 빼, 열린 운영 화면이 그 게시판을 다시 읽지 않게 한다.
- **영구 삭제 원장:** 핸들러 표지는 누가·언제를 남기고, 서비스가 같은 트랜잭션에서 지운 게시판마다 대상(`BOARD_MASTER_PURGE`, 게시판 ID)을 남긴다. 원장 기록이 실패하면 삭제도 되돌아간다.
- **첨부의 소유 근거:** 사용 안 함 게시판에서는 작성자의 소유 근거도 닫는다(D1 기각 ②). 작성자는 자기 첨부를 받거나 지우지 못하고, 조회 대행 권한자와 파일 관리자만 연다.
- **권한 표:** 메뉴·접근 탭의 게시글 권한은 동작마다 모두 필요한 권한(엔드포인트 권한과 대행 권한)과 서버 판정의 추가 조건(지정 게시판 편집, 커뮤니티 회원, 사용 여부의 운영자 예외, 글 열람)을 적는다. 기간 조건은 게시 종료일만이다 — 시작일 집행은 B1 이다.
- **사용처:** 사용 안 함으로 바꾸기 전 확인은 지정 용도, 지식 허브 탭(기여 탭은 그 기능을 넣은 구성에서라고 조건을 붙인다), 도움말 센터의 질의응답·1:1 문의를 알린다.
- **남은 경계:** 직접 SQL 로 넣은 NULL 댓글·만족도 설정은 화면이 받음으로 보이고 저장하면 받음으로 바뀐다(V2_109 이후 앱 경로로는 생기지 않는다). 설정 탭은 건드리지 않은 첨부 수·크기도 화면 상한(20개·10MB)으로 다시 검사해, API 로 상한 밖 값을 넣은 게시판은 다른 항목을 저장하려면 그 값을 먼저 맞춰야 한다(종전 편집 창과 같다). 작성 화면은 `bbsId` 없이 들어오면 공지 게시판 작성으로 간다.

착수 전 진단(공유 OCI 읽기 집계): 게시글 378건 가운데 `version` NULL 0, 작성일 NULL 0, 답글 0, 시작일·종료일을 가진 글 0, 형식 오류 0, 시작>종료 0이다. 그래서 게시글 `version`의 보정·`NOT NULL` 전환은 하지 않는다(D10 의 조건부 승인 대상이 생기지 않았다). 다른 환경에 NULL 행이 있으면 그 글의 작성 화면 수정·운영 일정 변경(단건·일괄)은 400(INVALID_STATE, "버전 정보가 없는 옛 글")으로 막힌다(fail-closed) — 저장하면 Hibernate 가 NULL 버전을 올리지 못하므로 판정 단계에서 거절한다. 도입 기관은 `tb_bbs_item.version IS NULL` 을 진단해 보정한다(§9). 이 경로 밖의 기존 쓰기(삭제·해결 표시)는 이 판정 전부터 같은 행에서 실패한다.

- **쓰기 규칙:** 등록·답글(파일 포함)은 업로드·채번 전에 예약 미허용 미래 시작일을 거부한다. 수정은 파일 처리 전에 버전(없으면 400, 다르면 409) → 공개 뒤 시작일 변경 자격(403) → 예약 허용(400) → 합친 기간 순서(400) 순으로 본다. 작성 경로의 빈 날짜는 저장값을 지우지 않는다(종전에는 지웠다). 운영 단건은 해제를 받지 않고 오늘보다 이른 종료일을 거부한다 — 해제는 일괄 `CLEAR_END` 만이다(작성 화면 경로는 종전대로 과거 종료일을 받는다). 일괄은 모든 대상을 먼저 판정해 하나라도 어긋나면 전체를 적용하지 않고, 뜻이 같은 값인 글은 건너뛴다(이력·버전 그대로).

DB 는 `NOT NULL DEFAULT 'N'` 이다.

- **원장·하한:** 인가 원장에 엔드포인트·바인딩·서비스 가드·수동 가드(공개 뒤 시작일 변경, 고정 판정, 추천 취소의 필수·금지 토큰)를 더했다. 입력 계약 원장은 바인딩 합과 같게 올렸다. 메시지 번들 하한은 29 다(실측 33, 여유 폭 4 — 앞선 실측 기록의 2 차이는 시험 주석에 정정했다). PG 통합 시험(정렬·고정 상한 경합·동시 추천 취소)은 게시판 소유 게이트로 등록했다.

### B1~B3 구현 기록(2026-10-23, 화면)

- **게시 상태 표지:** 화면은 오늘을 계산하지 않는다(DEC-OPS-140) — 브라우저 날짜로 '게시 종료' 를 그리던 표지를 걷고 서버 `postingStatus` 로 예약·게시 종료를 그린다(목록·상세·업무 홈 카드). 고정 표지도 서버 `pinned` 만 따른다.

- **운영 게시물 탭:** 조회 조건(제목·게시 상태·상단 고정)은 URL 밖 상태이고 `조회`·Enter 로만 적용한다. 일정 바꾸기와 고정 바꾸기는 권한이 달라 대화상자를 나눴다(`BOARD_UPDATE_ALL`·`BOARD_PIN`, 지정 게시판이면 편집 권한도 — 판정 리터럴은 이 화면 파일에 둔다). 선택 처리는 종료일 바꾸기·해제와 고정·해제이고 서버가 전체를 다시 판정한다. 고정을 받지 않는 게시판에서는 해제만 연다. 조건이 바뀌어 선택이 풀리면 알린다. 공용 표에 선택 범위(`selectionScope`)를 opt-in 으로 더해 PR E2E 가 전수가 된다.

- **통계 이름(D3):** '오늘 등록된 글', '전체 등록 건수', 계열 이름 '등록(작성일 기준)' 이다. 집계 질의는 바꾸지 않았다.
- **원장:** operation 수 431, 화면 쓰기 권한 표시 부채(`ungatedWriteMax`)는 추천 단추가 권한을 보게 되어 39 → 37 로 내렸다. 폼 census·라우트 기능 원장(상세 라우트는 동결 목록이라 그대로, 게시글 목록 라우트의 추천에 `unlike`)·정직성 계약(시작일 집행·예약 설정·추천 꺼짐과 취소·필수 비밀글 짝)을 함께 갱신했다. 옛 정직성 계약이 새 서버에 red 임을 먼저 확인한 뒤 바꿨다.
- **남은 경계:** 업무 홈 카드에는 고정 표지를 두지 않았다(정렬은 서버가 고정 글을 앞에 둔다). 운영 화면의 일정·고정 변경 뒤 업무 홈 조회는 무효화하지 않고 캐시 수명에 맡긴다. 목록에서는 내 추천을 거둘 수 없다.

### 공통 수용 시나리오

> [2026-10-26] 1·2번의 메뉴 부분은 [ADR-0043](decisions/ADR-0043-board-publish-flow-and-designated-boards.md) 결정 1·2가 대체했다 — 마법사는 메뉴를 만들지 않고, 메뉴는 결과 화면·메뉴·접근 탭의 '메뉴에 붙이기'로 메뉴 관리에서 붙인다. 2번은 '생성 결과를 모를 때 다시 만들지 않고 방금 만든 게시판을 찾아 이어 간다'로 읽는다. 아래 원문은 당시 기록으로 둔다.

시나리오의 운영자는 게시판·커뮤니티 운영 묶음(B2 뒤에는 `BOARD_PIN` 포함)을 받은 사용자다. 1·2·4번은 메뉴·권한 관리 권한(`MENU_READ`·`MENU_CREATE`·`MENU_UPDATE`·`AUTHRT_READ`·`AUTHRT_GRANT`, 기본 `ROLE_ADMIN`)도 가진 경우에 해당한다.

1. 운영자가 새 자료실을 만들고, 다시 검색하지 않고 메뉴·접근 탭에서 공개 준비를 끝낸다.
2. 메뉴 등록 실패 뒤 다시 시도해도 게시판과 메뉴가 중복되지 않는다.
3. 사용 안 함 게시판에는 이용자가 주소로도 글을 쓸 수 없다. 운영자는 목록을 보고 정리한다.
4. 관리자 그룹에만 보이는 메뉴는 공개 준비 점검을 통과하지 않는다.
5. 예약 글은 목록·검색·FAQ·첨부·댓글 어디서도 미리 보이지 않고, 공개일에 목록 위쪽에 나온다.
6. 작성자가 공개된 글의 시작일을 바꿔 목록을 올릴 수 없다.
7. 고정 글은 상한을 넘지 않고, 종료일이 지나면 일반 정렬로 돌아간다.
8. 설정을 동시에 저장하면 뒤 저장이 409를 받고 최신 값과 비교한다.
9. 기능을 꺼도 기존 비밀글·댓글·첨부·추천 집계는 유지된다.
10. 키보드만으로 생성·설정·선택 처리·취소를 끝낸다.

사용성 측정(완료율·오류·소요 시간)은 운영자 표본과 현행 기준값을 정할 수 있을 때 따로 계획한다. 측정 전에는 개선 수치를 적지 않는다.

## 9. 남은 위험과 경계

- 게시판별 접근 권한은 이번 범위 밖이다. "특정 그룹에만 여는 게시판"은 커뮤니티 귀속 외에는 만들 수 없다.
- 예약 집행은 환경마다 기존 데이터를 진단한다. 공유 OCI는 2026-10-23 결정대로 보정 없이 집행하므로 기록용 미래 시작일 글은 시작일까지 작성자·조회 대행 권한자에게만 보인다. 도입 기관은 자기 환경의 진단 결과로 보정 여부를 따로 정한다.
- 관리 센터 통계는 작성일 기준 등록 건수(요약 카드는 전체 등록 건수)라 예약·비밀·사용 안 함 게시판 글을 센다. 수만 드러나며, 화면 이름으로 의미를 밝힌다.
- 게시판·커뮤니티 운영 묶음에는 메뉴·권한 관리 권한(`MENU_*`·`AUTHRT_*`)이 없다. 2026-10-26부터 마법사는 게시판 만들기(`BBS_MST_CREATE`)만 요구하므로([ADR-0043](decisions/ADR-0043-board-publish-flow-and-designated-boards.md) 결정 1) 그 묶음으로 게시판을 만들고 사용으로 바꿀 수 있지만, 메뉴에 붙이기와 일반 그룹 표시는 메뉴·권한 담당자에게 요청해야 한다. 묶음 구성 변경은 별도 결정 대상이다.
- 본문 서버 정제가 없는 상태는 그대로다. 방어선은 렌더 시점 정제다. 서버 정제 도입은 C1 이후의 별도 결정이다.
- 도움말 1:1 문의의 평문 본문이 HTML 렌더러로 그려지는 문제는 남는다(C1에서 함께 처분).
- 신규 표준 용어 6건의 공유 OCI 적용과 도입 기관 메타 일치는 환경마다 다시 확인한다.
- 게시글 `version` 은 NOT NULL 이 아니다. 도입 환경은 `tb_bbs_item.version IS NULL` 행을 진단하고, 있으면 보정·`NOT NULL` 전환을 승인받는다. 그 전까지 그 글의 수정·일정 변경은 400 으로 막힌다(§7 B1 구현 기록).
