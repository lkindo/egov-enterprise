# ADR-0060 — 토큰을 비대칭 키로 서명하고 Next 에는 공개키만 둔다

- 상태: Accepted
- 결정일: 2026-11-14
- 승인: 사용자가 2026-11-14 원점 평가의 개선점을 "모두 고쳐줘"라고 지시한 뒤, JWT 비대칭 서명은 "ADR부터 진행"을 골랐고, 초안의 전환 선택지 가운데 "A. 두 번 배포"를 골랐다.
- 구현 시점: Spring Boot 4.1.3 재기록 묶음. `api-server/src/main/resources/application.yml` 과 격리 E2E 실행기(`scripts/run-isolated-e2e.mjs`)가 여섯 DB 벤더 인증 증거의 입력이라, 그 묶음에서 증거를 다시 기록할 때 함께 넣는다. 그때까지 현재 HMAC 서명이 유효하다.

## 배경

- 백엔드 `JwtTokenProvider`(foundation)가 `JWT_SECRET` 하나로 접근 토큰(1시간)과 재발급 토큰(7일)을 HMAC 으로 서명한다. 재발급 토큰은 DB 에도 저장해 대조한다.
- Next 프록시(`frontend/src/proxy.ts`)도 같은 `JWT_SECRET` 으로 접근 토큰의 서명·만료·종류를 확인해 화면 이동을 거른다. 프록시가 비밀을 쓰는 곳은 이것뿐이다.
- 그래서 Next 서버를 침해하면 비밀이 새고, 그 비밀로 아무 사용자의 토큰이든 만들 수 있다. 백엔드도 그 토큰을 받는다(2026-11-14 원점 평가의 보안 지적).

## 결정

1. **서명 알고리즘은 ES256(P-256 ECDSA)** 이다. 백엔드(jjwt)와 Next Edge 런타임의 Web Crypto 가 모두 지원하고 서명이 짧다.
2. **키는 키링으로 준다.** MFA·주민번호 키링과 같은 꼴이다.
   - 백엔드: `JWT_SIGNING_ACTIVE_KID`, `JWT_SIGNING_KEYS_JSON`(`{"<kid>":"<PKCS#8 개인키 Base64>"}`).
   - Next: `JWT_VERIFY_KEYS_JSON`(`{"<kid>":"<SPKI 공개키 Base64>"}`). 개인키는 받지 않는다.
   - 토큰 머리의 `kid` 로 검증 키를 고른다. 모르는 `kid` 와 허용 밖 `alg`(none 포함)는 거부한다.
3. **키 교체 순서**: 새 키쌍을 만든다 → 새 공개키를 Next 에 먼저 더해 배포한다 → 백엔드의 활성 kid 를 새 키로 바꾼다 → 재발급 토큰 수명(7일)이 지나면 옛 키를 두 쪽에서 뺀다. 절차는 구현과 함께 [키 교체 런북](../../04-operations/crypto-key-rotation.md)에 더한다.
4. **운영 강제**: 운영 오버레이와 `scripts/deploy.sh` 사전 검증이 두 키링을 요구한다. 개발용 기본 키쌍은 저장소에 두되(지금의 개발용 HMAC 기본값과 같은 성격), 운영에서 그 키를 쓰면 기동을 멈춘다. 두 쪽은 공개키 지문(값 아님)을 로그에 남겨 설정이 맞는지 대조할 수 있게 한다.
5. **전환은 두 번 배포로 한다.**
   - 1차 배포: 백엔드는 새 토큰을 ES256 으로 발급하고, 옛 HMAC 토큰(접근·재발급)도 검증한다. Next 는 공개키로 검증하되 옛 HMAC 접근 토큰도 받는다. 사용자는 다시 로그인하지 않는다.
   - 2차 배포(1차 뒤 재발급 토큰 수명 7일 이상): 두 쪽 모두 HMAC 검증과 `JWT_SECRET` 을 뺀다. 이때부터 Next 에 서명 비밀이 없다.
   - 전환 기간 동안 Next 에는 HMAC 비밀이 남는다 — 이 위험은 최대 재발급 토큰 수명만큼으로 한정하고, 2차 배포를 미루지 않는다.

## 바뀌지 않는 것

- 토큰의 클레임·수명·세션 주기(session cycle)·재발급 토큰 DB 대조·MFA 단계는 그대로다.
- 인가 판정은 지금처럼 백엔드가 한다. 프록시의 확인은 화면 이동을 거르는 앞단이다.

## 검증 계획

- 백엔드: ES256 발급·검증, 모르는 kid·alg 거부, 전환 기간의 HMAC 수용과 2차 배포 뒤 HMAC 거부의 단위 시험.
- Next: 공개키 검증, 프런트 환경 변수에 개인키가 없음을 보는 계약, Edge 런타임 Web Crypto 검증 시험.
- 운영: 설정 안전 린터·운영 오버레이 계약·`deploy.sh` 사전 검증의 부정 시험, 운영 오버레이로 로그인·재발급하는 릴리스 스모크.
- E2E: 격리 E2E 실행기가 일회용 키쌍을 만들어 두 쪽에 준다.

## 위험

- 두 쪽 키 설정이 어긋나면 로그인한 화면 이동이 모두 로그인 화면으로 돌아간다 — 공개키 지문 로그와 배포 사전 검증으로 막는다.
- 개인키를 잃으면 새 토큰을 만들 수 없다(이미 발급한 토큰은 수명까지 유효). 개인키는 MFA 키처럼 백업한다.
