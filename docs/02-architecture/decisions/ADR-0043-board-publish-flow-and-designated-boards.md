# ADR-0043 — 게시판 공개 동선: 메뉴와 분리한 생성, 공개 준비 기준, 지정 게시판 보호, 화면 유형 이름

- 상태: Accepted
- 결정일: 2026-10-26
- 승인: 2026-10-26 사용자가 게시판 메뉴·프로세스·운영 UX 분석 보고서의 결정 카드 D-1~D-5를 "권고대로 진행"으로 승인했다. 같은 지시로 0차(결함 수정)와 1차(편의 보강)를 이어서 진행한다. 2차(안내문 컬럼, 이용자용 게시판 목록 메뉴 등 스키마·메뉴 데이터 변경)와 3차(인가·데이터 의미 변경)는 대상과 건수를 확정한 뒤 따로 승인받는다.
- 대체: [ADR-0040](ADR-0040-board-operations-management.md) 결정 8의 "공개 준비는 일반 그룹에 보이는 활성 메뉴가 있어야 통과한다"(→ 결정 3). [설계서](../board-management-expansion-design.md) §5.3의 마법사 3단계 '메뉴·접근 확인'(메뉴 위치·이름·순서 입력과 `MENU_CREATE`·`MENU_READ` 요구), 결과 화면의 남은 일 순서, 수용 시나리오 1·2의 메뉴 부분(→ 결정 1·2). §5.6의 "isHandOffScreenRoute는 넓히지 않는다" 가운데 메뉴 경로 인계(→ 결정 1). [DEC-OPS-332](../../archived/operational-decisions-history.md#dec-ops-332) ②의 "목록은 코드와 템플릿이 정본의 짝일 때만 이름을, 아니면 저장된 코드를 보인다"(→ 결정 5).

## 배경

게시판 기능을 6개 관점으로 분석하고 적대적으로 검증했다. ADR-0040의 운영 화면·예약·고정·변경 이력은 설계대로 동작한다. 그러나 공개까지의 동선과 지정 게시판 보호에 다음 문제가 있었다.

- 마법사가 게시판 생성(`BBS_MST_CREATE`)과 메뉴 등록(`MENU_CREATE`·`MENU_READ`)을 한 제출로 묶었다. 그래서 '게시판·커뮤니티 운영' 묶음만 받은 담당자는 게시판을 하나도 만들 수 없다. 메뉴 등록은 구조 저장이 아닌 옛 단건 등록이라 버전 대조·3단계 제한·민감 작업 원장을 거치지 않는다. 상위 메뉴 후보가 고정값 셋이라 메뉴를 고친 기관이나 축소 구성에서는 게시판만 만들어지고 메뉴 등록이 실패한다.
- 메뉴는 접근을 막지 않는다(ADR-0040 §3.1). 사용 중인 게시판은 메뉴가 없어도 주소·통합 검색·허브 탭·업무 홈 카드로 열린다. 그런데 공개 준비 점검은 일반 그룹 메뉴만 세어, 이미 모두에게 열린 업무게시판을 '통과 못함'으로, 커뮤니티 귀속 게시판을 영원히 '통과 못함'으로 판정했다.
- 앱이 ID로 직접 쓰는 게시판(공지·FAQ·업무·Q&A·위키) 가운데 서버가 아는 것은 공지·FAQ·업무뿐이다. 영구 삭제는 어떤 지정 게시판도 막지 않아, 글이 없는 새 설치 환경에서는 업무 홈 카드·공개 FAQ·도움말 1:1 문의·지식 허브 탭이 쓰는 게시판을 지울 수 있다.
- 화면 유형을 실제로 정하는 값은 템플릿(`tmplt_id`)인데, 목록은 유형 코드와 템플릿이 정본 짝일 때만 이름을 보여 주요 시드 게시판이 'BBST01' 같은 코드로 보였다.

## 결정

1. **게시판 생성과 메뉴 연결을 나눈다(D-1).** 마법사는 게시판만 만들고 `BBS_MST_CREATE`만 요구한다. 마법사의 메뉴 단계와 옛 단건 메뉴 등록 호출을 걷는다. 메뉴는 결과 화면과 운영 화면 메뉴·접근 탭의 '메뉴에 붙이기'로 메뉴 관리에 넘긴다. 이 인계는 게시판 이용 화면 주소(식별자 쿼리 `bbsId`)와 이름, 돌아갈 곳을 싣고, 메뉴 관리는 새 메뉴 위치 고르기 대화상자를 연다. 메뉴 저장은 메뉴 관리의 구조 저장이 그대로 권한(`MENU_CREATE`·`MENU_UPDATE`, 그룹 표시는 `AUTHRT_GRANT`)을 집행한다. 화면 인계는 식별자 문자(영문·숫자·`_`·`-`)로 된 쿼리 쌍만 셋까지 받고 자유 입력은 싣지 않는다. 메뉴 관리는 게시판 코드를 모른다. 커뮤니티 귀속 게시판은 메뉴 안내를 건너뛴다(입구는 커뮤니티 화면이다).
2. **공개는 '사용 전환'으로 한다(D-2).** 게시판은 지금처럼 사용 안 함으로 만든다(ADR-0040 결정 1 유지). 마법사 결과 화면에 '지금 사용으로 바꾸기'를 둔다. 이 동작은 기존 사용 상태 바꾸기 경로(`BBS_MST_UPDATE`, 변경 이력·버전)를 쓰고, 권한이 없으면 단추 대신 요청 안내를 보인다. 결과 화면의 남은 일은 '글 준비 → 사용 전환 → (선택) 메뉴에 붙이기' 순서다. 아티팩트 시안의 '만들 때 바로 사용' 선택은 두지 않는다.
3. **공개 준비 점검의 기준을 '사용 중 + 이용자가 찾는 길 하나 이상'으로 바꾼다(D-3).** 찾는 길은 일반 그룹에 보이는 활성 메뉴, 지식 허브 탭, 업무 홈 카드, 사용 중인 커뮤니티 화면(귀속 게시판)이다. 관리자 그룹(`ROLE_ADMIN`·`ROLE_SYSTEM`)에만 보이는 메뉴는 여전히 찾는 길로 세지 않는다(ADR-0040 수용 시나리오 4 유지). 메뉴·그룹·커뮤니티를 판정할 수 없으면 확인 불가로 끝나고 통과로 추정하지 않는다. 귀속 커뮤니티가 사용 중지면 입구가 없다. 판정에 쓰는 커뮤니티 이름·사용 여부는 커뮤니티 기능이 foundation 포트로 알려 주고, 기능이 없으면 확인 불가다. 이용자용 게시판 목록(디렉터리)은 메뉴 데이터 승인 뒤(2차) 찾는 길에 더한다. ADR-0040 결정 8의 다른 항목인 '공지·FAQ 지정 게시판은 그 편집 권한(`NOTICE_EDIT`·`FAQ_EDIT`)이 어느 그룹엔가 배정돼 있어야 한다'는 그대로 둔다 — 바꾸는 것은 메뉴 항목뿐이다.
4. **지정 게시판의 영구 삭제를 서버가 거부한다(D-4).** 지정 용도에 Q&A(도움말 1:1 문의·지식 허브 질의응답)와 위키(지식 허브 위키 탭)를 더하고 서버 설정(`nuri.boards.qna-id`·`wiki-id`)으로 둔다. 기본값은 지금 화면 상수와 같다. 단건·일괄 영구 삭제는 지정 게시판이면 거부하고 사유를 알린다. 사용 안 함 전환은 지금처럼 허용하고 확인에서 사용처를 보인다. 화면 상수(`board-ids.ts`)와 서버 기본값이 같은지는 기존 계약 시험이 대조한다(과도기 가드 — 기관이 환경별로 바꾼 값은 서버 설정이 정본이다).
5. **화면 유형 이름을 템플릿 기준으로 보인다(D-5).** 이름은 실제 화면을 정하는 `tmplt_id`로 정한다. 내장 레이아웃이 아닌 값(예: `TMPLAT_BOARD_DEFAULT`)은 '기본 목록형(레이아웃 미지정)'으로 보인다. 유형 코드와 템플릿 짝이 정본과 다르면 이름 옆에 그 사실을 덧붙인다. 정본 표는 여전히 `board-types.ts` 하나다(DEC-OPS-332 ①·③·④ 유지). 생성 요청은 내장 레이아웃 7개의 템플릿만 받는다.

## 영향과 검증

- 공개까지의 화면 왕복이 '마법사 → 메뉴 관리 → 설정 탭'에서 '마법사 → 결과 화면의 사용 전환'으로 준다. 메뉴는 필요할 때 붙이고 메뉴 관리에서 돌아오는 단추로 운영 화면에 돌아온다.
- 마법사가 메뉴 단건 등록을 부르지 않으므로 그 화면 서비스 메서드를 걷고, `POST /api/v1/admin/system/menus`는 operation 소비 원장 축 1에 대체 표면(구조 저장)으로 등재한다. 화면 고아 래칫은 올리지 않는다(H2).
- 정직성 계약은 '마법사는 게시판을 사용 안 함으로 만든다'를 유지하고, 메뉴 생성 단언은 '메뉴를 만들지 않는다'로 바꾼다. 공개 준비 판정은 관리자 전용 메뉴·사용 중지 커뮤니티·판정 불가가 통과하지 않는다는 부정 시험으로 고정한다. 지정 게시판 영구 삭제 거부와 화면 상수·서버 기본값 대조는 변이를 되돌리면 실패하는지 확인한다.
- 스키마·메뉴 데이터 변경은 없다. 2차에서 이용자용 게시판 목록 메뉴, 위키·FAQ 메뉴 이름, 안내문 컬럼을 따로 승인받는다.
