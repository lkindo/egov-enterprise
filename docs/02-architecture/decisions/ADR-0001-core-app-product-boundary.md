# ADR-0001: 코어/앱 제품 경계와 배포 기준

- 상태: Accepted
- 결정일: 2026-08-15 (2026-08-16 생성 파이프라인 확정)
- 관련: `business-core`, `business-app`, `template/reusable-base`

## 맥락

이 저장소는 동작하는 전자정부 기능 참조판이면서 신규 SI의 시작점이다. 그러나 `business-core`에
선택 기능인 banner·popup·community·survey 구현 55파일과 해당 테스트 8파일이 남아 있어,
“코어는 항상 필요한 기반”이라는 모듈 이름과 실제 내용이 달랐다. 별도 `template/reusable-base`
브랜치는 이 기능을 제거했지만 2026-08-16 실측에서 현재 개발선보다 486커밋 뒤(고유 5커밋)에 있어 지속적인
배포 기준으로 삼으면 최근 보안·DB·게이트 수정이 누락된다.

## 결정 요인

- 신규 프로젝트가 유지해야 할 코어와 삭제 가능한 예제를 컴파일 경계로 구분해야 한다.
- 현재 API 경로, Java 패키지, DB 스키마와 데모 기능은 유지해야 한다.
- 장기 분기된 템플릿에 보안 수정을 반복 이식하는 운영 모델은 피해야 한다.
- 경계가 다시 흐려지는 것을 실행 가능한 테스트가 차단해야 한다.

## 검토한 대안

1. `business-core`에 샘플을 유지한다. 이동 비용은 없지만 코어의 의미와 삭제 가능성이 계속 어긋난다.
2. 샘플을 삭제하고 `template/reusable-base`만 공식 배포한다. 가장 작지만 데모를 잃고 장기 분기 드리프트가 남는다.
3. 샘플을 `business-app`으로 이동하고 현재 개발선을 단일 정본으로 유지한다.

## 결정

대안 3을 채택한다.

- `business-core`는 인증·인가·사용자·조직·메뉴·프로그램·코드·정책 등 필수 기반만 보유한다.
- banner·popup·community·survey는 선택 가능한 참조 기능으로 `business-app`에 둔다.
- 이동 시 Java 패키지, 공개 타입, API 경로와 DB 계약은 바꾸지 않는다.
- `ServiceLayerIsolationTest`가 이 샘플 패키지의 core 재유입을 차단한다. Gradle 의존 방향도
  `business-app → business-core`만 허용해 core→app 역참조를 컴파일 단계에서 막는다.
- 현재 개발선이 코드·보안 수정의 정본이다. `template/reusable-base`는 2026-07 정리 실험의
  역사 스냅샷으로 보존하되 최신 베이스로 안내하지 않는다.
- 신규 프로젝트용 base는 정확한 릴리스 태그에서 `core`·`collaboration`·`demo` 프로필 중 하나를
  선택해 생성한다. 프로필·도메인·물리 테이블·시퀀스의 SSOT는
  `config/reusable-base-profiles.json`이며, 장기 브랜치나 수동 삭제 목록을 정본으로 두지 않는다.
- DB baseline은 현재 versioned migration 전체를 일회용 PostgreSQL DB에 적용한 결과로 만들고,
  다른 빈 DB에 다시 적용해 테이블·시퀀스·표준 메타 행 수까지 검증한다. 운영·공유 DB를 축소하지 않는다.

## 결과

- 장점: 코어 경계가 물리적으로 성립하고, 데모 기능과 API는 그대로 유지된다. 보안 수정의 정본도 하나다.
- 비용: 프로필 매니페스트와 도메인 간 의존 경계를 지속해서 관리해야 하며, 새 선택 기능을 추가할 때
  소스·DB 소유권을 함께 등록해야 한다.
- 배포 조건: base는 깨끗한 `v*` 릴리스 태그에서만 공식 생성한다. 생성된 소스는 프로필 계약,
  Java 컴파일, 프런트 타입검사, harness, 실 PostgreSQL 스키마 검증을 통과해야 한다.
- 운영 원칙: base는 릴리스 산출물이며 장기 생존 브랜치로 수동 동기화하지 않는다.
