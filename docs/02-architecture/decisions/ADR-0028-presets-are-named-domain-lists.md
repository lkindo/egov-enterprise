# ADR-0028 — 시작 구성은 이름 붙은 기능 목록이고 같은 목록은 같은 결과를 낸다

- 상태: Accepted
- 결정일: 2026-10-13
- 승인 범위: 사용자 결정 DEC-OPS-256 ④(2026-10-10 — 시작 구성을 이름 붙은 기능 목록으로 바꾸고 pack 순위를 걷는다, ADR 로 확정)와
  2026-10-12 결정 U2(manifest 제거 경로 보정과 '같은 목록 = 같은 결과' 계약을 먼저 두고 해석기 단일화는 매니페스트 v2 에서)·
  U10(v1 에서 v2 로 일괄 전환)·U13(원장 pack 태그를 소유 파생 기대로, 시작 구성의 게이트·연쇄는 exact 목록으로)·
  U15(새 인증 시작 구성은 PR 에서 빼고 main·야간 시험에서 검증)
- 대체:
  - [ADR-0001](ADR-0001-core-app-product-boundary.md) 결정의 "신규 프로젝트용 base는 정확한 릴리스 태그에서 `core`·`collaboration`·`demo`
    프로필 중 하나를 선택해 생성한다. 프로필·도메인·물리 테이블·시퀀스의 SSOT는 `config/reusable-base-profiles.json`이며" 부분.
    정확한 릴리스 태그에서 공식 생성한다는 요건과 '장기 브랜치나 수동 삭제 목록을 정본으로 두지 않는다' 는 그대로다.

## 맥락

생성기는 시작 구성과 기능 직접 선택을 같은 해석기로 풀었지만(DEC-OPS-239) 소스 투영의 수단은 둘이었다. 시작 구성은 빠진 pack 의
`removePaths` 와 그 연쇄로, 직접 선택은 카탈로그의 기능 소유 경로와 그 연쇄로 지웠다. 두 수단이 같은 결과를 낸다는 보장은 없었고,
화면 생존 대조(DEC-OPS-265)는 남는 화면만 보므로 비화면 파일의 차이를 잡지 못했다.

2026-10-12 정밀 점검으로 시작 구성마다 같은 기능 목록의 직접 선택과 제거 집합을 대조했다. collaboration·demo 는 차이가 0 이었고 core
시작 구성만 프런트 파일 15개(410 대 425)를 덜 지웠다. 10단계 B4 가 문자 스키마와 게시판 시험을 기능 소유로 옮긴 뒤에는 19개였다.
리다이렉트 화면 2개를 빼면 게시판 디렉터리의 레이아웃·컴포넌트, 쪽지 레이아웃·오류 화면·폼 검증, 문자 폼 검증과 그 시험이었다.
앱 실행 경로에는 없었지만 시험은 core 생성물의 vitest 에서 계속 돌았다. Java·게이트 차이는 0 이었다.

차이의 근본 원인은 소유 선언이 한곳에 있지 않다는 것이었다. 기능의 소유는 v1 manifest(pack·순위·제거 경로·클러스터·프로필 승인)와
생성기 모듈의 코드 상수 여러 곳, 원장 셋의 pack 태그로 나뉘어 있었고, pack 모드와 직접 선택 모드가 열두 곳에서 갈렸다.

## 결정

1. 시작 구성은 [`config/modules/presets.json`](../../../config/modules/presets.json) 의 이름 붙은 기능 목록이다. 같은 기능 목록은
   시작 구성으로 고르든 직접 고르든 같은 결과를 낸다 — 해석된 구성(테이블·시퀀스·권한·메뉴·탭 숨김·외래 키·기능 저하·외부 요구)과
   소스 투영(Java·프런트·게이트·규칙 제거 집합)이 같다. 시작 구성의 이름은 구성 식별(레시피·해시·lock)과 커밋된 기대치에만 남는다.
   기대치는 게이트 승인·Java 연쇄·규칙 제거의 exact 목록과 CI 레이아웃(`ci`)이다. 수 래칫이 아니라 목록이라 교체도 붉다.
2. 계약이 이를 지킨다([preset 동치 계약](../../../scripts/project-composer-preset-equivalence.test.mjs)). 카탈로그의 시작 구성마다
   같은 목록을 직접 고른 구성과 해석 결과(식별 필드 제외)를 비교하고, 생성기와 같은 판정인 정밀 점검의 제거 집합을 양방향으로
   대조한다. 시작 구성 목록을 카탈로그에서 읽으므로 새 시작 구성도 대조를 받는다. 차이는 파일 이름으로 보고한다.
3. 투영 수단은 하나다. 시작 구성도 직접 선택과 같은 간선(화면 계열 포함)을 따르고, 화면 제외 경로를 기능 규칙에서 계산한다.
   생성기·정밀 점검과 관찰자(라우트 원장·도달성 census·CI 범위 분류·검토 범위·생성물 표지·수동 삭제)는 기능 소유로 투영하거나
   판정한다. 시작 구성 목록이 필수 의존 폐포에 닫혀 있는지는 카탈로그 적재가 검사한다 — 순위 검사는 없다.
4. 기능 소유의 정본은 [`config/modules`](../../../config/modules/) 하나다 — 기능 파일, 필수 기반 `core.json`, 시작 구성 `presets.json`.
   pack·순위·v1 manifest 는 없다. 횡단 게이트 원장은 소유를 적지 않고 기대 생존을 기능 소유에서 계산한다. 스크립트는 시작 구성
   이름을 열거하지 않고 `presets.json` 을 읽는다. 생성물에는 구성의 기능 파일과 활성 구성 하나가 남고, `presets.json` 의 `active`
   가 생성물 표지다.
5. 새 시작 구성은 같은 규칙으로 더한다. 기능 목록과 표시 이름을 적고, 기대치는 실제 생성으로 정한다. '공통 기반 + 설문'(`survey`)과
   '공통 기반 + 결재'(`approval`)가 그렇게 들어왔다(DEC-OPS-295). 두 시작 구성은 PR CI 에서 빼고(`ci.pr` 이 null) main 의 두 레이아웃과
   야간 시험(T2)에서 돈다(DEC-OPS-296). `custom` 은 직접 선택 구성의 이름이라 시작 구성 id 로 쓸 수 없다.

## 결과

- 시작 구성은 자주 쓰는 목록에 붙인 이름이다. 지금 `core` ⊂ `collaboration` ⊂ `demo` 는 포함 관계지만 그것은 규칙이 아니다.
  `survey`·`approval` 은 `collaboration` 을 포함하지 않는다.
- ADR-0001 이 '비용' 으로 적은 프로필 매니페스트 관리는 기능 파일 관리가 된다. 새 기능은 기능 파일 하나를 더한다. 코드에서
  계산하는 사실(Java 참조 간선·이벤트·포트 연동·외래 키·메뉴)은 적지 않고, 카탈로그가 선언과 양방향으로 대조한다.
- 구성 해시가 바뀐다(카탈로그의 원천이 `config/modules` 다). 로컬 DB 번들은 다시 만든다.

## 검증과 한계

- 첫 판(10단계 13a, DEC-OPS-285)은 collaboration pack 의 제거 경로에 게시판·쪽지·문자 화면 디렉터리 셋을 더해 차이를 없앴다.
  변경 전 트리에서 계약이 core 프런트 19개를 이름으로 지목했다. 매니페스트 v2(11단계 C1~C8, DEC-OPS-288~294)가 투영 수단을 하나로
  합쳐 그 보정은 필요가 없어졌고, 전환(C7, DEC-OPS-294)이 v1 manifest 와 생성기 상수를 걷었다. 전환 단계마다 29개 구성(시작 구성 3,
  단독 22, 빈 선택, 대표 직접 선택, 전체)의 정밀 점검 파일 목록을 기준선과 대조했다.
- 2026-10-13 측정: 시작 구성 5개와 단독 선택 22개의 정밀 점검 차단 0. core 시작 구성은 Java 545·프런트 456개 파일과 게이트 13개를
  지우고, 같은 목록의 직접 선택과 같다.
- 계약은 생성 전 판정(정밀 점검)까지 본다. 생성물의 DB 번들·하네스·시험은 CI 재사용 잡과 야간 시험(T2)이 본다.
- 계약은 정밀 점검을 시작 구성마다 두 번 돌려 운영 계약 시간이 는다. 별도 파일이라 다른 계약과 병렬로 돈다.
