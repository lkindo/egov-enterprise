# ADR-0028 — 시작 구성은 이름 붙은 기능 목록이고 같은 목록은 같은 결과를 낸다

- 상태: Accepted
- 결정일: 2026-10-13
- 승인 범위: 사용자 결정 DEC-OPS-256 ④(2026-10-10 — 시작 구성을 이름 붙은 기능 목록으로 바꾸고 pack 순위를 걷는다, ADR 로 확정)와
  2026-10-12 결정 U2(이번 단계는 manifest 제거 경로 보정 + '같은 목록 = 같은 결과' 계약 + 이 ADR, 해석기 단일화는 매니페스트 v2)
- 대체: 이번 단계에는 없다. 결정 4 의 매니페스트 v2 가 끝나면 [ADR-0001](ADR-0001-core-app-product-boundary.md) 결정의
  '`core`·`collaboration`·`demo` 프로필 중 하나를 선택해 생성한다'와 '프로필·도메인·물리 테이블·시퀀스의 SSOT 는
  `config/reusable-base-profiles.json`' 문장, [ADR-0020](ADR-0020-selectable-reusable-backend-layouts.md) '검증과 후속 범위'의
  '누적 프로필' 언급을 대체한다. 그 단계의 기록이 확정한다
- 관련: [ADR-0027](ADR-0027-ci-reusable-admission-layout-and-nightly.md), [선택형 프로젝트 생성기 설계](../project-composer-design.md),
  [생성기 가이드](../../03-guides/project-composer-guide.md), [재사용 가이드](../../03-guides/reusable-base-guide.md)

## 맥락

생성기는 시작 구성(`core`·`collaboration`·`demo`)과 기능 직접 선택을 같은 해석기로 푼다(DEC-OPS-239). 그러나 소스 투영의 수단은
둘이다. 시작 구성은 빠진 pack 의 `removePaths` 와 그 연쇄로, 직접 선택은 카탈로그의 기능 소유 경로와 그 연쇄로 지운다. 두 수단이
같은 결과를 낸다는 보장은 없었다. 화면 생존 대조(DEC-OPS-265)는 남는 화면만 보므로 비화면 파일의 차이를 잡지 못한다.

2026-10-12 정밀 점검으로 시작 구성마다 같은 기능 목록의 직접 선택과 제거 집합을 대조했다. collaboration·demo 는 차이가 0 이었고,
core 시작 구성만 프런트 파일 15개를 덜 지웠다. 10단계 B4 가 문자 스키마와 게시판 시험을 기능 소유 디렉터리로 옮긴 뒤에는 19개였다.
그중 리다이렉트 화면 2개(`/admin/community/boards/[id]`·`/write`)는 거버넌스 투영이 생성물에서 이미 지운다. 남은 17개는 게시판
디렉터리의 레이아웃·컴포넌트, 쪽지 레이아웃·오류 화면·폼 검증, 문자 폼 검증과 그 시험 5개다. 앱 실행 경로에는 없지만 시험은 core
생성물의 vitest 에서 계속 돌았다. Java·게이트 차이는 0 이었다.

DEC-OPS-256 ④ 는 시작 구성을 이름 붙은 기능 목록으로 바꾸고 pack 순위를 걷기로 정했다. 해석기와 소유 선언을 하나로 합치는 일은
매니페스트 v2(11단계)가 맡는다. 그 전에 pack 모드를 읽는 관찰자(도달성 census·라우트 원장)를 고치면 생성기와 어긋난다.

## 결정

1. 시작 구성은 이름 붙은 기능 목록이다. 같은 기능 목록은 시작 구성으로 고르든 직접 고르든 같은 결과를 낸다 — 해석된 구성
   (테이블·시퀀스·권한·메뉴·탭 숨김·외래 키·기능 저하·외부 요구)과 소스 투영(Java·프런트·게이트·규칙 제거 집합)이 같다.
   시작 구성의 이름은 구성 식별(레시피·해시·lock)과 커밋된 기대치(게이트 승인·Java 연쇄 목록)에만 남는다.
2. 계약이 이를 지킨다([preset 동치 계약](../../../scripts/project-composer-preset-equivalence.test.mjs)). 카탈로그의 시작 구성마다
   같은 목록을 직접 고른 구성과 해석 결과(식별과 제거 경로 문자열 제외)를 비교하고, 생성기와 같은 판정인 정밀 점검의 제거 집합을
   양방향으로 대조한다. 시작 구성 목록을 카탈로그에서 읽으므로 새 시작 구성도 대조를 받는다. 차이는 파일 이름으로 보고한다.
3. 이번 단계는 pack 선언을 고쳐 차이를 없앤다. collaboration pack 의 `frontend.removePaths` 에 게시판 화면·쪽지 화면·문자 관리
   화면 디렉터리 셋을 더한다. 두 투영 수단은 그대로 두므로 pack 모드 관찰자와 생성기가 계속 같은 값을 본다.
4. pack·rank 제거, 시작 구성도 같은 간선과 제거 규칙을 따르는 해석기 단일화, 기능 소유 정본의 이동은 매니페스트 v2(11단계)에서
   한다. 그때 결정 2 의 계약이 두 수단을 하나로 바꾼 전후의 동치를 본다.

## 검증과 한계

- red 증명: 변경 전 트리에서 계약이 core 프런트 19개를 이름으로 지목한다. 더한 경로 하나를 빼면 그 디렉터리의 파일만, survey
  pack 이 collaboration 기능의 단말 파일을 지우면 collaboration 의 '시작 구성만 지운 파일'로, 해석기가 시작 구성 메뉴만 거르면
  해석 결과 차이로 붉다.
- 구성 해시가 바뀐다(카탈로그 해시가 manifest 를 덮는다). 로컬 DB 번들은 다시 만든다.
- 계약은 생성 전 판정(정밀 점검)까지 본다. 생성물의 DB 번들·하네스·시험은 CI 재사용 잡과 야간 시험(T2)이 본다.
- 정밀 점검 6회로 운영 계약 시간이 수십 초 는다. 계약은 별도 파일이라 다른 계약과 병렬로 돈다.
