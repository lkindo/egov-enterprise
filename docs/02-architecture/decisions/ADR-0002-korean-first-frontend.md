# ADR-0002: 한국어 우선 프런트엔드와 API 메시지 범위

- 상태: Accepted
- 결정일: 2026-08-15
- 관련: `frontend`, `foundation` MessageSource

## 맥락

프런트엔드는 `<html lang="ko">`와 한국어 화면을 사용하지만, `next-intl`은 로그인 오류 2개와
대시보드 문구 2개에만 연결돼 있었다. 사용자가 로케일을 고르는 UI는 없고 `NEXT_LOCALE` 쿠키만
바꾸면 일부 문구만 영어가 되어 한 화면 안에서 언어와 접근성 메타데이터가 불일치했다. 반면 백엔드
오류 응답은 `Accept-Language`와 ko/en MessageSource를 실제로 사용한다.

## 결정 요인

- 부분 번역을 다국어 지원으로 오인시키지 않아야 한다.
- 전자정부 관리자 UI의 현재 제품 언어는 한국어다.
- 실제 사용 중인 API 오류 지역화 계약은 보존해야 한다.
- 미래 다국어 도입 기준을 명확히 해 반쪽 스캐폴드의 재유입을 막아야 한다.

## 검토한 대안

1. 현 상태를 유지한다. 변경은 작지만 언어 혼합과 false-completion이 계속된다.
2. 전 화면을 ko/en으로 번역한다. 제품 요구·번역 책임자·키 추출 정책 없이 범위가 과도하다.
3. 프런트엔드를 한국어 단일 언어로 선언하고 반쪽 런타임을 제거한다. API 오류의 ko/en 지원은 유지한다.

## 결정

대안 3을 채택한다.

- 프런트 UI의 지원 언어는 한국어 하나다. `html[lang]`도 `ko`로 고정한다.
- `next-intl`, 프런트 카탈로그, 로케일 쿠키 유틸과 연결되지 않은 메시지 상수는 제거한다.
- 백엔드의 `messages_ko.properties`·`messages_en.properties`와 `Accept-Language` 오류 응답은
  비브라우저 API 소비자를 위한 별도 계약으로 유지한다.

## 결과와 재도입 조건

- 장점: 번들·요청 설정·중복 카탈로그가 줄고 화면 언어가 일관된다.
- 비용: 영어 UI는 제공하지 않는다. 영어가 필요한 파생 프로젝트는 새 제품 기능으로 도입해야 한다.
- 다국어 재도입은 지원 로케일과 번역 책임자가 정해지고, 가시적 로케일 선택기, `html[lang]` 동기화,
  화면 단위 카탈로그 완결성, 누락 키/전환 E2E가 한 묶음으로 구현될 때만 허용한다.
