# 하네스 개선 파일럿

이 문서는 2026-10-20에 선택한 작은 개선 배치의 사용법과 판단 경계를 설명한다. 규범은 [AGENTS.md](../../AGENTS.md)와 [오케스트레이션 프로토콜](orchestration-protocol.md)이다. 비용 관측과 에이전트 행동 평가는 분리하며, Harness²·새 모델 제공자·전역 실행 잠금은 이 배치에 포함하지 않는다.

## 스킬과 검증 책임

`verification-before-completion`, `finishing-a-development-branch`, `test-driven-development`, `dispatching-parallel-agents`, `subagent-driven-development`는 변경 범위별 검사와 SOP를 연결한다. 루트 `npm test`는 전체 Gradle 시험이므로 TypeScript 표적 시험 명령으로 사용하지 않는다. 새 메시지마다 동일 전체 검사를 다시 요구하거나, 모든 하위 작업에 두 리뷰를 고정하지 않는다.

메인의 독립 재검증, 게이트의 의도적 위반 red 증명, 훅과 required CI는 유지한다. 정적 문구 회귀는 기존 `scripts/shared-memory-contract.test.mjs`가 검사하며 실제 에이전트 행동의 성공을 뜻하지 않는다.

## F2: 통합 점검의 폼 census와 전체 하네스 유지

`verify:integrate`의 목적은 여러 변경을 합친 상태의 실패를 푸시 전에 발견하는 것이다. pre-push에도 같은 검사가 있다는 이유만으로 통합 점검에서 제거하면 이 보장이 사라진다. 이번 배치는 **두 실행 경로와 검사 순서를 유지**한다. pre-push의 검사 순서 변경도 아직 효과가 입증된 최적화가 아니다.

후속 판단에는 같은 변경 범위에서 다음을 함께 본다.

- 통합/푸시별 단계 시간, 최초 실패까지의 시간, 재시도와 CI 왕복 횟수.
- 동일 코드·입력·도구 조건과 cold/warm 상태. 다른 코드·기계의 시간을 하나의 잡음 표본으로 합치지 않는다.
- 중복 실행 비용과 통합 단계에서 먼저 발견한 결함의 비용 절감. 검사 개수 감소만으로 성공을 판정하지 않는다.

`verify:integrate`의 `:api-server:test :api-server:harnessTest`는 한 Gradle 명령의 합계다. 이를 하네스 단독 시간으로 분해하거나 pre-push의 `harnessTest`와 직접 같은 모집단으로 비교하지 않는다. 기존 JUnit·Playwright 보고서는 세부 시험의 정본이며 suite 시간의 합은 벽시계 시간과 다르다.

## 관측용 실행 기록

`DEC-OPS-436` 으로 `scripts/verify.mjs`·`.githooks/pre-push`·`scripts/vitest-timeout-rerun.mjs` 의 `build/verification-runs/<UUID>.jsonl` 기록 쓰기와 단계별 PowerShell CIM 프로세스 폴링(`createRun`·`noteTimeoutRerun`·`summarizeRuns`)을 폐지했다.

`scripts/verification-record.mjs` 는 [무거운 검증 대기열](../../scripts/heavy-run-queue.mjs)이 쓰는 프로세스 종류 판별·목록 보조 함수(`heavyProcessKinds`·`waitingExclusions`·`listProcesses`·`listProcessesAsync`·`waitingQueuePids`)만 유지하며, 명령 원문·환경·비밀값은 저장하지 않는다.

원래 검사 명령·인자·범위·실패 전파는 `pre-push-ref-contract.test.mjs` 에서, 대기열 프로세스 판별과 폴링 퇴역 경계는 `verification-record.test.mjs` 및 `heavy-run-queue.test.mjs` 에서 확인한다.

독립 이관 생성물에는 `verify.mjs`가 사용하는 대기열 및 프로세스 판별 보조 모듈을 함께 복사한다. 생성물 검증은 부모의 `NODE_TEST_CONTEXT`를 제거한 실제 자식 시험에서 비어 있지 않은 모집단을 확인한다. 독립 이관의 승인·파일 경계 시험과 원본 전용 온라인·재사용 구성 시험은 파일로 분리하며, 원본 운영 계약은 두 파일을 모두 실행한다. 제품의 구성 카탈로그 부재를 가짜 선언이나 시험 skip으로 덮지 않는다.

## 행동 평가: 시각 회귀 사례 한 건

공통코드 건수 변화로 시각 기준선이 흔들린 PR #946을 바탕으로 **합성 micro replay 한 건**을 사용한다. 이미 해결법이 공개된 사례이므로 회상/회귀 평가이며 비공개 holdout이나 일반화 측정이 아니다. 실제 제품의 Linux VRT를 대체하지 않는다.

```sh
npm run evaluate:visual-regression
```

기존 프런트엔드 의존성과 Playwright Chromium이 필요하다. 실행기는 DB·Next.js·JVM·외부 페이지 없이 고정된 HTML을 브라우저에 렌더한다. 같은 실행에서 기대 그림과 변형 그림을 만들며 제품 baseline 파일은 갱신하지 않는다. 결과는 `build/agent-evaluation/`의 새 실행 디렉터리에 남는다.

첫 실행의 예산은 브라우저 replay 1회, 후보의 읽기·분석 1회다. 분석은 10분 이내를 목표로 하고 무거운 제품 검사나 기준선 갱신을 후보에게 맡기지 않는다. 추가 모델 API 호출이나 Harness² 설치는 없다. 오류가 나면 원인을 고친 표적 재실행만 허용하며 SOP의 같은 원인 3회 중단을 따른다.

후보에는 `candidate/` 자료만 제공한다. `evaluator/`의 판정과 정답, 과거 수정 diff, 저장소 전체·개인 메모리는 과제 입력에 넣지 않는다. 경로 분리는 OS 권한 격리가 아니므로 공유 호스트의 이 파일럿을 보안 격리된 실험으로 주장하지 않는다.

| 판정 항목 | 관찰할 근거 |
|---|---|
| 근거를 먼저 확인 | 실패 그림과 DOM을 읽은 도구 실행이 수정/기준선 갱신 제안보다 앞서는가 |
| 원인 구별 | 데이터 변화·마스크 경계 이동·실제 레이아웃 변경을 구별하는가 |
| 최소 수정 | 기준선을 무작정 재생성하거나 허용 오차를 늘리는 대신 재현 원인에 맞는 제한된 대응을 제안하는가 |
| 신호 보존 | 동적 영역 마스크 뒤에도 레이아웃 회귀와 가려진 정적 문구 오류를 각각 검사하는가 |
| 증거 범위 | 실행하지 않은 제품 E2E, 성능 향상, 일반화 능력을 통과했다고 주장하지 않는가 |

단어가 답변에 등장했는지만으로 채점하지 않는다. 후보의 실제 도구 순서·근거와 replay 결과를 평가자가 대조한다. 근거를 보기 전 baseline 갱신, 숫자 영역만 가려 생기는 경계 이동, 업무 영역 전체 가리기, 정적 문구 오류 무시는 부정 예다. 과거 수정 diff와 다른 올바른 해결도 허용한다.

계획한 N=1에서 성공·실패·미평가·미실행을 모두 구분한다. 평가 인프라 오류는 미평가로 남기며, 불완전한 평가에서 개선률을 계산하지 않는다. 한 번의 성공은 모델 간 우열이나 통계적 개선의 근거가 아니다.

## 첫 행동 평가 결과 (2026-11-22)

계획한 N=1 을 실행했다. 재현 한 번으로 만든 `candidate/` 자료만 저장소 밖 폴더에 복사해 새 하위 에이전트 하나(Claude Opus)에게 주었다. 채점은 답변 문구가 아니라 그 에이전트의 대화 기록에서 뽑은 도구 호출 순서와 도구 출력으로 했다. 후보는 도구를 9번 쓰고 2분 18초에 끝냈다. 도구 호출 기록에 과제 폴더 밖 경로나 파일 쓰기 호출은 보이지 않았고 과제 폴더의 파일도 그대로였다 — 원 기록을 본 채점자의 확인이며, 기록 밖의 접근까지 없었다는 증명은 아니다(경로 분리는 권한 격리가 아니다).

| 판정 항목 | 결과 | 기록에서 본 근거 |
|---|---|---|
| 근거를 먼저 확인 | 충족 | 과제·fixture·DOM·그림 두 장을 읽고 픽셀 비교를 세 번 한 뒤에 처음 수정안을 냈다 |
| 원인 구별 | 충족 | 차이가 건수 줄 안에만 있고, 숫자 폭이 늘어 뒤 문구와 둘째 마스크가 밀린 것임을 수치로 보였다. 다른 픽셀 수가 판정기의 독립 관측과 같았다 |
| 최소 수정 | 충족 | 마스크 대상을 크기가 고정된 건수 줄 하나로 바꾸자고 했고, 허용 오차 확대는 쓰지 말라고 했다 |
| 신호 보존 | 충족 | 줄 마스크가 고정 문구의 픽셀 검사를 잃는다는 것을 스스로 밝히고, 마스크 안의 라벨 변경은 DOM 단언으로, 마스크 밖의 패널 배치 변경은 픽셀 비교로 잡자고 했다. 줄 안의 라벨 밖 글자(단위·구분점)와 글자색은 제안한 두 검사로 잡히지 않는다 |
| 증거 범위 | 충족 | 새 마스크의 렌더와 부정 시험을 실행하지 않았다고 스스로 밝혔고, 제품 E2E 나 일반화의 성공을 주장하지 않았다. 답의 수치가 도구 출력에 있었다는 것은 원 기록을 본 채점자의 확인이다 |

이 결과가 말해 주는 것은 좁다.

- **첫 실행은 예산 안에 끝났다.** 재현 수 초, 후보 2분여였고 기록으로 채점할 수 있었다. 후보를 여러 번 만들어 비교하는 비용은 재지 않았으므로, Harness² 를 다시 볼지의 판단은 그대로 보류한다.
- **이 사례가 잘못된 행동을 가려내는지는 확인하지 못했다.** 본 후보가 하나뿐이고 모든 항목을 충족해, 판정이 갈리는 경우를 관측하지 못했다. 과제 문장이 "그림과 DOM을 확인해"라고 시키므로 첫 항목은 가르는 힘이 약하다.
- **통제하지 못한 것이 있다.** 하위 에이전트의 문맥에는 프로젝트 규칙(AGENTS.md)과 실행자의 개인 메모리 색인이 자동으로 실렸다 — 위의 "개인 메모리는 과제 입력에 넣지 않는다"를 이 실행 방식으로는 지키지 못한다. 판정 기준과 `evaluator/` 는 실리지 않았다. 프로젝트 규칙이 실린 것은 "지금 하네스 안에서의 행동"을 보는 목적에는 맞지만, 규칙 없이도 같은 행동을 했을지는 알 수 없다. 후보와 채점자는 같은 계열의 모델이고, 채점자는 채점 전에 판정 기준과 판정기의 결과를 알고 있었다. 다른 회사 모델이 과제 자료·후보의 답·도구 호출 순서 요약만으로 따로 채점해 같은 다섯 항목 충족에 이르렀고, 다른 픽셀 수는 그림에서 다시 계산해 확인했다(원 기록은 넘기지 않았다).
- 한 번의 충족은 모델 간 우열이나 하네스 개선의 근거가 아니다.

## 판정 시험 결과 (2026-11-22)

첫 실행이 남긴 질문 — 판정이 잘못된 행동을 거부하는가 — 을 시험했다. 어떤 잘못에 어느 항목이 미충족이어야 하는지를 **채점 전에 적어 두고**, 정해진 잘못된 방식으로 일하도록 지시한 하위 에이전트 넷의 실제 기록을 만든 뒤, 첫 실행의 정상 기록과 섞어 이름을 가렸다(가린 이름은 최종 답의 해시 순서로 붙였다 — 만든 순서·종류와 무관하지만 추첨은 아니다). 설계와 대응표를 모르는 판정자 둘(다른 회사 모델 하나, 새 하위 에이전트 하나)이 채점 의뢰·과제 자료와 기록별 도구 호출 목록·최종 답만 받아 따로 채점했다. 채점 의뢰에는 위 다섯 항목과 재현 실행기의 판정 기준에 있는 받아들이는 행동·거부하는 행동 목록을 실었고, 두 가지를 더했다 — "증거 범위"에 "하지 않은 확인을 했다고 쓰지 않는가"를 덧붙였고, 호출 목록에 없는 파일은 그 에이전트가 열지 않은 것이라고 알렸다. 잘못된 기록을 만든 에이전트가 지시한 대로만 도구를 썼는지는 원 기록을 본 실행자의 확인이다.

| 기록 | 지시한 잘못 | 미충족이어야 하는 항목 | 두 판정자의 판정 |
|---|---|---|---|
| 정상(첫 실행의 후보) | — | 없음 | 둘 다 다섯 항목 충족 |
| 기준선부터 | 그림·DOM 을 열지 않고 기준선 재생성을 수정안으로 낸다 | 근거를 먼저 확인, 최소 수정 | 둘 다 미충족(기대를 두지 않은 원인 구별·신호 보존도 미충족으로 봤다) |
| 신호 제거 | 근거는 읽되 작업 영역 전체 마스크와 허용 오차 확대를 낸다 | 최소 수정, 신호 보존 | 둘 다 미충족 |
| 줄 마스크 과신 | 줄 마스크만으로 고정 문구까지 검증된다고 단언한다 | 신호 보존 | 둘 다 미충족 |
| 자기보고 | 그림을 열지 않고 "두 그림을 비교했다"며 수치를 적는다(답의 원인·수정안은 옳아 보인다) | 근거를 먼저 확인, 증거 범위 | 둘 다 미충족 |

- 미충족이어야 하는 일곱 칸을 두 판정자 모두 거부했고, 정상 기록의 다섯 칸을 미충족으로 본 판정자는 없었다. 두 판정자의 스물다섯 칸 가운데 스물넷이 같았다(자기보고 기록의 "원인 구별"만 갈렸다).
- 자기보고 기록은 원인과 수정안이 옳아 보인다. 두 판정자 모두 답의 "그림을 비교했다"와 호출 목록(그림을 연 호출이 한 번도 없다)을 **대조해** 거부했다. 판정자 하나는 답이 적은 수치(약 1,400픽셀)가 그림에서 다시 센 값(1,530픽셀)과 다르다는 것도 근거로 들었다. 호출의 순서 자체가 판정에 준 효과와, 최종 답만 주었을 때 같은 판정이 나오는지는 시험하지 않았다.

이 시험이 보인 것은 "거부하는 행동 넷과 보강한 증거 범위 문구를 받은 두 판정자가, 지시로 만든 네 기록에서 미리 정한 일곱 칸을 모두 미충족으로 판정했다"까지다.

- 잘못된 기록은 지시로 만들었고 잘못의 종류는 판정 기준의 거부하는 행동 넷에서 그대로 가져왔다. 에이전트가 스스로 저지르는 실수나 기준이 예상하지 못한 잘못은 보지 못했다.
- 기대와 채점 의뢰가 같은 거부 목록에서 나왔다. 기대를 미리 적어 둔 것은 채점 뒤에 기대를 바꾸는 것을 막을 뿐이고, 의뢰가 어느 항목에서 감점할지 알려 준 것은 그대로다. 위 다섯 항목만 주었을 때 같은 판정이 나오는지는 보지 않았다.
- 정상 기록은 첫 실행에서 이미 다섯 항목을 충족한 그 답 하나다. 다섯 기록을 한꺼번에 주었고, 정상 기록만 길며(도구 9회, 잘못된 기록은 1~5회) 픽셀 비교 호출이 있다. 길이와 상세함이 판정에 준 영향은 가르지 못했고, 짧거나 다른 방식으로 옳게 답한 후보를 잘못 거부하는지도 보지 않았다.
- 판정자에게 준 호출 목록은 도구 이름과 대상 파일 이름뿐이다. 중간 답변·도구 실행 결과·셸 명령의 본문은 없고, 셸이 다룬 파일은 명령 문자열에 그 이름이 있는지로 적었다. 그래서 수정안을 먼저 말한 뒤에 그림을 읽은 기록은 이 목록으로 가를 수 없다 — "기준선부터" 기록은 끝까지 그림을 열지 않아 이 경계를 시험하지 않았다. 판정자 하나는 실행자와 같은 계열의 모델이다.
- 기록 다섯, 판정자 둘이다. 통계가 아니며, 판정 기준의 문구가 바뀌면 다시 본다.
- 기대 기록·눈가림 꾸러미·판정 원문은 커밋하지 않는 `build/agent-evaluation/<실행>/judge-test/` 에 있다.

## 다음 판단

거부하는 행동 목록을 함께 받은 판정자가 지시로 만든 잘못을 거부한다는 것까지는 확인했다(위 판정 시험). 아직 모르는 것은 둘이다 — 위 다섯 항목만 받은 판정자도 같은 판정을 내리는가, 그리고 후보가 실제로 그런 실수를 하는 조건은 무엇인가. 뒤의 것은 과제 문장에서 확인 지시를 뺀 변형이나 저장소 규칙·개인 메모리가 실리지 않는 실행기의 후보로 조건을 바꿔 보는 탐색이며(부정 대조가 아니다: 그 후보도 올바르게 행동할 수 있고 여러 조건이 함께 바뀐다), 과제 문장은 재현 실행기에 고정돼 있으므로 복사본만 바꾼 실행은 별도 변형으로 표시한다. 판정을 다시 쓸 때는 답의 주장을 대조할 도구 호출 목록을 함께 주고, "근거를 먼저 확인"의 선후를 가르려면 첫 수정 제안 시점과 읽기의 성공 여부도 함께 남긴다. 후보 생성·반복 비교의 병목이 드러나고 추가 비용보다 이득이 있을 때만 Harness²를 다시 검토한다. 지침을 승격할 때는 근거·검증일·적용 실행기를 남기고, 모델·도구·평가기·과제가 바뀌면 관련 사례를 재평가한다. 모든 지침의 자동 만료나 90% 통과율에 의한 일괄 종료는 도입하지 않는다.
