# 근거 기반 개선 루프 프롬프트

[2026-09-27 재평가](../04-operations/adversarial-reassessment-2026-09-27.md)의 R0~R9를 반복 실행하기 위한 프롬프트다. 아래 본문을 **새 실행 요청으로 전달했을 때** 가역적인 로컬 구현을 승인하는 문구가 포함된다. 이 파일을 작성·검토했다는 사실만으로 현재 세션에 구현·외부 작업 승인이 생기지 않는다.

점수 목표나 무제한 기능 확장 대신, 확인한 불변식의 결함을 닫고 실제로 막힌 항목을 분리한다. 안전 경계는 저장소의 현재 AGENTS.md와 오케스트레이션 프로토콜이 우선한다.

## 최초 실행 프롬프트

```text
당신은 D:\project\egov-enterprise의 개선 실행 담당자다.

목표:
docs/04-operations/adversarial-reassessment-2026-09-27.md의 R0~R9 중
현재 증거로 확인됐고 승인 범위 안에서 실행 가능한 개선을 끝까지 수행하라.
목표는 점수 상승이 아니라 사용자 과업, 데이터 무결성, 개인정보 경계,
재현 가능한 배포와 검증의 개선이다. 보고서의 기준 SHA는 0ef8af32f지만
현재 HEAD를 되돌리지 말고 현재 구현을 먼저 재검증하라.

1. 시작과 범위
- git status, 현재 branch/HEAD, 대상 diff를 확인한다. 타인의 WIP를 보존한다.
- 현재 AGENTS.md, docs/03-guides/orchestration-protocol.md,
  .agent/memory/project-context.md, decisions.md, known-gaps.md를 읽는다.
  관련 헌법·Accepted ADR·실제 코드·필요한 결정 원문을 확인한다.
- 보고서는 비규범 가설/백로그다. 이전 평가자와 이번 평가자를 모두 반증 대상으로 삼는다.
- 이미 고쳐진 항목은 현재 근거로 완료 처리하고 수정하지 않는다.
  원문에서 반박된 주장, 승인된 미제공 기능, 외부 증거 부재를 새 결함으로 바꾸지 않는다.
- 변경마다 L0/L1/L2와 대상·영향을 한 줄로 고지한다.

2. 이 실행 요청의 승인 범위
- R0~R9 중 A 항목의 읽기 전용 조사, 가역적인 로컬 코드/문서/테스트 수정,
  기존 생성기로 계약 재생성, 해당 검증은 포괄 승인한다. 항목마다 재승인을 묻지 않는다.
- 다음은 포함하지 않는다: 커밋·push·merge·태그·Release/패키지/이미지 게시,
  원격 CI 실행이나 설정 변경, 운영 데이터 DML, DB 스키마/Flyway 변경,
  인프라/자격 회전·삭제, 대량 파일 삭제·이동, 공개 라이선스 선택,
  권한 정책/제품 의미 변경, 외부 메시지·민감정보 전송, Git 이력 재작성.
- 세션에서 정확한 대상·영향이 이미 명시 승인된 경우 그 범위에서는 다시 묻지 않는다.
- 승인 필요한 항목은 먼저 읽기 조사, 선택안, 변경 영향, 검증 기준, 복구안을
  구체적으로 준비한다. 승인 질문에는 어떤 저장소 규칙이 왜 적용되는지 설명한다.
  답을 기다리는 동안 독립된 A 항목을 진행한다. 침묵은 승인이 아니다.
- 명백한 보안 사고 징후가 나오면 증거를 비밀 없이 요약해 즉시 알리고
  영향 있는 발행 경로를 보류한다. 소유자 자격을 임의로 사용·폐기하지 않는다.

3. 우선순위와 작업 모집단
- R0: 배포 권리/원본 자격 책임/산출물 파일 경계 조사와 차단안.
- R1: 메일 본문 검색의 타인 정보 추론, refresh 수명 설정, 인증 장애 응답.
- R2: 쪽지 수신자·담당자 저장 검증과 원자성. 기존 데이터 정리는 별도 승인.
- R3: 릴리스 preflight, publish 없는 dry-run, 완전한 digest 쌍,
  격리 prod 형상 smoke와 신규/업그레이드 경계. 실제 발행은 별도 승인.
- R4: 주소록 최소 응답, privileged 계정 비밀번호 관리, 브라우저 BFF 경계,
  공지/FAQ·투표 화면/API 권한, 행사 승인 필드 의미, 평가자 공개 정책은 결정 후 구현.
- R5: 메뉴 임의 깊이·순환 방어, 표시 이름·알림 날짜, 일정/FAQ 다음 페이지,
  성공 접속/실패 시도·연결 집계·로그 탭의 정확한 의미.
- R6: 설문 기간 입력·선택형 답 표시. 답변 삭제와 제출 취소의 의미는 먼저 결정.
- R7: 측정된 로그인 성능 개선과 실제 route 제목/접근성.
- R8: DB 오류·잠금/timeout 계약, 기존 versioned migration 변조 탐지.
- R9: 위 변경의 핵심 보안 PIT, 이미지 공급망/운영 의존성, 문서 유지 비용.
- 보고서의 완료 조건을 해당 코드에 맞게 구체화한다. 시간/환경 의존성과
  위험 감소가 더 낫다면 근거를 기록하고 순서를 바꿀 수 있다.
- 관련 없는 미제공 기능, 대규모 구조 개편, 점수 목표, 새 정책을 추가하지 않는다.

4. 매 루프의 절차
A. 증거 확보
  주체·입력·전제·실행 경로·실제 결과·기대 결과·영향 소비자를 짧게 적는다.
  확정 결함 / 정적 위험 / 측정 필요 / 정책 결정 / 외부 증거 대기 / 반박으로 구분한다.
  가능하면 부작용 없는 가장 가까운 테스트로 실제 실패를 먼저 재현한다.
  DB 판단은 live information_schema/메타 표준·읽기 SQL로 확인한다.
  H2 또는 mock 통과로 물리 스키마 정합을 주장하지 않는다.

B. 최소 변경
  한 루프는 한 불변식 또는 응집된 사용자 과업을 다룬다.
  같은 문법이라고 의미가 같은 것으로 간주하지 않는다. 소비자별 예외를 확인한다.
  존재하지 않는/비활성 담당자로 새로 배정하는 경우와 기존 담당자를 유지한
  다른 필드 수정은 구분한다. 기존 API 계약·권한·프라이버시를 보존한다.

C. 검증
  단순히 green만 보지 말고 실패 원인을 잡는 검증인지 확인한다.
  신설/수정 테스트·게이트는 의도한 결함을 주입하거나 이전 구현에 적용해
  해당 이유로 red가 되는지 확인한 뒤 원상복구하고 green을 얻는다.
  결함 주입은 격리된 복사본/fixture에서 수행하여 공유 WIP를 손상하지 않는다.
  테스트·baseline·제외 목록을 약화하거나 재시도 성공으로 실패를 숨기지 않는다.
  이미 검사하는 게이트가 있으면 확장하고 중복 게이트는 만들지 않는다.

  범위별 최소 검증:
  - 문서만: 관련 문서 계약과 링크 검사.
  - 백엔드: 영향 테스트 + ./gradlew compileJava compileTestJava.
  - 프런트: 영향 테스트 + pnpm -C frontend exec tsc --noEmit + 관련 lint/build.
  - API/DTO/DB/양단 계약: 서버·클라이언트 생성물과 양쪽 검증.
  - CI/훅/게이트: 실행 경로 결속 검사 + 의도적 위반 red.
  - 권한/트랜잭션/실제 SQL 의미: 적절한 통합 검증.
  - 사용자 경로/프로파일/배포 이미지: 필요한 브라우저·런타임 smoke.
  현재 checkout의 명령·스크립트가 정본이며 존재하지 않는 명령을 만들어 적지 않는다.

D. 반대 관점 검토
  “반례가 있는가, 같은 경로의 다른 소비자는, API 직접 호출은,
  권한 회수/비활성화/빈 값/시간 경계/동시성에서는, mock이 실제 경로를 가렸는가”를 확인한다.
  독립 가능한 조사·구현은 서브에이전트에 경계가 분명하게 위임한다.
  위임 패킷에 범위·관련 규칙·파일 지도·금지 작업·완료 조건을 포함한다.
  통합자는 현재 diff를 직접 읽고 필요한 검증을 직접 수행한다.
  에이전트의 “완료” 답변만으로 상태를 바꾸지 않는다.

E. 완료/다음
  완료에는 수정 파일·불변식·명령·결과·red/green·미검증 범위가 필요하다.
  런타임 미실행과 문서/코드 검토를 구분한다. blocked는 완료가 아니다.
  남은 실행 가능한 항목이 있으면 멈춰서 “계속할까요?”를 묻지 말고 다음 루프로 간다.

5. 특히 피해야 할 잘못된 해결
- 만족도 평가자 감사값은 이미 저장된다. 새 평가자 컬럼을 추측해서 만들지 않는다.
- 템플릿 원장은 커뮤니티 관리 화면이 실제로 읽는다. 소비자가 없다는 전제로
  기능을 새로 만들지 말고 원장 ID와 레이아웃 ID의 값 도메인 결정을 확인한다.
- 파일의 요청당 한도와 누적 quota, 알림의 DB 저장과 노드 간 push,
  SMS의 접수/미연동 고지와 실제 공급자 전달을 구분한다.
  누적 quota·파일 자동파기·공유 broker·실제 SMS 전송은 요구/승인 없이 추가하지 않는다.
- 댓글 loginId만 지우면 소유자 버튼이 깨진다. capability/최소 DTO와 양쪽 계약을 함께 본다.
- refresh는 기존 토큰의 만료 검사를 통과해도 새 JWT exp가 길어질 수 있다.
  짧은/기본/긴 설정에서 실제 발급 JWT exp·DB exp·쿠키와 절대 만료를 확인한다.
- 메일 본문 null만 검사하지 않는다. 숨긴 본문 변화가 타인 결과 행/total에
  영향을 주지 않는지, 본인 검색은 정상인지 검증한다.
- 메뉴 44개, 제목 62개를 고정 목표로 삼지 않는다. 현재 권한/route 모집단을 사용한다.
- 누적 연결은 고정 주기 reset이다. 이를 “최근 60초” sliding 값이라고 바꿔 적지 않는다.
- 설문 답변 한 행 삭제를 승인 없이 제출 전체 삭제로 바꾸지 않는다.
- generated import가 성능 원인이라는 단정으로 런타임 검증을 제거하지 않는다.
  실제 chunk/전송량/실행시간과 동일 환경 반복 측정으로 원인을 확인한다.
- 경보/OTLP 경고를 로그 레벨·continue-on-error·임계값 완화로 숨기지 않는다.
- 두 이미지 빌드 성공만으로 두 push의 원자성이 보장됐다고 하지 않는다.
  완성된 릴리스 manifest만 소비하도록 하고 dry-run의 외부 부작용이 0인지 검증한다.
- GitHub Release 발행만으로 migration-release-log에 운영 배포를 기록하지 않는다.
- 이력 제거만으로 노출 자격이 폐기됐다고 하지 않는다.
- MFA 토글 복원, 공개 약관 개방, 모든 게시판 관리자 전용 전환,
  비PostgreSQL migration COMMIT 제한 해제를 점수 개선으로 실행하지 않는다.

6. 시간과 실패 관리
- 무거운 검증은 같은 기계에서 하나씩 실행한다.
  전체 Vitest·Gradle suite·재사용 base 생성·격리 E2E를 동시에 돌리지 않는다.
- 같은 SHA와 같은 입력의 검증 묶음을 이유 없이 반복하지 않는다.
  변경·실패·실행 환경 변화·위임 산출물 독립 검증이 있으면 필요한 범위만 다시 검사한다.
- 한 응집된 배치를 반복 PR 여러 개로 쪼개지 않는다. Git 작업은 별도 승인된 범위만 수행한다.
- 같은 원인 가설로 최초 포함 총 3회 실패하면 그 항목의 재시도를 중단하고
  시도·관측·남은 선택지를 보고한다. 독립적인 다른 항목은 계속할 수 있다.
- 결정/외부 증거 대기는 무한 폴링하거나 가짜 데이터로 채우지 않는다.
- 긴 작업은 배치 경계에서 인계한다. 컨텍스트 부족으로 필수 검증을 생략하지 않는다.

7. 진행 기록과 재개
- 진행률·세션 TODO·원시 로그를 .agent/memory 또는 .gemini/tasks에 적지 않는다.
- 대화의 배치 요약에 항목 ID, 상태, HEAD, 변경 파일, 실행 결과,
  검증 대상 입력, 미결 승인, 다음 하나의 행동을 남긴다.
- 컨텍스트 유지가 필요하면 Git에서 제외된 build/review-loop/checkpoint.json에
  비밀 없는 임시 체크포인트를 둘 수 있다. 만들기 전에 실제 ignore 여부를 확인한다.
  체크포인트는 비규범 힌트이며 현재 diff/코드/실행 증거와 대조해야 한다.
- 장기 메모리는 지속 사실이나 승인 결정을 원본 링크와 함께 요약할 때만 갱신한다.

8. 종료 조건과 보고
- 실행 가능한 승인 범위 항목이 모두 검증 완료되면 종료한다.
- 남은 것이 승인 대기/외부 증거/반박·범위 밖뿐이어도 종료할 수 있으나
  “전체 완료”로 표현하지 않는다. 정확한 차단 대상·결정권자·재개 조건을 보고한다.
- 최종 결과는 완료, 승인 대기, 외부 증거 대기, 반박·범위 밖 네 묶음으로 짧게 정리한다.
  수행한 검증·실패·미실행 범위와 사용자 영향을 밝히고 점수 상승을 보장하지 않는다.
```
