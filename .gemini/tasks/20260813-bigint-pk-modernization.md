# BIGINT 자동 PK 현대화 실행 원장

> 상태: L2 설계결정 승인 후 실행 중
> 승인 근거: 사용자는 비운영 시스템임을 전제로 수동 PK가 필요한 항목은 유지하고, 내부 기술 PK는 `BIGINT IDENTITY`로 전환하며 기존 데이터도 일괄 변환하는 방향의 계획 수립과 순차 실행을 명시했다.
> 실행 원칙: 공유/운영 DB에는 직접 DDL/DML을 실행하지 않는다. 저장소 Flyway와 일회성 PostgreSQL 17 검증 DB에서만 전환을 검증한다.

## 1. 물리 스키마 실측

- 실측 DB: 로컬 프로젝트 E2E PostgreSQL 17.9 (`egov-e2e-postgres`, `127.0.0.1:15432`)
- 실측 방법: `.agent/scripts/db-bridge.js`의 SELECT-only/read-only 연결
- 실측 시점 Flyway: rank 34, versioned migration 최신 적용본 `V2_31`, 실패 0
- 주의: 저장소 최신은 `V2_48`이므로 이 DB는 최신 구조 검증원이 아니라 기존 데이터·타입·FK census 증거다. 최종 정합은 빈 PostgreSQL 17에 전체 Flyway를 적용하는 `schemaValidationTest`로 판정한다.
- 대상 64개 엔티티가 매핑하는 물리 테이블은 모두 존재했다. 63개는 수동 문자열/복합 PK이고, `tb_menu_info.menu_sn`만 이미 `BIGINT`였다.
- 대상 테이블의 정확한 행 수 합계는 4,272행이다. 최다는 `tb_web_log` 4,003행이며, 44개 BIGINT 전환 후보 중 다수는 0행이다.
- 주요 참조 위험: `tb_file_master.atch_file_id` inbound FK 14개, `tb_user_info.esntl_id` 10개, `tb_bbs_master.bbs_id` 5개, `tb_bbs_item.pst_id` 3개다.
- 예외: `SurveyRespondent` 엔티티는 수동 단일 PK처럼 보이지만 실제 `tb_srvy_rspdnt` PK는 `(srvy_tmplt_id, srvy_id, srvy_rspdnt_id)` 3컬럼 복합키다. 선행 매핑 정합성 검토 없이 자동키로 바꾸지 않는다.
- 중복 매핑: `DeptManage`와 `OrganizationManage`가 모두 `tb_ognz_info.ognz_id`를 사용한다. 두 엔티티를 하나의 물리 PK 변경으로 함께 다뤄야 한다.

## 2. 표준 메타 판정

- `meta_standard_words`: 주소록=`ADBK`, 회원=`MBR`, 일련번호=`SN`이 대표어로 존재한다.
- `meta_standard_domains`: 기존 숫자 일련번호는 `일련번호N10`/`일련번호N22`이며 각각 `NUMERIC`이다.
- 자동 내부키는 PostgreSQL `BIGINT`이므로 `_id` 문자열 용어를 그대로 타입만 변경하지 않는다. `BIGINT`용 일련번호 도메인과 `_sn` 용어를 메타에 먼저 등록하고 물리 컬럼·JPA·API 명칭을 함께 맞춘다.

## 4. 실행 순서

1. **Wave 1 — AddressBook 파일럿**: 외부 inbound FK 0, E2E 데이터 각 1행. `adbk_id`→`adbk_sn`, `adbk_constnt_id`→`adbk_mbr_sn`, 자식 FK를 명시하고 DB/JPA/API/FE를 한 폐포로 전환한다.
2. **Wave 2 — 무참조·0행 단독 테이블**: Hpcm·InternetSvcGuidance·OnlineManual·Popup(완료), MyPageContent, DeptJobBox 등. Template은 자연키로 재분류해 제외.
3. **Wave 3 — 단일 FK 업무 테이블**: Banner, DeptJob, Diary, DtaUseStats, MemoReport, RewardManage, Schedule, Scrap, SentMail, WorkReport 등.
4. **Wave 4 — 묶음형 도메인**: Note 3종, OnlinePoll 3종, Survey 5종, Board/Blog/Community.
5. **Wave 5 — 고참조·고용량**: FileMaster와 로그 3종. FK 14개 및 쓰기량/배치 성능을 별도로 검증한다.
6. **Wave 6 — Menu 생성전략 보정과 예외 정리**: 기존 BIGINT 시드 충돌 방지, SurveyRespondent 복합키 매핑 정합, 린터 베이스라인 최종 축소.

## 5. 각 Wave 공통 완료 조건

- Expand: 신규 `_sn BIGINT GENERATED BY DEFAULT AS IDENTITY` 및 참조 `_sn` 컬럼 추가
- Sync: 기존 행과 FK를 결정적으로 백필하고 null/고아 0건 검증
- Redirect: JPA `Long` + `GenerationType.IDENTITY`, repository/service/controller/DTO/OpenAPI/frontend 소비자를 모두 이관
- Contract: 기존 문자열 기술키와 수동 채번 제거, 사유가 적힌 `-- linter:ignore`를 파괴 DDL 한 줄에만 적용
- 검증: 관련 단위/계약 테스트, `harnessTest`, `schemaValidationTest`, 백엔드 compile, 프론트 codegen/tsc, 필요 시 전체 `localGate`
- 가드레일: `PkGenerationStandardLinterTest.GRANDFATHERED`는 실제 전환이 끝난 엔티티만 사유와 함께 제거하고 baseline integrity manifest를 같은 변경에서 갱신한다.
